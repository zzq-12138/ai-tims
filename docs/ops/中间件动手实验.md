### 1.2 MySQL 前置部署（仅实验 A 的 MySQL 持久化扩展与实验 C 的可选落库需要）

**谁需要装**：
- **毕设 VM：已有 MySQL 8.0.46 @3306，账号 dev（密码 `~/secrets/mysql_pwd`），业务库 `aitims`——不要新建实例、不改密码、不动业务库**。若需要给 Nacos 建持久化库，直接在现有实例上建 `nacos_config` 库即可（见实验 A 前置依赖）。
- **云机：无 MySQL，需要时按下装**（完整命令，可直接复制）：

```bash
mkdir -p /home/dev/lab/mysql/conf /home/dev/lab/mysql/data
docker run -d --name lab-mysql \
  -p 13306:3306 \
  -v /home/dev/lab/mysql/conf:/etc/mysql/conf.d \
  -v /home/dev/lab/mysql/data:/var/lib/mysql \
  -e MYSQL_ROOT_PASSWORD=lab12345 \
  -e TZ=Asia/Shanghai \
  --health-cmd="mysqladmin ping -h localhost -plab12345" \
  --health-interval=10s --health-timeout=5s --health-retries=10 \
  mysql:8.0 \
  --character-set-server=utf8mb4 --collation-server=utf8mb4_general_ci

# 验收：healthy + 能进客户端
docker ps --filter name=lab-mysql          # 预期 (healthy)
docker exec lab-mysql mysql -uroot -plab12345 -e "SELECT VERSION();"
# 预期输出 8.0.x；字符集核验：
docker exec lab-mysql mysql -uroot -plab12345 -e "SHOW VARIABLES LIKE 'character_set_server';"
# 预期 utf8mb4
```

说明：4G 云机上需调参（`innodb_buffer_pool_size=128M` + `performance_schema=OFF`，配置文件经 `./conf` 挂载；不加参数时 MySQL 8 默认内存占用偏大，会挤压其它组件）。**3306 端口在任何环境都不对公网开放**（云机安全组，见 1.4）。

> ⚠ **两条实测教训（2026-11-04 学习机回填）**：
> 1. **本机 lab-mysql 是 `docker run` 起的独立容器，不是 compose 项目**——清理用 `docker rm -f lab-mysql`（见 7.2 已改正），执行 `docker compose -p lab-mysql down` 会报 no such project。
> 2. **云机上 Nacos 容器不能写 `127.0.0.1:13306` 连它**（容器里的 127.0.0.1 是 Nacos 自己）：要用 `172.17.0.1:13306`（docker0 网关）或同一 compose 网络内的服务名；MySQL 8 的 JDBC 串还需 `allowPublicKeyRetrieval=true&useSSL=false`，否则 caching_sha2 认证失败。

### 1.3 4G 云机：内存预算与 swap

预算基数：Ubuntu 空载 250~350M + Docker 100~150M ≈ 底座 0.5G，可用 ≈3.5G（以 `free -h` 为准）。每个组件上线前后各看一眼 `free -h`，可用 ≥1.5G 再动手。

**全组件通用：先开 2G swap**（Milvus 限额合计 2G 贴着可用内存跑，无 swap 则峰值触发 OOM killer——`docker ps` 里容器消失/Restarting，`dmesg | grep -i oom` 可见记录）：

```bash
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
free -h    # 预期 Swap 行 2.0Gi
```

云端没有 k3s，不存在 kubelet 与 swap 的兼容问题，放心开（k3s 的 swap 话题见第 6 节）。

### 1.4 云端安全组与公网红线（第一道墙）

安全组在阿里云控制台配置（**需在控制台确认**实例所属安全组与当前规则）。原则：**按需临时开、用完即关；管理界面类端口一律不对公网开放**。

| 端口 | 用途 | 公网放行？ |
|---|---|---|
| 22 | SSH | ✅ 开，但**限制来源 IP**（控制台配白名单） |
| 5000 / 5500 | registry（无认证 HTTP） | ⛔ **绝不开公网**。无 TLS 无认证 = 任何人可推恶意镜像。外部验证走 SSH 隧道 |
| 15672 / 8849 / 9091 | RabbitMQ/Nacos/Milvus 管理台 | ⛔ 不开公网，走 SSH 隧道（见下）；确需开放仅限内网 VPC 或加强认证（**需在控制台确认**内网条件） |
| 8848 / 9848 / 19530 / 5672 / 3306 / 6379 | 中间件服务端口 | ⛔ 默认不开；SSH 上去 curl localhost 即可验收 |
| **2375 / 2376** | Docker Remote API | ⛔⛔ **绝对禁止**。2375 无 TLS 等于把 root shell 挂公网，勒索挖矿最经典入侵口 |

SSH 隧道替代公网暴露（本机执行）：

```bash
# 本机浏览器访问云上的 RabbitMQ 管理台（35672 为偏移端口时）
ssh -L 35672:localhost:35672 root@<公网IP>
# 浏览器开 http://localhost:35672

# 一次转发多个端口（Nacos 控制台 + RabbitMQ 管理台 + registry）
ssh -L 18849:localhost:18849 -L 35672:localhost:35672 -L 5500:localhost:5500 root@<公网IP>
```

> ⚠ **这条 `ssh -L` 必须在你的本机执行，绝不能在云机自己身上执行**——否则 ssh 进程会在云机上监听 35672/18849/5500，之后容器 `up` 直接报 `address already in use`（2026-11-04 学习机实测踩坑）。隧道随 SSH 会话关闭而失效；本机若开了代理软件，浏览器访问 `localhost` 可能被拦截，需加代理例外或临时关闭。

### 1.5 云端 Docker 镜像加速（ECS 访问 Docker Hub 慢是常态）

```bash
# 阿里云专属加速地址：控制台 → 容器镜像服务 ACR → 镜像加速器（每账号一个专属地址，需在控制台确认）
sudo mkdir -p /etc/docker
sudo tee /etc/docker/daemon.json >/dev/null <<'EOF'
{
  "registry-mirrors": [
    "https://<你的ID>.mirror.aliyuncs.com",
    "https://docker.m.daocloud.io"
  ]
}
EOF
sudo systemctl restart docker    # 不重启不生效——VM 侧踩过的坑 #8 同款
```

备用前缀：`1ms.run`（`milvusdb/*` 靠它，daocloud 对该命名空间 403 的坑不因环境而消失）；etcd 走 `quay.io` 官方。

### 1.6 从 VM 搬镜像/配置上云（可选，省下载时间）

```bash

ssh ubuntu-server "docker save alpine:3.20 | gzip" > alpine.tgz
scp alpine.tgz root@<云公网IP>:/tmp/
# 云上：docker load < /tmp/alpine.tgz
```

注意：生产 VM 的正本 `docker/docker-compose.yml` 与 `~/secrets/` **不要整包拷上云**——云机按随时可释放的一次性实验场对待。

### 1.7 统一隔离方案（VM 铁律，云机照做养成习惯）

**实验根目录**：`/home/dev/lab/`，每个组件一个子目录。四条纪律（缺一不可）：
1. **独立 compose project 名**：`-p lab-<组件>`（决定网络与卷前缀）；
2. **端口偏移**：实验实例监宿主机偏移端口，容器内部端口不变；
3. **bind mount 数据卷**：数据落子目录，删目录即删数据。
4. **改完 compose 必须强制重建**：`ports` / `volumes` 的变更对已存在容器不生效，用 `docker compose -p lab-<组件> up -d --force-recreate`。**容器 healthy 只代表容器内进程正常，不代表端口映射正确**（学习机实测：ports 段缩进错一位，容器绿了但 curl 不通）。

## 2. 实验 A：Nacos（约 1.5h）

### 目标

从零写 compose 跑起 Nacos v3 standalone，理解它强制 AUTH_TOKEN 的怪脾气，并用真实微服务向它注册。

### 前置依赖

| 依赖 | 毕设 VM | 云机 |
|---|---|---|
| Docker + compose（1.1） | ✅ 已有 | 需自装 |
| MySQL（可选，仅「MySQL 持久化」扩展用） | ✅ 已有（1.2，直接用现有实例建库） | 需自装（1.2 完整命令） |

**何时不必装 MySQL**：本实验 L1~L3 用 Nacos 内置 Derby（`nacos-data` 卷持久化）完全够——毕设 VM 生产 Nacos 就是 Derby 形态。**何时需要**：想练「配置持久化到 MySQL」（更接近生产口径，答辩可讲）。步骤：

```bash

mysql -udev -p -h127.0.0.1 -e "CREATE DATABASE IF NOT EXISTS nacos_config DEFAULT CHARACTER SET utf8mb4;"

#    与 Nacos 3.0.3 对应的版本分支需现场确认；VM 可 wget 或本地下载后 scp）

# 3) 实验 compose 的 nacos 段加环境变量（L1 的 compose 基础上）：
#   SPRING_DATASOURCE_PLATFORM=mysql
#   MYSQL_SERV_ADDR=<Nacos 容器可达的地址>  MYSQL_DB=nacos_config
#   MYSQL_USER=dev / MYSQL_PASSWORD=<从 ~/secrets/mysql_pwd 取或 lab12345>
# 注意 MYSQL_SERV_ADDR 变量名以 Nacos 3 实际要求为准（需现场确认，起不来先看容器日志）
# ⚠ 地址写法（实测踩坑）：127.0.0.1:13306 在 Nacos 容器里指向它自己，必然连不上；
#   用 172.17.0.1:13306（docker0 网关）或与服务同 compose 网络时的服务名 mysql:3306；
#   JDBC 串追加 allowPublicKeyRetrieval=true&useSSL=false，否则 MySQL 8 认证失败
```

### L2 数据持久化

任务：给 compose 加卷（bind mount `./data:/home/nacos/data`），用控制台建一条测试配置（配置管理→新建，随便写个 `lab:test`），然后 `docker compose -p lab-nacos down && docker compose -p lab-nacos up -d`（**不带 -v**），重新登录控制台确认配置还在。

### L3 资源与安全

任务：加 `mem_limit: 512m`（对照正本 JVM_XMS=256m/XMX=512m 理解堆与容器限额的关系）；确认控制台当前未开鉴权（`NACOS_AUTH_ENABLE=false`），思考并写下：生产开 `true` 还需要改哪几项（写在记录表里）。

### L4 接入项目（真实调用；**仅毕设 VM 可做**）


**常见失败与判读**：

## 3. 实验 B：Milvus 三件套（约 2.5h，最长也最值）

| 依赖 | 毕设 VM | 云机 |

> 说明：项目事件流当前是 stub（M4 才接 RabbitMQ，发布签名不变），所以本实验的「真实调用」用管理 API 走通一条完整消息流——这正是 M4 接入后消息走的同一条路。此 L4 两环境都可做（不依赖项目服务）。

任务：发一条消息到默认交换机、路由到 `lab-queue`，再取出来：

```bash
# 发
curl -sf -u lab:lab123 -X POST http://localhost:35672/api/exchanges/%2F/amq.default/publish \
  -H 'content-type: application/json' \
  -d '{"properties":{},"routing_key":"lab-queue","payload":"tims-hello","payload_encoding":"string"}' && echo SENT
# 收（ack_requeue_false 取走即删；encoding 字段新版管理 API 强制要求）
curl -sf -u lab:lab123 -X POST http://localhost:35672/api/queues/%2F/lab-queue/get \
  -H 'content-type: application/json' -d '{"count":1,"ackmode":"ack_requeue_false","encoding":"auto"}'
```

> ⚠ `encoding` 字段是实测补的：新版 RabbitMQ 管理 API（3.13.x 学习机实测）缺它返回 `400 bad_request [{key_missing,encoding}]`，补 `"encoding":"auto"` 后 200 并正常返回 payload。

**可选 MySQL 落库演示**：把 get 回来的 payload 写入 MySQL 表（`CREATE TABLE lab_mq_demo.msg(id BIGINT AUTO_INCREMENT PRIMARY KEY, payload TEXT, created_at DATETIME DEFAULT NOW());`，用 1.2 的连接信息）——模拟「消费侧把消息持久化」，体会 M4 事件消费的雏形。

**常见失败与判读**：
- API 返回 401 → 账号错或 guest 远程登录被禁（见 L3）；
- publish 返回 `routed:false` → 队列不存在或 routing_key 打错；
- 容器 healthy 但 35672 拒绝连接 → 管理台插件仅 3-management 镜像自带，纯 `rabbitmq:3` 没有（想清楚为什么选 management 版）。

## 6. k3s 在毕设 VM 上执行的前置条件与风险（不在云端练）

> 实际安排（2026-11-03 确认）：**k3s 不占云服务器，直接在毕设 VM 上做**。具体步骤照 [k3s单节点搭建手册.md](k3s单节点搭建手册.md) 执行，本节只讲「动手前必须确认的事」。VM 现状：6 个 Java 微服务 + Milvus 三件套 + Nacos/Redis/RabbitMQ/registry 七容器常驻（见 `docker ps`）。

1. **内存预算**：k3s 空载 0.6~1.5G（DEVLOG 的 8.5G 预算是 16G 含监控全家桶的口径，VM 上**不要装监控**）。16G 总量足够，但装前必须看一眼：`free -h`，available ≥2G 再动手；不够就先分时停掉非必需容器（如 Milvus 三件套，用完 `docker start` 恢复）。
2. **端口占用检查**：`ss -lntp | grep -E ':(6443|80|443|8080)\b'`——6443 必须空闲；80/443 历史上空着（tomcat9 已 disable），若被占则 k3s 安装加 `--disable traefik`。**Traefik 与网关 8080 的关系**：Traefik 接管的是 80/443 入口，网关 8080 是应用端口，三者不冲突；真正要防的是 80/443 被其他进程先占导致 Traefik 起不来（k3s 手册阶段七第 4 行的失败对照）。
3. **与已有 Docker 共存**：k3s 自带 containerd 与 Docker 并存、镜像互不可见——应用镜像必须推 `localhost:5000` 后经 `registries.yaml` 给 k3s 用（k3s 手册阶段五）；不要为 k3s 装第二个 ingress、不要动现有 `tims-*` 容器与 compose 正本。
4. **装前必须拍 VMware 快照**（VMware 界面 → VM → Snapshot → Take Snapshot，建议命名 `aitims-pre-k3s-<日期>`），并在 DEVLOG 记一条快照名与时间。k3s 万一折腾坏（iptables/路由被改），回滚快照比清理现场可靠得多——这是 VM 环境相对云机最大的优势，必须用上。
5. **时机**：建议 **M4 推送压测结束后再做**。k3s 安装期容器反复启停会抢 CPU/内存（4 vCPU 是瓶颈，DEVLOG 已拍板负载分时错开），期间跑 200 单压测会污染 P95 时延数据；压测数据一旦作废重跑成本高。
6. 练完的清理走 k3s 手册阶段八（`k3s-uninstall.sh`，不碰 Docker 侧），异常时回滚快照。

## 8. 自检题答案（先自己想，再看）

<details>
<summary>A：为什么 Nacos 客户端必须连带 9848？</summary>

Nacos 2.x 起客户端长连接改走 gRPC，端口固定为「主端口+1000」（8848→9848）。OpenAPI 8848 只服务 HTTP 请求，注册与配置推送走 9848；容器部署只映射 8848 时服务会连不上注册中心。同理控制台 UI 在 Nacos 3 独立到了容器内 8080，所以才有第三个 8849 映射。
</details>

<details>
<summary>B：为什么 Milvus 需要 etcd 和 minio？</summary>

三者分工：etcd 存元数据（collection schema、段信息、时间戳等「目录」），minio 存对象数据（向量段文件、索引等「内容」），milvus 本体是查询/写入引擎。standalone 版三个进程只是被打包成三个容器协同，少任何一个 milvus 都无法启动——这也是 compose 里 `depends_on` 与健康检查存在的原因。内存预算 256/256/1536 来自 16G 总量台账分配，实测四容器并存余量 11.7G；4G 云机下调到 128/128/1024 的代价见实验 B ☁ 注意。
</details>

<details>
<summary>C：为什么 AMQP 5672 和管理台 15672 要分开？</summary>

它们是两套不同协议：5672 是 AMQP 0-9-1 业务协议，给应用程序（将来的 Spring 消费者）收发消息用；15672 是 HTTP，给管理台 UI 与管理 API 用。分离后可以按需收敛暴露面——例如生产只对应用网段开 5672、管理台仅内网运维可达。顺带：4369 是节点发现、25672 是节点间通信，这就是本实验把 AMQP 偏移到 25672 时看似撞名实则不冲突的原因（撞的是宿主机端口，容器内 25672 未发布）。
</details>

<details>
<summary>D：为什么 registry 必须挂数据卷？</summary>

镜像层文件全部落在容器内 `/var/lib/registry`，不挂卷则容器删除（乃至 compose down）即全部镜像蒸发——而 registry 的意义恰恰是「镜像的持久底座」：k3s 阶段 IfNotPresent 依赖它常驻镜像，删卷等于删交付物。这也是为什么生产用命名卷 `registry-data`、实验教 bind mount——形式不同，「数据必须在容器生命周期之外」的本质相同。
</details>
