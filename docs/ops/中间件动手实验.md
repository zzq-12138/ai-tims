## 实验 A：Nacos（约 1.5h）

### 目标
从零写 compose 跑起 Nacos v3 standalone，理解它强制 AUTH_TOKEN 的怪脾气，并用真实微服务向它注册。

### L1 跑起来（只给要求，不给答案——自己写 `docker-compose.yml`）

要求清单（对照复盘文档 1.2 的正本片段核对自己的写法）：
- 镜像 `nacos/nacos-server:v3.0.3`，`MODE=standalone`；
- 端口按偏移表：宿主机 18848→8848、19848→9848、18849→8080；
- **必须**给 `NACOS_AUTH_TOKEN`（Base64 ≥32 字节）与 `NACOS_AUTH_IDENTITY_KEY/VALUE`——先故意不给跑一次，看报错（这是本实验第一个考点）；
- `container_name` 改 `lab-nacos`。

**验收（自己跑，不用等人判）**：

```bash
cd /home/dev/lab/nacos && docker compose -p lab-nacos up -d
docker ps --filter name=lab-nacos            # 预期 STATUS 含 (healthy)，约 30s 后
curl -sf http://localhost:18848/nacos && echo OPENAPI_OK
```

浏览器开 `http://192.168.40.10:18849` 能看到控制台 = 过。

### L2 数据持久化

任务：给 compose 加卷（bind mount `./data:/home/nacos/data`），用控制台建一条测试配置（配置管理→新建，随便写个 `lab:test`），然后 `docker compose -p lab-nacos down && docker compose -p lab-nacos up -d`（**不带 -v**），重新登录控制台确认配置还在。

**验收**：down/up 循环后配置仍存在 + `ls ./data` 目录非空。

### L3 资源与安全

任务：加 `mem_limit: 512m`（对照正本 JVM_XMS=256m/XMX=512m 理解堆与容器限额的关系）；确认控制台当前未开鉴权（`NACOS_AUTH_ENABLE=false`），思考并写下：生产开 `true` 还需要改哪几项（写在记录表里）。

**验收**：`docker inspect lab-nacos --format '{{.HostConfig.Memory}}'` 输出 `536870912`；重启后 healthy。

### L4 接入项目（真实调用）

任务：把正在运行的 ticket-system **临时**指到实验 Nacos（不改任何配置文件，用环境变量覆盖后重启进程）：

```bash
# 在 VM 上以项目既有的启动方式重启 ticket-system，注入覆盖变量（脚本名需现场确认，
# 项目用 restart 脚本 + 环境变量注入的既有模式，如 NACOS_ADDR）：
NACOS_ADDR=localhost:18848 <按项目现有方式重启 ticket-system>
```

**验收**：等 30~60s，浏览器开实验 Nacos 控制台（18849）→ 服务列表出现 `ticket-system`，即真实注册链路打通。**验完立刻按原方式重启 ticket-system 恢复指向生产 Nacos**，并在生产控制台（8849）确认它重新注册回来。

**常见失败与判读**：
- 容器反复重启 → 日志里找 `AUTH_TOKEN`（L1 故意省略的后果，补上即可）；
- 控制台 404 → 8849 映射错方向（应是 `18849:8080`，容器内是 8080）；
- L4 服务列表空 → 服务没注册到 18848 端口（`NACOS_ADDR` 写成 `localhost:8848` 会静默注册到生产，检查 `docker logs tims-nacos --tail 20` 是否多了注册记录来区分）。

## 实验 B：Milvus 三件套（约 2.5h，最长也最值）

### 目标
亲手把 milvus + etcd + minio 三件套跑起来，理解三者分工与内存预算，并把项目的向量化链路真实打到实验实例上。

### L1 跑起来

要求清单：
- 三个服务：`milvusdb/milvus:v2.4.15`（`milvus run standalone`）、`milvusdb/minio:RELEASE.2024-05-28T17-19-04Z`（`minio server /minio_data`）、`quay.io/coreos/etcd:v3.5.14`；
- milvus 的 `ETCD_ENDPOINTS` / `MINIO_ADDRESS` 指向 compose 内的服务名（内网用服务名不用 localhost——想清楚为什么）；
- 只有 milvus 映射宿主机端口（29530→19530、29091→9091），etcd/minio 不映射；
- `mem_limit` 按正本预算 1536m/256m/256m，`depends_on` 顺序 etcd+minio → milvus；
- 若本机没有镜像，拉取用 `docker pull` 配 daocloud/1ms.run 前缀逐站试（复盘 2.4 坑 #1 的实战复现）。

**验收**：

```bash
cd /home/dev/lab/milvus && docker compose -p lab-milvus up -d
docker compose -p lab-milvus ps              # 预期三容器 Up（milvus healthy 需等 ~1-2 分钟，start_period 60s）
curl -sf http://localhost:29091/healthz && echo MILVUS_OK
```

### L2 数据持久化

任务：三个服务各加 bind mount（`./etcd-data:/etcd`、`./minio-data:/minio_data`、`./milvus-data:/var/lib/milvus`）；记下三个目录 `du -sh` 初值；`docker compose -p lab-milvus down && up -d` 后确认容器 healthy 且目录数据仍在。

**验收**：down/up 后 healthz 仍 200 + 三个数据目录非空（目录 du 不归零）。
（说明：功能性验证——真查到向量——放在 L4，这里以「数据落盘 + 服务复还」为持久化判据。）

### L3 资源与安全

任务：核对三容器内存限额 `docker stats --no-stream | grep lab-`；确认 minio 账号 `minioadmin/minioadmin` 只暴露在 compose 内网（宿主机 `curl localhost:9000` 应拒绝——因为 L1 就没映射端口，想清楚这就是安全设计）。

**验收**：`docker inspect lab-milvus --format '{{.HostConfig.Memory}}'` = `1610612736`；宿主机访问不到 minio/etcd 端口。

### L4 接入项目（真实调用：同步一条知识到实验 Milvus）

任务：临时把 ticket-knowledge 指向实验 Milvus（环境变量覆盖，`.env.example` 口径是 `MILVUS_HOST/MILVUS_PORT`；启动脚本名**需现场确认**）：

```bash
MILVUS_HOST=localhost MILVUS_PORT=29530 <按项目现有方式重启 ticket-knowledge>
```

然后在 `/kb` 前端（或 curl 调知识接口）新建一条知识并走完 发布 流程；VectorSyncService 每 10s 扫描待同步知识，观察服务日志出现同步成功记录。

**验收**：MySQL 里该知识 `synced_at` 被更新（`mysql -udev -p aitims -e "SELECT id,title,synced_at FROM kb_knowledge ORDER BY update_time DESC LIMIT 1;"`，**需现场确认**字段名）；服务日志无 sync 报错 = 向量真实写入了实验 Milvus。**验完立刻恢复指向生产 Milvus（19530）并重启服务**。

**常见失败与判读**：
- milvus 一直 unhealthy → `docker logs lab-milvus-1`：连不上 etcd/minio 多为 `ETCD_ENDPOINTS`/`MINIO_ADDRESS` 写成了宿主机端口或 localhost；
- 拉镜像 403 → daocloud 对 `milvusdb/*` 无缓存（生产踩过的坑 #23），换 1ms.run 前缀或 etcd 走 quay；
- L4 日志报连接 19530 超时 → 覆盖变量没生效（启动脚本是否真的透传了环境变量，**需现场确认**注入链路）。

## 实验 C：RabbitMQ（约 1.5h）

### 目标
跑起 3-management 版本，亲手完成一条消息从交换机到队列的真实收发，理解 M4 事件流将怎么用。

### L1 跑起来

要求清单：镜像 `rabbitmq:3-management`；`hostname` 设 `lab-rabbit`（想清楚为什么要设）；账号 `lab/lab123`（`RABBITMQ_DEFAULT_USER/PASS`）；端口 25672→5672、35672→15672。

**验收**：

```bash
cd /home/dev/lab/rabbitmq && docker compose -p lab-rabbitmq up -d
docker ps --filter name=lab-rabbitmq         # 预期 (healthy)
curl -sf -u lab:lab123 http://localhost:35672/api/overview | head -c 120   # 预期返回 JSON
```

### L2 数据持久化

任务：加 bind mount `./data:/var/lib/rabbitmq`；用管理 API 建一个队列：

```bash
curl -sf -u lab:lab123 -X PUT http://localhost:35672/api/queues/%2F/lab-queue \
  -H 'content-type: application/json' -d '{"durable":true}' && echo QUEUE_OK
```

`docker compose -p lab-rabbitmq down && up -d` 后重新执行下面验收第一条。

**验收**：`curl -sf -u lab:lab123 http://localhost:35672/api/queues/%2F/lab-queue | grep -o '"name":"lab-queue"'` 有输出（重启后队列仍在）。

### L3 资源与安全

任务：加 `mem_limit: 350m`（对照正本）；确认默认 `guest` 账号不能登录管理台（RabbitMQ 出厂禁止 guest 远程登录，这也是为什么必须显式建 lab 用户——想清楚这条安全默认值的意义）。

**验收**：`docker inspect lab-rabbitmq --format '{{.HostConfig.Memory}}'` = `367001600`；用 `guest/guest` 登 35672 被拒。

### L4 接入项目（真实调用：发一条消息再收回来）

> 说明：项目事件流当前是 stub（M4 才接 RabbitMQ，发布签名不变），所以本实验的「真实调用」用管理 API 走通一条完整消息流——这正是 M4 接入后消息走的同一条路。

任务：发一条消息到默认交换机、路由到 `lab-queue`，再取出来：

```bash
# 发
curl -sf -u lab:lab123 -X POST http://localhost:35672/api/exchanges/%2F/amq.default/publish \
  -H 'content-type: application/json' \
  -d '{"properties":{},"routing_key":"lab-queue","payload":"tims-hello","payload_encoding":"string"}' && echo SENT
# 收（requeue=false，取走即删）
curl -sf -u lab:lab123 -X POST http://localhost:35672/api/queues/%2F/lab-queue/get \
  -H 'content-type: application/json' -d '{"count":1,"ackmode":"ack_requeue_false"}'
```

**验收**：发送返回 `{"routed":true}`；取回的 JSON 里 `payload` 为 `tims-hello`。

**常见失败与判读**：
- API 返回 401 → 账号错或 guest 远程登录被禁（见 L3）；
- publish 返回 `routed:false` → 队列不存在或 routing_key 打错；
- 容器 healthy 但 35672 拒绝连接 → 管理台插件仅 3-management 镜像自带，纯 `rabbitmq:3` 没有（想清楚为什么选 management 版）。

### L2 数据持久化

任务：加 bind mount `./data:/var/lib/registry`；推一个镜像进去：

### L4 接入项目

任务：按项目 tag 规则 `localhost:5500/tims/{svc}:{ver}` 命名并推送一个镜像（当前尚无业务镜像，业务镜像的制作在学习路线阶段④；此处用任意基础镜像按规则命名即可），然后在浏览器开 `http://192.168.40.10:5500/v2/tims/redis/tags/list`。

**验收**：tags 列表返回你推的 tag = 仓库侧交付链路（命名规范）已打通。

**常见失败与判读**：
- push 报 `http: server gave HTTP response to HTTPS client` → 地址没带 `localhost:` 前缀（用 IP 就会默认走 HTTPS，对照 L3 思考题）；
- `connection refused :5500` → 容器没起或端口映射写反。

## 自检题答案（先自己想，再看）

<details>
<summary>A：为什么 Nacos 客户端必须连带 9848？</summary>

Nacos 2.x 起客户端长连接改走 gRPC，端口固定为「主端口+1000」（8848→9848）。OpenAPI 8848 只服务 HTTP 请求，注册与配置推送走 9848；容器部署只映射 8848 时服务会连不上注册中心。同理控制台 UI 在 Nacos 3 独立到了容器内 8080，所以才有第三个 8849 映射。
</details>

<details>
<summary>B：为什么 Milvus 需要 etcd 和 minio？</summary>

三者分工：etcd 存元数据（collection schema、段信息、时间戳等「目录」），minio 存对象数据（向量段文件、索引等「内容」），milvus 本体是查询/写入引擎。standalone 版三个进程只是被打包成三个容器协同，少任何一个 milvus 都无法启动——这也是 compose 里 `depends_on` 与健康检查存在的原因。内存预算 256/256/1536 来自 16G 总量台账分配，实测四容器并存余量 11.7G。
</details>

<details>
<summary>C：为什么 AMQP 5672 和管理台 15672 要分开？</summary>

它们是两套不同协议：5672 是 AMQP 0-9-1 业务协议，给应用程序（将来的 Spring 消费者）收发消息用；15672 是 HTTP，给管理台 UI 与管理 API 用。分离后可以按需收敛暴露面——例如生产只对应用网段开 5672、管理台仅内网运维可达。顺带：4369 是节点发现、25672 是节点间通信，这就是本实验把 AMQP 偏移到 25672 时看似撞名实则不冲突的原因（撞的是宿主机端口，容器内 25672 未发布）。
</details>

<details>
<summary>D：为什么 registry 必须挂数据卷？</summary>

镜像层文件全部落在容器内 `/var/lib/registry`，不挂卷则容器删除（乃至 compose down）即全部镜像蒸发——而 registry 的意义恰恰是「镜像的持久底座」：k3s 阶段 IfNotPresent 依赖它常驻镜像，删卷等于删交付物。这也是为什么生产用命名卷 `registry-data`、实验教 bind mount——形式不同，「数据必须在容器生命周期之外」的本质相同。
</details>
