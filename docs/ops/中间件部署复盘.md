## 1. Nacos v3.0.3（注册中心）

### 1.1 它承担什么、为什么选它

- **承担**：六微服务（gateway/system/order/knowledge/ai/push）的服务注册与发现；网关用 `lb://` 前缀路由到 Nacos 服务名（任务书钉死口径）。
- **为什么选**：技术栈锁死 Spring Cloud 2025.0.0 + Spring Cloud Alibaba 2025.0.0.0（nacos-client 3.0.3，DEVLOG 2026-11-02 实证 GA），Nacos 是该生态默认注册中心；M1 起六服务注册后网关路由全通，服务列表稳定 6 条。
- **部署形态**：standalone 单机 + 内嵌 Derby 持久化。毕设规模不需要 MySQL 存储模式（留作优化项，见 compose 注释）。

### 1.2 实际部署

目录：编排位于仓库 `docker/docker-compose.yml`（正本），数据落命名卷 `nacos-data`。compose 片段（摘自正本）：

```yaml
services:
  nacos:
    image: nacos/nacos-server:v3.0.3
    container_name: tims-nacos
    environment:
      - MODE=standalone
      - NACOS_AUTH_ENABLE=false        # Nacos 3 启动脚本强制要求 AUTH_TOKEN（Base64, >=32 字节），即使鉴权关闭
      - NACOS_AUTH_TOKEN=ZGV2LXRpbXMtZGV2LXRpbXMtZGV2LXRpbXMtZGV2LTEyMzQ=   # 开发期固定示例值，生产必须替换：openssl rand -base64 32
      - NACOS_AUTH_IDENTITY_KEY=serverIdentity
      - NACOS_AUTH_IDENTITY_VALUE=tims-dev
      - JVM_XMS=256m
      - JVM_XMX=512m
    ports:
      - "8848:8848"                    # HTTP OpenAPI / 控制台后端
      - "9848:9848"                    # gRPC（客户端端口 = 8848 + 1000，必须一并映射）
      - "8849:8080"                    # Nacos 3 控制台 UI（容器内 8080，避开宿主机网关 8080）
    volumes:
      - nacos-data:/home/nacos/data
    healthcheck:
      test: ["CMD-SHELL", "curl -sf http://localhost:8848/nacos > /dev/null || exit 1"]
      interval: 10s
      timeout: 5s
      retries: 12
      start_period: 30s
    restart: unless-stopped
```

关键参数理解：

| 参数 | 为什么这么写 |
|---|---|
| `9848` 必须映射 | Nacos 2/3 客户端走 gRPC，端口固定为主端口 +1000，只映射 8848 服务会连不上（DEVLOG 未记录此坑为独立条目，属 compose 注释口径，**需现场确认理解**） |
| `8849:8080` | Nacos 3 控制台 UI 在容器内 8080，与网关 8080 冲突，故映射宿主机 8849 |
| `NACOS_AUTH_TOKEN` | Nacos 3 启动脚本强制校验（Base64 ≥32 字节），即使 `AUTH_ENABLE=false` 也必须给——真实踩坑，见 1.4 |
| Derby 而非 MySQL | 单机演示规模够用，少一个依赖；MySQL 存储留作优化项 |

## 2. Milvus standalone（向量检索三件套：milvus + etcd + minio）

### 2.1 它承担什么、为什么选它

- **承担**：知识库向量检索（M3 硬指标 HYBRID Hit@3 ≥80% 的向量路）。collection `kb_knowledge_vec`：`knowledge_id` 主键 + `tenant_id`/`device_type` 标量字段（多租户检索 expr 前置过滤，先过滤后 TopK）+ HNSW / COSINE 索引；向量来自智谱 embedding-3（1024 维）。
- **为什么选 standalone**：任务书钉死 Milvus standalone；单机毕设规模（50 条种子知识起步）不需要集群版。etcd 存元数据、minio 存对象（段文件）、milvus 本体跑查询——三件套缺一不可。
- **为什么 etcd 不用 milvusdb 镜像**：见 2.4 踩坑 #1。

### 2.2 实际部署

compose 片段（摘自正本，内存严格按台账预算）：

```yaml
  etcd:                                              # 元数据
    image: quay.io/coreos/etcd:v3.5.14               # VM 镜像源对 milvusdb/etcd 无缓存，用 quay 官方（Milvus 2.4 兼容 v3.5.14）
    container_name: tims-etcd
    environment:
      - ETCD_AUTO_COMPACTION_MODE=revision
      - ETCD_AUTO_COMPACTION_RETENTION=1000
      - ETCD_QUOTA_BACKEND_BYTES=4294967296
    command: etcd -advertise-client-urls=http://etcd:2379 -listen-client-urls http://0.0.0.0:2379 --data-dir /etcd
    mem_limit: 256m
    volumes:
      - etcd-data:/etcd
    restart: unless-stopped

  minio:                                             # 对象存储
    image: milvusdb/minio:RELEASE.2024-05-28T17-19-04Z
    container_name: tims-minio
    environment:
      MINIO_ACCESS_KEY: minioadmin                   # 开发期固定；生产注入环境变量
      MINIO_SECRET_KEY: minioadmin
    command: minio server /minio_data
    mem_limit: 256m
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:9000/minio/health/live"]
    volumes:
      - minio-data:/minio_data
    restart: unless-stopped

  milvus:                                            # 本体
    image: milvusdb/milvus:v2.4.15
    container_name: tims-milvus
    command: ["milvus", "run", "standalone"]
    environment:
      ETCD_ENDPOINTS: etcd:2379
      MINIO_ADDRESS: minio:9000
    mem_limit: 1536m
    ports:
      - "19530:19530"                                # gRPC（Java SDK）
      - "9091:9091"                                  # 健康检查 / metrics
    volumes:
      - milvus-data:/var/lib/milvus
    depends_on:
      - etcd
      - minio
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:9091/healthz"]
      interval: 30s
      timeout: 10s
      retries: 10
      start_period: 60s                              # Milvus 启动慢，给足 60s
    restart: unless-stopped
```

注意：**etcd 与 minio 的端口没有映射到宿主机**（`docker ps` 里是 `2379-2380/tcp`、`9000/tcp` 不带映射），只在 compose 内部网络互通——少暴露即少攻击面，这也是三个容器端口规划里值得学的点。

### 2.3 验证方法

```bash

# 2) Milvus 健康接口（业务级判据）

# 3) 端到端判据（真正证明可用，M3 已实测）：
```

### 2.4 真实踩坑（逐条对应 DEVLOG）

| # | 现象 | 根因 | 解决 | DEVLOG 出处 |
|---|---|---|---|---|
| 1 | 拉镜像 403：daocloud 加速源对 `milvusdb/*` 全部拒绝 | 加速站只缓存部分命名空间，milvusdb/* 无缓存且返回 403 | 显式前缀逐站试：`1ms.run` 有 `milvusdb/milvus` 与 `milvusdb/minio`，etcd 改走 quay.io 官方；**tag 取现网实际可拉的版本，而非硬编码官方 compose 文档版本** | 2026-11-03 批 B「新坑 #23」 |
| 2 | SDK 查询抛 `The key name is not found` | milvus-sdk-java 2.4.4 的 `SearchResultsWrapper.getRowRecords` 依赖 outFields 名称匹配，属已知缺陷 | 改用 `getIDScore()` 解析，不取标量字段（详情统一回查 MySQL） | 2026-11-03 批 C「新坑 #24」 |
| 3 | Milvus 宕机后应用请求长时间阻塞无返回 | SDK 缓存的 gRPC channel 默认无 RPC deadline，对端宕机会无限等 | `ConnectParam.withRpcDeadline(10s)`（签名经 javap 现场核对）+ `isAvailable()` 30s 失败退避 | 2026-11-03 批 C「新坑 #25」 |
| 4 | 初版 kb 代码用 `@Data` 编译失败 | 项目口径不用 Lombok（order 服务全手写 getter） | 删注解手写 getter；新模块进项目前先看既有代码风格 | 2026-11-03 批 B |

内存结论：四容器并存 healthy 时 VM 内存余量 11.7G（16G 规格），证明 256/256/1536 预算合理（DEVLOG 2026-11-03 批 B）。

## 3. RabbitMQ 3-management（事件总线）

### 3.1 它承担什么、为什么选它

- **承担**：工单领域事件的异步分发（M2 的 `ticket.closed` 等事件，当前实现为 EventPublisher stub：日志 + Redis LPUSH `tims:event:stream`；M4 换 RabbitMQ，**发布签名不变**）。后续 AI 慢通道/推送快通道的事件流、异步任务都走它。
- **为什么选 3-management**：带管理台（15672），调试交换机/队列/绑定可视化，毕设排障效率高；实际版本 3.13.7（DEVLOG 记录）。
- **任务书口径**：事件总线 `ai-tims.event`（见 `.env.example` 注释）。

### 3.2 实际部署

compose 片段（摘自正本）：

```yaml
  rabbitmq:
    image: rabbitmq:3-management
    container_name: tims-rabbitmq
    hostname: tims-rabbit                    # 固定 hostname，节点名稳定，数据卷重建才不会出现孤儿节点数据
    environment:
      - RABBITMQ_DEFAULT_USER=tims           # 开发期固定；生产注入环境变量
      - RABBITMQ_DEFAULT_PASS=tims123
    mem_limit: 350m
    ports:
      - "5672:5672"                          # AMQP
      - "15672:15672"                        # 管理台 UI
    volumes:
      - rabbitmq-data:/var/lib/rabbitmq      # 数据卷持久化，避免重启丢队列
    healthcheck:
      test: ["CMD", "rabbitmq-diagnostics", "-q", "ping"]
      interval: 15s
      timeout: 10s
      retries: 10
      start_period: 30s
    restart: unless-stopped
```

### 3.3 验证方法

```bash
# 1) 容器健康
docker ps --filter name=tims-rabbitmq      # 预期 (healthy)

# 2) 节点真活着（不是端口开着就算）
docker exec tims-rabbitmq rabbitmqctl status | head -5    # 预期看到 RabbitMQ version 3.13.7

# 3) 管理台 API 可用
curl -sf -u tims:tims123 http://localhost:15672/api/overview | head -c 200
# 预期返回 JSON（含 rabbitmq 版本、rates 等）

# 4) 浏览器打开 http://192.168.40.10:15672，用 tims/tims123 登录能进管理台
```

**判据**：healthy + `rabbitmqctl status` 正常 + 管理 API 返回 200（DEVLOG 2026-11-03 P0 收尾验证记录）。

### 3.4 真实踩坑

DEVLOG 原文（2026-11-03 P0 收尾）：**「无新增问题；两个官方镜像（rabbitmq、registry）直连可拉，未触发镜像源降级策略」**。即 Docker Hub 直连加速源对 `rabbitmq`、`registry` 这类官方顶级镜像有缓存，没有像 milvusdb/* 那样 403。这一条本身就是有用经验：**403 与否取决于命名空间是否被加速站缓存，不是所有镜像都会踩**。

（部署当日曾遇 ci.yml 因 PAT 缺 workflow 权限推送被拒，属 Git 权限问题非 RabbitMQ 问题，复盘归档在 DEVLOG「阻塞」条目。）

## 4. registry:2（本地镜像仓库）

### 4.1 它承担什么、为什么选它

- **承担**：本地 Docker 镜像仓库，是 k3s 阶段 `imagePullPolicy: IfNotPresent` 方案的配套（应用镜像先推到这里，k3s 单节点直接本地拉）。
- **为什么选它**：DEVLOG 2026-11-02 拍板口径「不买云、不用 TCR，镜像方案 = 公司仓库 / 本地 registry」；`registry:2` 是官方最小实现，128M 内存就能跑。论文口径「单节点 k3s 验证 + 企业集群 namespace 级部署」中，本地 registry 就是单节点侧的镜像来源。
- **tag 规则**：`localhost:5000/tims/{svc}:{ver}`。
- **为什么不用配 TLS**：`localhost` / `127.0.0.1` 地址在 Docker 生态默认按 insecure（HTTP）通道处理，无需证书（DEVLOG P0 收尾「研究与选型」原文；k3s containerd 侧行为见文档二第 6 节，**需现场确认**）。

### 4.2 实际部署

compose 片段（摘自正本）：

```yaml
  registry:
    image: registry:2
    container_name: tims-registry
    mem_limit: 128m
    ports:
      - "5000:5000"
    volumes:
      - registry-data:/var/lib/registry       # 持久化，删容器不丢镜像
    healthcheck:
      test: ["CMD-SHELL", "wget -qO- http://localhost:5000/v2/ || exit 1"]
      interval: 15s
      timeout: 5s
      retries: 6
    restart: unless-stopped
```

### 4.3 验证方法（DEVLOG 原样复刻的「真实推拉」流程）

```bash
# 1) 服务可用
curl -sf http://localhost:5000/v2/ && echo OK            # 预期 {} 或 200
curl -sf http://localhost:5000/v2/_catalog               # 预期 {"repositories":["tims/redis",...]}

# 2) 真实推拉验证（核心判据，照抄 DEVLOG 记录）
docker pull redis:7-alpine
docker tag redis:7-alpine localhost:5000/tims/redis:7-alpine
docker push localhost:5000/tims/redis:7-alpine
docker rmi localhost:5000/tims/redis:7-alpine            # 删本地，模拟"另一台机器"
docker pull localhost:5000/tims/redis:7-alpine           # 能拉回即通

# 3) digest 一致性（DEVLOG 实测值 1cf73a2f）
docker push localhost:5000/tims/redis:7-alpine 2>&1 | grep -o 'digest: sha256:[0-9a-f]*'
docker images --digests | grep tims/redis                # 拉回 digest 与推送 digest 应一致
```

**判据**：`/v2/` 200 + 推删拉闭环成功 + 前后 digest 一致 + `_catalog` 可见。只 `docker ps` 看 Up 不算验证。

### 4.4 真实踩坑

同 RabbitMQ：官方镜像直连可拉，无新增问题（DEVLOG 原文）。关联经验两条：

- Docker 加速源配置在 `/etc/docker/daemon.json`（三加速源 + 日志限制 50m×3）；改完必须 `systemctl restart docker` 才生效（DEVLOG 坑 #8：daemon.json 写入早于服务启动不会重读）。
- 遗留优化（DEVLOG 未来优化项）：registry 尚未配 garbage-collect 定时清理，长期推镜像会膨胀——练习环境无所谓，生产 registry 后续要补（**待补充**：清理策略未实施）。

### 4.5 「自己重做一遍」练习路径

```bash
mkdir -p ~/lab/registry && cd ~/lab/registry
# 拷正本 registry 段为 docker-compose.yml，改：
#   a) container_name: lab-registry
#   b) 端口偏移：5500:5000（5000 是生产仓库端口）
#   c) 卷改 bind mount：./data:/var/lib/registry

docker compose -p lab-registry up -d
curl -sf http://localhost:5500/v2/ && echo OK

# 完整走一遍 4.3 的推拉闭环（把 localhost:5000 换成 localhost:5500）
# 进阶：curl http://localhost:5500/v2/tims/redis/tags/list 看镜像 tag 列表

docker compose -p lab-registry down -v
rm -rf ~/lab/registry
```

**不能碰**：`tims-registry` 容器、端口 5000、卷 `registry-data`（里面是已推入的全部镜像层；k3s 阶段 IfNotPresent 靠它）。另注意 5000 也是常见应用端口，若练习时被占先 `ss -lntp | grep 5000` 确认是谁。

## 5. 通用：隔离练习的总规则与红线

### 5.1 四个一律

1. **一律新目录**：练习 compose 放 `~/lab/<组件>/`，绝不在 `/home/dev/ai-tims/docker/` 里改动或新建文件（那是正本，改动影响所有服务）。
2. **一律 -p 项目名**：`docker compose -p lab-<组件> up -d`。项目名决定 compose 创建的网络与卷前缀，是隔离的第一道墙。
3. **一律改 container_name**：正本里都写死了 `container_name`，练习副本不改名会直接冲突起不来。
4. **一律 bind mount 代替命名卷**：练习数据落 `./data` 这类子目录，`down -v` 后 `rm -rf` 目录就干净；命名卷容易被忘掉变成垃圾。

### 5.2 端口偏移对照表（练习用）

| 组件 | 生产端口 | 练习偏移 |
|---|---|---|
| Nacos | 8848 / 9848 / 8849 | 18848 / 19848 / 18849 |
| Milvus | 19530 / 9091 | 29530 / 29091 |
| RabbitMQ | 5672 / 15672 | 25672 / 35672 |
| Registry | 5000 | 5500 |

**绝对不能占用的端口**：8080（网关）、3306（MySQL）、6379（Redis）、以及上表「生产端口」列的全部端口；k3s 搭建后追加 6443 / 80 / 443 / 10250（见文档二）。

**绝对不能动的卷与容器**：所有 `tims-*` 前缀容器；所有正本命名卷（`nacos-data/redis-data/etcd-data/minio-data/milvus-data/rabbitmq-data/registry-data`，实际卷名带项目前缀，`docker volume ls` 现场核对）。**尤其禁止在 `/home/dev/ai-tims/docker` 目录执行 `docker compose down -v`**——会把全部中间件数据卷一起删除。

### 5.3 出问题先看什么

```bash
docker compose -p lab-xxx ps              # 容器状态
docker logs --tail 50 lab-xxx-1           # 起不来先看日志
docker compose -p lab-xxx down -v         # 练习环境随时可推倒重来，这是它存在的意义
```

练习环境怎么折腾都不会伤到生产——前提是第 5.1 节的四条真的照做了。
