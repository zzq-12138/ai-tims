> **提示**：以下为历史记录，最新状态见 `public/04-进度现状.md` 与 `public/06-待办与优先级.md`。

这份文件是"在公司机器上做过什么"的台账，也是照着做的操作手册。
原则很简单：**先登记、再执行、做完补结果**。出了事能照着记录倒查。

## 一、使用规则

1. **先登记再执行**：动公司机器的命令，先在下表加一行（时间、机器、账号、要执行的命令、目的），执行完把结果补进同一行。不要先做后补。
2. **只读脚本用普通账号，不用 root**：`server_check.sh`、`cluster_check.sh` 都是只读，普通账号跑即可。只有确实需要 root 的写操作才用 root，并在"备注"里写明原因。
3. **传脚本用单引号 heredoc**：写成 `<<'EOF'`（带引号），这样脚本里的 `$`、反引号不会被本地 shell 提前展开；写完必须 `md5sum` 核对，和这里登记的值一致才算传对。
4. **写操作、部署必须单列**：凡是会改配置、写数据、起停服务、部署镜像的操作，单独占一行，必须在"备注"里写清**回滚方式**（例如恢复哪个备份文件、回滚到哪个镜像 tag、`kubectl rollout undo` 哪次发布）。没写回滚方式的操作不要执行。
5. **机器标识**：用 IP 最后两段区分，例如 `19.64`。同一台机器多次操作也每次都记，不要合并。
6. **时间**：用执行时那台机器的时间，精确到分钟即可。
7. **口令一律不入库**：本文档入库（Git）后对协作者可见，凡口令/令牌/密钥只记键名与用途，值统一写「见现场配置」；真实值以集群 `tims-app-secret` 与执行机本机速查文件为准，不写进任何提交内容。

## 三、只读体检脚本：分步执行方法

两个脚本都已放在仓库 `docs/ops/` 下：

- `server_check.sh`：单机体检（CPU / 内存 / 磁盘 / 负载 / 容器 / 权限 / 系统）
- `cluster_check.sh`：K8s 集群余量体检（节点余量 / 不可调度原因 / 命名空间申请量 / 能放几套）

**不要一次性把两个脚本粘进终端**，按下面 4 步走，一步一确认。

### 第 0 步：准备目录（只读，随便跑）

```bash
mkdir -p ~/tims-check && cd ~/tims-check && pwd
```

预期输出：`/home/你的用户名/tims-check`（最后一行是路径，说明目录建好了）。

### 方案 A：从已有服务器拷过来（推荐，最不容易错）

如果公司机器和你的开发机之间网络可达：

```bash
# 在开发机上执行（把 USER 和 IP 换成公司机器）
scp ~/tims-check/server_check.sh ~/tims-check/cluster_check.sh USER@公司机器IP:~/tims-check/
```

预期输出：两行进度，末尾 `100%`，没有报错。

### 方案 B：手动粘贴（网络不通时用）

在 `~/tims-check` 目录下，先执行下面这行"开工"命令：

```bash
cat > server_check.sh <<'EOF'
```

**回车后终端会等你继续输入**（不会回到提示符）。这时把仓库里 `docs/ops/server_check.sh` 的全部内容粘进去，然后**另起一行**输入：

```bash
EOF
```

回车后回到提示符，文件就写好了。`cluster_check.sh` 同样操作，把内容换成 `docs/ops/cluster_check.sh`。

**注意**：开始那行必须是 `<<'EOF'`（带单引号），结尾的 `EOF` 必须顶格、前后不能有空格。

### 第 1 步：核对文件（这一步不能省）

```bash
md5sum server_check.sh cluster_check.sh
```

预期输出（两个值必须一字不差）：

```
ffeeabe47f6f0e1d232ea0e800e626b9  server_check.sh
c1a2cc36ad01c72b89807c1b7a7cc5cd  cluster_check.sh
```

对不上就是粘贴时漏行/多了空行，**不要执行**，删掉重来（`rm server_check.sh`）。

### 第 2 步：跑单机体检，并把输出存成日志

```bash
bash server_check.sh 2>&1 | tee server_check_$(hostname)_$(date +%F).log
```

预期：约 42 行，最后 3 行是结论区，形如

```
== 结论 ==
总体: 勉强可用
扣分项: ...
```

日志文件名示例：`server_check_web01_2026-11-14.log`。

### 第 3 步：跑集群体检（只有 K8s 节点才需要）

先确认有没有只读权限：

```bash
kubectl auth can-i list nodes
```

- 返回 `yes` → 继续往下；
- 返回 `no` → 把这一行结果记进台账，找管理员开只读权限（nodes、pods 的 get/list），脚本会给出同样的提示，不会报错。

```bash
bash cluster_check.sh 2>&1 | tee cluster_check_$(hostname)_$(date +%F).log
```

预期：约 26 行（空集群也正常），关键看最后一段：

```
【4】结论（基准：一套 = 8 核 / 16 GiB / 磁盘可用 100G）
  可调度节点合计剩余: ...
  按 Requests 估算: 约 N 套 ...
  按实际用量估算: 约 N 套 ...
```

### 第 4 步：把结果发回来

```bash
cat server_check_*.log cluster_check_*.log
```

整段复制发我即可（不要截图，文字方便我算）。多台机器就是每台重复第 0～4 步，日志文件名带 hostname，不会互相覆盖。

## 四、多台机器怎么排优先级（读结果时的顺序）

1. 先看【2】不可调度节点：被 cordon 或带 `NoSchedule` 污点的节点，余量再大也用不上，不能算。
2. 再看 `Req` 百分比：这是调度器眼里的占用；`实际` 那行是真实用量。两者差很远，说明"申请得多、其实很闲"，可以找管理员要回一些 requests。
3. 磁盘看 `server_check` 的 `/var/lib/docker` 那一行，要 ≥100G 可用；`cluster_check` 读不到节点磁盘，必须靠单机脚本补。
4. 结论以 Requests 为准（排不进去就是排不进去），实际用量只作参考。

## 六、2026-11-14 公司集群余量实测结论（master1，只读）

> 数据来源：2026-11-14 14:36 在 master1 执行 `bash cluster_check.sh`（只读），对应台账中的那一行。

### 6.1 可调度节点与余量

| 节点 | 规格 | 按 Requests 剩余 | 状态 |
|---|---|---|---|
| rn-8300 | 32 核 / 125.7G | 4.5 核 / 37.6G | Ready，可调度 |
| worker1 | 8 核 / 31.1G | 2.1 核 / 9.0G | Ready，可调度 |
| worker2 | 8 核 / 31.1G | 2.0 核 / 10.9G | Ready，可调度 |
| **合计** | | **约 8.6 核 / 57G** | 仅这 3 台可调度 |

不可调度的节点：

- master1 / master2 / master3 均带 `node-role.kubernetes.io/master:NoSchedule` 污点；
- `ubuntu-standard-pc-q35-ich9-2009` 已 cordon，并附加 `node.kubernetes.io/unschedulable:NoSchedule`。

### 6.2 结论

1. **总量放得下，单 Pod 放不下**：一套按 8 核 / 16GiB 申请，三台合计 8.6 核 / 57G，总量够；但 Kubernetes 调度以单节点为单位，单节点最大剩余只有 **4.5 核（rn-8300）**。
2. **不要按"整机 8 核"申请**：应改用 namespace 配额 `requests.cpu=8`、`requests.memory=16Gi`，把服务拆成多个小规格 Pod，由调度器分散到三台节点。若单个 Pod 写死 8 核，会一直 Pending。
3. **最大占用方**：`mlops-test` 有 30 个 Pod、约 **83G 内存请求**，是全集群最大占用者。建议向管理员确认它是否为可收缩的闲置测试环境；若可回收，本次部署余量会明显宽松。
4. **磁盘余量尚未测**：`cluster_check.sh` 只读 K8s API，读不到节点磁盘。仍需在 rn-8300 / worker1 / worker2 上各跑一次 `server_check.sh`，重点看 `/var/lib/docker` 是否 ≥100G 可用，再把结果补进台账。

## 七、公司集群操作边界（2026-11-14 确认）

> 适用范围：公司 kubeadm 集群（master1/2/3 + rn-8300/worker1/worker2 + 已 cordon 的 `ubuntu-standard-pc-q35-ich9-2009`）。本节只补充「能做 / 不能做」，不改变前面各节已登记的操作方法与结论。

### 7.1 我们只做这四类动作

1. 在**自己新建的 namespace** 内创建资源（Deployment / StatefulSet / Service / ConfigMap / Secret / PVC / Ingress 等）。
2. **只读**查询集群信息（`kubectl get` / `describe` / `top`、日志、事件）。
3. 向管理员**申请配额**（namespace 的 requests / limits、存储、镜像仓库权限）。
4. 给**自己的资源打标签**（用于识别归属与后续清理）。

### 7.2 明确禁止

- 修改他人的任何对象：Deployment / StatefulSet / ConfigMap / Service / PVC / Secret / Ingress 等；
- 修改 master 节点的污点或可调度状态（taint / uncordon）；
- 创建集群级 CRD 或 ClusterRole / ClusterRoleBinding；
- 删除他人的镜像与 PV。

### 7.3 他人命名空间仅作背景，不干预
