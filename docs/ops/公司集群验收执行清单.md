## 1. `kubectl apply -k` 渲染与 server 侧校验

```bash
kubectl kustomize deploy/k8s/overlays/company | kubectl apply --dry-run=server -f -
```

- **预期**：输出 41 个资源 `configured (server dry run)`，无 `no matches for kind`、无 `strict decoding error`。
- **失败判读**：
  - `no matches for kind`：公司 kubectl 内置 kustomize 版本不兼容，改用独立 `kustomize build` 再 `kubectl apply -f -`。
  - `unknown field`：说明公司侧开了 `--validate=strict`，对照本文末尾「禁止字段」清单。
  - `forbidden`：当前账号无 namespace 写权限，找管理员要 `edit` 角色。

## 2. IngressClass

```bash
kubectl get ingressclass
kubectl -n ai-tims get ingress tims-ingress -o jsonpath='{.spec.ingressClassName}{"\n"}'
```

- **预期**：存在名为 `nginx` 的 IngressClass，且 `DEFAULT` 列可能为 `<none>`；ingress 输出的 `ingressClassName` 为 `nginx`。
- **失败判读**：
  - 列表里叫 `nginx-ingress` / `traefik` / 其他：改 `deploy/k8s/base/ingress.yaml` 的 `ingressClassName` 后重新 apply。
  - 列表为空：集群未装 Ingress Controller，Ingress 永远不会分配 ADDRESS，需管理员安装或改用 NodePort。

## 3. Ingress 注解是否被实际支持

```bash
kubectl -n ai-tims describe ingress tims-ingress | sed -n '/Annotations/,/Events/p'
# 现场实测：上传一个 20MB 附件
curl -k -H "Authorization: <token>" -F "file=@20mb.bin" https://tims.company.local/api/order/attachment
```

- **预期**：注解原样存在；20MB 上传返回 2xx（`proxy-body-size: 25m` 生效）。
- **失败判读**：
  - 返回 `413 Request Entity Too Large`：Controller 不认 `proxy-body-size`（部分版本用 ConfigMap 全局配置），需在 Controller ConfigMap 调大。
  - 大文件/长连接 60s 断开：`proxy-read-timeout` 未生效，同样改 Controller 配置。

## 4. 默认 StorageClass 与 PVC

```bash
kubectl get sc
kubectl -n ai-tims get pvc
kubectl -n ai-tims get pv | grep ai-tims
```

- **预期**：存在一个 `(default)` 标记的 StorageClass；7 个 PVC 全部 `Bound`（4 个静态 + rabbitmq/redis/nacos 各 1 个模板生成）。
- **失败判读**：
  - 无默认 SC 且 PVC `Pending`：给 `deploy/k8s/base` 下 PVC/volumeClaimTemplates 补 `storageClassName`。
  - `ProvisioningFailed ... quota`：公司存储配额不足，找管理员扩容。
  - `pod has unbound immediate PersistentVolumeClaims`：StatefulSet 会卡在 Pending，先解决 PVC。

## 6. PSA / PSP 与安全上下文

```bash
kubectl get psp -A
kubectl get ns ai-tims --show-labels
kubectl -n ai-tims get pod -o jsonpath='{range .items[*]}{.metadata.name}{" "}{.spec.securityContext.runAsUser}{"\n"}{end}'
```

- **预期**：1.24 下 PSP 可能仍存在但已弃用；namespace 无 `restricted` 强约束；业务 Pod `runAsUser=10001`，中间件按其镜像默认用户运行。
- **失败判读**：
  - namespace 标了 `pod-security.kubernetes.io/enforce=restricted`：业务 Pod 已满足，但 MySQL/Redis/RabbitMQ 可能因 `allowPrivilegeEscalation`/capabilities 被拒，需管理员放宽到 `baseline`。
  - `Error: container has runAsNonRoot and image has non-numeric user`：中间件被强制 `runAsNonRoot`，同样需放宽。

## 7. 镜像仓库可达与凭据

## 9. containerd 1.6.24 对镜像 tar 的兼容

```bash
# 在公司任意节点
sudo ctr -n k8s.io images import /path/tims-images-1.0.0.tar
sudo ctr -n k8s.io images ls | grep ai-tims | wc -l
```

- **预期**：11 个镜像可导入、可列出（6 个后端 + 1 个前端 `ai-tims-front` + 4 个中间件 rabbitmq/milvus/etcd/minio；另有 `MANIFEST.txt`、`MANIFEST.md5`、`load-all.sh` 三个文本文件，合计 14 个文件。镜像数曾误记为 13，已更正）。

## 13. 前端改动：构建通过 ≠ 部署可见（现场检查项）

```bash
# 13.1 确认线上页面用的是本次产物（对比入口 HTML 引用的 hash 与构建输出）
curl -s https://tims.company.local/ | grep -o 'assets/index-[^"]*\.js'

# 13.2 确认关键文案/字段确实进了线上 JS（以链式降级告警为例）
curl -s https://tims.company.local/assets/$(curl -s https://tims.company.local/ | grep -o 'assets/Knowledge-[^"]*\.js' | head -1 | cut -d/ -f2) \
  | grep -c 'chainDegraded'
```

- **现场检查项**：**本地 `npm run build` 通过 ≠ 部署可见。每次前端改动必须同步 VM 源码或 `dist`，并在页面上实际验一次**；只验后端接口 JSON、只看到本地 `dist` 里有字符串，都不算通过。
- **预期**：页面入口引用的 `index-*.js` hash 与构建产物一致；线上 `Knowledge-*.js` 中 `chainDegraded` 命中数 ≥ 1；改动对应的页面元素在浏览器里可见。
- **失败判读**：
  - hash 不一致或 grep 为 0：线上仍是旧产物（源码同步了但没重新构建/没替换 `dist`），重新构建并部署。
  - 构建机 `node -v` 找不到：本 VM 的 node 在 `/home/dev/node/bin`，需 `export PATH=/home/dev/node/bin:$PATH`，不要据此判定"无法构建"。
  - 页面元素仍不出现：用浏览器开发者工具看接口返回里是否有目标字段，再对照前端字段名（例如 `chainDegraded` 与后端 `chainDegraded` 是否同名）。
- **本次实测记录（2026-11-10）**：VM 源码已含告警代码，但 `dist` 是 11-07 旧产物，页面上看不到告警；在 VM 重新构建并部署到 `http://192.168.40.10:18080` 后，用 `admin` 打开 `ai_extracted#2118000999012345678`（`chain_trace.degraded=true`）详情，页面显示黄色告警"链式抽取发生降级"与"降级原因：step2:no_json…"。
