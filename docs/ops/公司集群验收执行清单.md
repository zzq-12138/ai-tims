## 1. `kubectl apply -k` 渲染与 server 侧校验

```bash
kubectl kustomize deploy/k8s/overlays/company | kubectl apply --dry-run=server -f -
```

- **预期**：输出 41 个资源 `configured (server dry run)`，无 `no matches for kind`、无 `strict decoding error`。
- **失败判读**：
  - `no matches for kind`：公司 kubectl 内置 kustomize 版本不兼容，改用独立 `kustomize build` 再 `kubectl apply -f -`。
  - `unknown field`：说明公司侧开了 `--validate=strict`，对照本文末尾「禁止字段」清单。
  - `forbidden`：当前账号无 namespace 写权限，找管理员要 `edit` 角色。

## 2. IngressClass

```bash
kubectl get ingressclass
kubectl -n ai-tims get ingress tims-ingress -o jsonpath='{.spec.ingressClassName}{"\n"}'
```

- **预期**：存在名为 `nginx` 的 IngressClass，且 `DEFAULT` 列可能为 `<none>`；ingress 输出的 `ingressClassName` 为 `nginx`。
- **失败判读**：
  - 列表里叫 `nginx-ingress` / `traefik` / 其他：改 `deploy/k8s/base/ingress.yaml` 的 `ingressClassName` 后重新 apply。
  - 列表为空：集群未装 Ingress Controller，Ingress 永远不会分配 ADDRESS，需管理员安装或改用 NodePort。

## 3. Ingress 注解是否被实际支持

```bash
kubectl -n ai-tims describe ingress tims-ingress | sed -n '/Annotations/,/Events/p'
# 现场实测：上传一个 20MB 附件
curl -k -H "Authorization: <token>" -F "file=@20mb.bin" https://tims.company.local/api/order/attachment
```

- **预期**：注解原样存在；20MB 上传返回 2xx（`proxy-body-size: 25m` 生效）。
- **失败判读**：
  - 返回 `413 Request Entity Too Large`：Controller 不认 `proxy-body-size`（部分版本用 ConfigMap 全局配置），需在 Controller ConfigMap 调大。
  - 大文件/长连接 60s 断开：`proxy-read-timeout` 未生效，同样改 Controller 配置。

## 4. 默认 StorageClass 与 PVC

```bash
kubectl get sc
kubectl -n ai-tims get pvc
kubectl -n ai-tims get pv | grep ai-tims
```

- **预期**：存在一个 `(default)` 标记的 StorageClass；7 个 PVC 全部 `Bound`（4 个静态 + rabbitmq/redis/nacos 各 1 个模板生成）。
- **失败判读**：
  - 无默认 SC 且 PVC `Pending`：给 `deploy/k8s/base` 下 PVC/volumeClaimTemplates 补 `storageClassName`。
  - `ProvisioningFailed ... quota`：公司存储配额不足，找管理员扩容。
  - `pod has unbound immediate PersistentVolumeClaims`：StatefulSet 会卡在 Pending，先解决 PVC。

## 5. 网络策略是否默认 deny-all

```bash
kubectl get networkpolicy -A
kubectl -n ai-tims get networkpolicy
```

- **预期**：`ai-tims` 内无 NetworkPolicy（本交付不含），或公司全局策略已放行同 namespace 东西向流量。
- **失败判读**：若存在 deny-all，六服务互调会超时。按 `deploy/k8s/README` 的端口表补放行：8080→8101/8102/8103/8104/8105，以及各服务→3306/6379/5672/8848/19530/9000。

## 6. PSA / PSP 与安全上下文

```bash
kubectl get psp -A
kubectl get ns ai-tims --show-labels
kubectl -n ai-tims get pod -o jsonpath='{range .items[*]}{.metadata.name}{" "}{.spec.securityContext.runAsUser}{"\n"}{end}'
```

- **预期**：1.24 下 PSP 可能仍存在但已弃用；namespace 无 `restricted` 强约束；业务 Pod `runAsUser=10001`，中间件按其镜像默认用户运行。
- **失败判读**：
  - namespace 标了 `pod-security.kubernetes.io/enforce=restricted`：业务 Pod 已满足，但 MySQL/Redis/RabbitMQ 可能因 `allowPrivilegeEscalation`/capabilities 被拒，需管理员放宽到 `baseline`。
  - `Error: container has runAsNonRoot and image has non-numeric user`：中间件被强制 `runAsNonRoot`，同样需放宽。

## 7. 镜像仓库可达与凭据

```bash
kubectl -n ai-tims get secret tims-registry
kubectl -n ai-tims run pulltest --rm -it --restart=Never \
  --image=<REG>/ticket-gateway:1.0.0 --image-pull-policy=Always -- command -v java
```

- **预期**：Secret 类型 `kubernetes.io/dockerconfigjson`；pulltest 能拉下镜像并打印 java 路径。
- **失败判读**：
  - `401 Unauthorized`：Secret 账号/密码错，或仓库项目未授权。
  - `manifest unknown`：push 未成功或 tag 不是 `1.0.0`，回查 0.2 的输出。
  - `x509: certificate signed by unknown authority`：公司仓库是自签证书，需给节点装 CA（管理员操作）。

## 8. 镜像架构

```bash
kubectl get nodes -o wide
docker image inspect <REG>/ticket-gateway:1.0.0 --format '{{.Architecture}}/{{.Os}}'
```

- **预期**：所有节点 `amd64`；镜像 `amd64/linux`。
- **失败判读**：出现 `exec format error` 或 `no match for platform in manifest`，说明构建机或镜像架构不对，需在 x86_64 上重建。

## 9. containerd 1.6.24 对镜像 tar 的兼容

```bash
# 在公司任意节点
sudo ctr -n k8s.io images import /path/tims-images-1.0.0.tar
sudo ctr -n k8s.io images ls | grep ai-tims | wc -l
```

- **预期**：13 个镜像可导入、可列出。
- **失败判读**：
  - `unexpected EOF`：tar 传输损坏，重传并复验 sha256。
  - 导入成功但 Pod 仍 `ImagePullBackOff`：优先走 0.2 的 push + 从仓库拉取；`docker save` 的多架构 index 在部分 containerd 版本下无法被 kubelet 直接识别（本次本地 k3s 演练已复现，见附录）。

## 10. 公网出口（智谱 / SMTP）

```bash
kubectl -n ai-tims exec deploy/ticket-knowledge -- sh -c 'timeout 5 bash -c "cat < /dev/null > /dev/tcp/open.bigmodel.cn/443" && echo reachable || echo blocked'
```

- **预期**：`reachable`。
- **失败判读**：`blocked` 时：
  - 向量化与 AI 抽取会降级：`chain_trace.degraded=true`，审核页（若已实现告警）应提示人工补录；
  - 处理方式：申请出网白名单，或把 `LLM_BASE_URL`/`ZHIPU_EMBEDDING_URL` 指向公司内网网关。**上线前必须给出结论，不能默认可用**。

## 11. 时区 / NTP

```bash
kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.name}{" "}{.status.nodeInfo.osImage}{"\n"}{end}'
kubectl -n ai-tims exec deploy/ticket-system -- date
kubectl -n ai-tims exec deploy/ticket-system -- sh -c 'echo $TZ'
```

- **预期**：Pod 内 `CST +0800`，`TZ=Asia/Shanghai`，与节点时间差 < 5s。
- **失败判读**：时区为 UTC → 检查 ConfigMap `TZ` 是否被覆盖；时间漂移 → 节点 NTP 未同步，工单时间线与 Token 校验都会异常。

## 12. Nacos 3 / Milvus 2.4 实际启动行为

```bash
kubectl -n ai-tims get pods -w
kubectl -n ai-tims logs statefulset/tims-nacos --tail=50
kubectl -n ai-tims logs deploy/tims-milvus --tail=50
kubectl -n ai-tims exec deploy/tims-milvus -- curl -sf http://127.0.0.1:9091/healthz && echo milvus-ok
```

- **预期**：nacos `1/1 Running` 且日志出现 `Nacos started successfully`；milvus 探针通过、`/healthz` 返回 ok；六服务全部注册到 Nacos。
- **失败判读**：
  - Nacos `CrashLoopBackOff` + `No such file`：PVC 权限问题，确认 `fsGroup: 1000` 生效。
  - Milvus 长时间 `0/1`：首次启动建索引慢，startupProbe 已给 10 分钟；超过 10 分钟查 etcd/minio 连通。
  - 服务注册不上：确认 `NACOS_ADDR=tims-nacos:8848` 与服务名一致。

## 附 B：演练中发现并已修复的交付缺陷

1. **`/app/logs` 权限**：Logback 写 `./logs/ai-tims.log`，镜像内目录不存在且 `/app` 归 root，非 root 10001 启动即崩。已在 `deploy/docker/Dockerfile` 补 `mkdir -p /app/logs && chown -R 10001:10001 /app`。
2. **Secret 未注入**：六服务只注入了部分密码，`RABBIT_PASSWORD` 等缺失导致 push/knowledge 认证失败退出。已在六个 Deployment 的 `envFrom` 统一加 `secretRef: tims-app-secret`。
