# AI-TIMS 发布流程（固定流程）

> 适用场景：从改代码到公司环境上线的完整链路。
> 本文只写 **2026-11-20 在台式、VM、公司内网实机验证过** 的路径，不写推测。
> 涉及环境事实（地址、账号、路径）以 `AI-TIMS-环境速查.md` 和 `docs/ops/公司环境操作记录.md` 为准。

---

## 0. 角色分工

| 角色 | 机器 | 只做这些事 | 绝对不做 |
|---|---|---|---|
| 编辑 / 传输 | 台式 Windows `g:\JAVA\Code\ai-tims` | 改代码、`scp` 单文件到 VM、整理交付包（镜像包统一放 `D:\ai-tims-images\`） | 不编译、不构建镜像、不连集群 |
| 编译 / 构建 / 导出 | 开发机 VM `dev@192.168.40.10`，仓库 `/home/dev/ai-tims` | `mvn package`、`docker build`、`docker save|gzip`、生成 MANIFEST | 不 push Harbor（网络不通）、不碰集群 |
| 装载 / 推送（特殊场景） | 公司内网任意装了 Docker 的机器（master1 或跳板机） | `md5sum -c`、`docker load`、`docker login`、`docker push` | 不改清单 |
| 发布 | master1（仓库在 `/data/sdv1/tims`） | 新版 `deploy.sh`：镜像准备（找包 → load → push）→ 改 `newTag`/前端 `image` → `apply -k` → `rollout status` → 回读 | 不 build 镜像 |

## 1. 改代码之前

1. 先读 `AI-TIMS-环境速查.md` 与 `/home/dev/DEVLOG.md`，确认环境事实与最近决策，不要凭记忆。
2. 台式 `git status`、`git log --oneline -5`、`git rev-parse HEAD`，同时看远端：`git fetch origin && git log --oneline origin/main -5`。
3. 台式与 VM **必须对齐到同一提交**再动代码；VM 工作区有大量未提交改动时，只覆盖本次改到的单个文件，不许整目录覆盖、不许 `git add .`。

---

## 2. 代码同步（台式 ↔ VM）

### 2.1 正常路径（VM 能读台式文件、GitHub 通）

1. 台式改完，记下文件清单。
2. 覆盖前先核对：把 VM 上的旧文件拉回本地，与台式**改动前**版本对比，确认差异只有本次改动（防止覆盖他人未提交的改动）。
3. VM 上备份：`cp <文件> /home/dev/verify-backup-<日期>/`。
4. `scp` 单个文件到 VM，`md5sum` 比对两边一致。
5. VM 上提交并推送（台式没配 git 身份时由 VM 提交）：

```bash
cd /home/dev/ai-tims
git add <只列本次文件>
git commit -F /tmp/commit-msg.txt
git push origin main
```

### 2.2 换行符（必看）

- 台式工作区是 **CRLF**，仓库历史是 **LF**。直接 `scp` 上去再提交，整文件都会显示为改动。
- 同步后在 VM 上统一转换：

```bash
cd /home/dev/ai-tims
sed -i 's/\r$//' <本次改到的文件...>
git add <本次改到的文件...>
```

- 转换不改变代码语义，但必须先转再提交；已提交错了可以 `git reset --soft` 后重来，不要 force push。

### 2.3 台式连不上 GitHub 时的绕行

1. 台式导出补丁（不要用 PowerShell `>` 重定向，会写成 UTF-16 导致 `git am` 报 `Patch format detection failed`）：

```powershell
git -C "g:\JAVA\Code\ai-tims" format-patch -1 <提交号> -o "$env:TEMP\patch-out"
scp "$env:TEMP\patch-out\0001-*.patch" ubuntu-server:/tmp/<名字>.patch
```

2. VM 用临时 worktree 应用并推送（不碰 VM 的脏工作区）：

```bash
cd /home/dev/ai-tims
git fetch origin
git worktree add /tmp/wt-push origin/main -b push-tmp
cd /tmp/wt-push
git am /tmp/<名字>.patch
git push origin HEAD:main          # 只允许 fast-forward，禁止 force
cd /home/dev/ai-tims
git worktree remove /tmp/wt-push && git branch -D push-tmp
git fetch origin && git reset --soft origin/main && git reset   # 只动 HEAD/索引，不碰工作区
```

3. 台式恢复网络后 `git fetch origin`；仍不通时可用直连地址取同一提交（不新增 remote、不改 config）：

```powershell
git -C "g:\JAVA\Code\ai-tims" -c core.sshCommand="ssh -o BatchMode=yes" fetch "ssh://ubuntu-server/home/dev/ai-tims" main
git -C "g:\JAVA\Code\ai-tims" reset --soft FETCH_HEAD
git -C "g:\JAVA\Code\ai-tims" reset
```

4. 核对两边 `git rev-parse HEAD` 相同。

```bash
cd /home/dev/ai-tims/ai-tims-parent
```

- `-pl` 可写单模块或逗号列表；`-am` 会一并编译 `ai-tims-common`。

- 结果核对：`ticket-*/target/<模块>-1.0.0-SNAPSHOT.jar` 存在且时间戳是本次。

## 4. 构建镜像（VM）

### 4.1 命名与 tag 规则

- 仓库路径固定 `harbor.xnunion.com/library/<name>`；Harbor 下**没有** `ai-tims` 项目，只有 `library`。
- 后端 `name` = 服务名：`ticket-ai`、`ticket-knowledge`、`ticket-gateway`、`ticket-system`、`ticket-order`、`ticket-push`。
- 前端 `name` = `ai-tims-front`（不是 ticket-front）。
- tag 语义化递增（`1.0.1` → `1.0.2` → `1.0.3`），**禁止 latest**，**禁止复用已推过的 tag 覆盖推送**（节点有镜像缓存，不会重拉）。

### 4.2 必须显式传仓库与 tag

`deploy/scripts/images.env` 里的 `REGISTRY_PREFIX` 是占位 `registry.company.internal/ai-tims`，`IMAGE_TAG` 默认 `1.0.0`；`export-images.sh` 默认 `REGISTRY=harbor.xnunion.com/library`、`TAG=1.0.0`。
**构建时必须显式指定，不能吃默认值。**

### 4.3 后端镜像

```bash
cd /home/dev/ai-tims
docker build \
  --build-arg JAR_FILE=ai-tims-parent/ticket-ai/target/ticket-ai-1.0.0-SNAPSHOT.jar \
  -f deploy/docker/Dockerfile \
  -t harbor.xnunion.com/library/ticket-ai:<tag> .

# ticket-knowledge 同理，换 JAR_FILE 与 tag
docker build \
  --build-arg JAR_FILE=ai-tims-parent/ticket-knowledge/target/ticket-knowledge-1.0.0-SNAPSHOT.jar \
  -f deploy/docker/Dockerfile \
  -t harbor.xnunion.com/library/ticket-knowledge:<tag> .
```

### 4.4 前端镜像

```bash
cd /home/dev/ai-tims
docker build -f ai-tims-front/Dockerfile -t harbor.xnunion.com/library/ai-tims-front:<tag> ai-tims-front
```

- Dockerfile 是多阶段：`node:20-alpine` 容器内 `npm install`（走 npmmirror）+ `npm run build`，运行层 `nginx:1.27-alpine`。

### 4.5 基础镜像

- VM 本地已具备：`eclipse-temurin:17-jre-jammy`、`nginx:1.27-alpine`、`node:20-alpine`。
- 构建前用 `docker images | grep <名字>` 确认；缺失时不要用公共替代镜像，先报告。

### 4.6 产出后核对

```bash
docker images harbor.xnunion.com/library/ticket-ai
docker images harbor.xnunion.com/library/ticket-knowledge
docker images harbor.xnunion.com/library/ai-tims-front
```

逐个确认新 tag 已出现、Image ID 与旧 tag 不同。

## 5. 导出（VM）

- 固定格式：`docker save | gzip` → `<name>-<tag>.tar.gz`，例如 `ticket-ai-1.0.2.tar.gz`。
- 目录：`/home/dev/tims-images-<日期>`，例如 `/home/dev/tims-images-20261120`。
- 每个包自检两道：
  1. `gzip -t <包>` 解压完整性；
  2. `tar -xzOf <包> manifest.json` 回读，确认 RepoTags 正是目标镜像，防止导出成别的镜像。
- 同时生成 `MANIFEST.txt`（文件/镜像标签/大小/md5/总量）与 `MANIFEST.md5`（`md5sum -c` 格式），最后跑一次 `md5sum -c MANIFEST.md5` 确认全 OK。
- 只导出本次要发的包，不要顺手重打其他服务或中间件。

### 5.1 镜像包位置约定（三处，别混）

| 环节 | 位置 | 角色 |
|---|---|---|
| 导出 | VM `/home/dev/tims-images-<日期>` | 构建产物，VM 上唯一导出目录 |
| 台式保管 | **`D:\ai-tims-images\`** | 台式上的包统一放这里，**不再放仓库的 `images/`** |
| 公司侧 | `/data/sdv1/tims/images/` | master1 上供 `deploy.sh` 自动 load/push 的目录 |

- `deploy.sh` 的 `IMAGES_DIR` 默认值是「仓库根下的 `images`」；**公司侧仍然用 `/data/sdv1/tims/images/`，不要因为台式改为 `D:\` 就跟着改公司那边的路径**（否则脚本找不到包）。
- 仓库 `images/` 下的历史包仅作留存，不再新增。

## 6. 迁移（VM → Windows → 公司内网）

- **VM 连不上 Harbor**：`getent hosts harbor.xnunion.com` 失败、`curl http://harbor.xnunion.com/v2/` 返回 000，且无 `~/.docker/config.json`（没有仓库凭据）。所以在 VM 上 push 不可能，也不要尝试。
- 路线：`scp` 把 tar.gz 与 `MANIFEST.txt` / `MANIFEST.md5` 从 VM 拉到台式 **`D:\ai-tims-images\`**（台系统一位置），再通过 U 盘/内网摆渡机拷进公司内网 `/data/sdv1/tims/images/`。
- 搬运后**必须先校验**：`md5sum -c MANIFEST.md5`（Windows 侧可用 `Get-FileHash -Algorithm MD5` 逐个比对）。

## 7. 装载与推送（新版脚本内置，手工版仅特殊场景）

### 7.1 默认：由 `deploy.sh` 自动完成

新版 `deploy/sdv1/deploy.sh` 在部署前做「镜像准备」（`ensure_image`）：

1. 在 `IMAGES_DIR`（默认 `<仓库根>/images`，其次 `<仓库根>/deploy/sdv1/images`）找包，包名 `<镜像名>-<tag>.tar` / `.tar.gz` / `<base>_<tag>.tar[.gz]`；**这是公司侧路径，固定为 `/data/sdv1/tims/images/`，不要因为台式改为 `D:\ai-tims-images\` 就改这里**；
2. 本机没有该 tag → `docker load -i <包>`，load 后再 `docker image inspect` 确认镜像确实在；
3. 远端 Harbor 没有该 tag（`docker manifest inspect` 失败）→ `docker push`；已存在则跳过（push 幂等）；
4. 任一步失败立即 `die` 中止，不会继续改集群。

前置条件：master1 上有 docker、已 `docker login harbor.xnunion.com`、包已放到 `/data/sdv1/tims/images/`。
**脚本 load 前不校验 md5/sha**，搬运环节仍要自己先跑 `md5sum -c MANIFEST.md5`。

### 7.2 手工版（`--no-image`，或脚本不可用时）

```bash
cd <交付目录>
md5sum -c MANIFEST.md5          # 必须全部 OK，FAILED 就重拷该文件

docker load -i ticket-ai-1.0.2.tar.gz
docker load -i ticket-knowledge-1.0.2.tar.gz
docker load -i ai-tims-front-1.0.3.tar.gz

docker login harbor.xnunion.com             # 账号找运维，不写进任何文档
docker push harbor.xnunion.com/library/ticket-ai:1.0.2
docker push harbor.xnunion.com/library/ticket-knowledge:1.0.2
docker push harbor.xnunion.com/library/ai-tims-front:1.0.3
```

- 用 `--no-image` 跑 `deploy.sh` 时，镜像必须已按上面步骤进 Harbor。
- **`deploy/scripts/load-and-push.sh` 仍不适用于本流程**：它 source `images.env`，按占位前缀 `registry.company.internal/ai-tims/<svc>:1.0.0` 找镜像再重打 tag，和实际构建的 `harbor.xnunion.com/library/<svc>:<新tag>` 对不上。
- 推送后可选校验：`docker pull harbor.xnunion.com/library/ticket-ai:<tag>`。

## 8. 部署（master1）

### 8.1 后端（ai / knowledge / gateway / system / order / push）

```bash
cd /data/sdv1/tims
EXPECTED_CONTEXT=kubernetes-admin@kubernetes ./deploy/sdv1/deploy.sh <service> <tag> --yes
```

- `service` 取值：`ai`、`knowledge`、`gateway`、`system`、`order`、`push`；对应 Deployment 为 `ticket-<service>`。
- 新版脚本实际动作（按顺序）：
  1. 校验参数，打印 context / namespace / 现有 Pod；
  2. **镜像准备**：按 `IMAGES_DIR` 找包，本机没有就 `docker load`，Harbor 没有就 `docker push`（`--no-image` 可跳过，见第 7 节）；
  3. 备份 `.bak`，改 `deploy/k8s/overlays/company/kustomization.yaml` 的 `newTag`，同步 base 的 `image:` 行（前端改 `base/apps/front.yaml`）；
  4. **部署前预检**：`kubectl kustomize` 渲染一次，打印全部 image 行与关键配置，和集群现状逐项对比；跨 ConfigMap 重复 key 告警；
  5. 版本回退（如 1.0.2 → 1.0.1）默认终止，必须交互输入 `DOWNGRADE` 或加 `--allow-downgrade`；
  6. `kubectl apply -k deploy/k8s/overlays/company` → 逐个 `rollout status --timeout=180s`（目标 tag 与当前相同时改为 `rollout restart`）→ `jsonpath` 回读实际镜像；
  7. 任一步失败：用 `.bak` 还原并重新 apply，打印回滚后的 tag 与排错命令。
- **禁止 `all`**：`all` = 6 个后端一次性改成同一个 tag（`BACKENDS=(order system gateway knowledge ai push)`），而一次发版通常只有部分服务有新镜像；新版还会先对 6 个镜像逐个 load/push，缺包直接中止。按服务逐个执行。
- 回滚后端：`./deploy.sh <service> <旧tag> --no-image --yes --allow-downgrade`。

### 8.2 前端

新版脚本的 `front` 分支已改为**改 `deploy/k8s/base/apps/front.yaml` 的 image tag + `apply -k`**，不再用 `kubectl set image`，符合「前端发版铁律」。可以直接：

```bash
cd /data/sdv1/tims
EXPECTED_CONTEXT=kubernetes-admin@kubernetes ./deploy/sdv1/deploy.sh front <新tag> --yes
```

手工等价做法（脚本不可用时）：

```bash
cd /data/sdv1/tims
sed -i 's|image: harbor.xnunion.com/library/ai-tims-front:.*|image: harbor.xnunion.com/library/ai-tims-front:<新tag>|' deploy/k8s/base/apps/front.yaml
kubectl apply -k deploy/k8s/overlays/company
kubectl -n ai-tims rollout status deploy/ai-tims-front --timeout=180s
```

- 仍然**禁止 `kubectl set image` 改前端**：只改集群不改清单，之后任何一次 `apply -k` 都会把 tag 带回旧值（2026-11-18 已因此丢过 1.0.2）。

### 8.3 master1 更新脚本（一次性）

```bash
# 1) 备份旧版（旧版 13,162 B，无 docker 逻辑）
cp -p /data/sdv1/tims/deploy/sdv1/deploy.sh /data/sdv1/tims/deploy/sdv1/deploy.sh.bak-$(date +%Y%m%d)

# 2) 传新版（在台式执行；localhost 换成你自己的传输方式）
scp deploy/sdv1/deploy.sh <账号>@<master1>:/data/sdv1/tims/deploy/sdv1/deploy.sh

# 3) 在 master1 校验：语法、关键特征、md5
bash -n /data/sdv1/tims/deploy/sdv1/deploy.sh
grep -c "docker load" /data/sdv1/tims/deploy/sdv1/deploy.sh   # 新版应为 1+
grep -c "IMAGES_DIR"  /data/sdv1/tims/deploy/sdv1/deploy.sh   # 新版应为 1+
md5sum /data/sdv1/tims/deploy/sdv1/deploy.sh                  # 新版 = 467f1110cece2dad1d05644b96716e1c（LF 版本）
```

- 若 master1 上编辑器改成 CRLF，md5 会变；此时以 `grep -c` 两条都 > 0 且 `bash -n` 通过为准。
- 前置条件：master1 有 docker 且能连 Harbor（`docker login harbor.xnunion.com` 已做过）、镜像包放在 `/data/sdv1/tims/images/`（脚本 `IMAGES_DIR` 默认 `<仓库根>/images`，其次 `deploy/sdv1/images`）。
- 旧版没有 docker 逻辑，也没有 `--no-image` / `--allow-downgrade`；换脚本前先确认新版已传上去，否则按第 7.2 节手工 load/push。

## 12. 已知坑清单

1. **CRLF**：台式工作区 CRLF、仓库 LF，scp 后不 `sed -i 's/\r$//'` 会导致整文件 diff。
2. **`images.env` 是占位值**：`registry.company.internal/ai-tims` + `1.0.0`，直接跑脚本会打错 tag。
3. **`load-and-push.sh` 不适用**：按占位仓库名找镜像，找不到本次的 `harbor.xnunion.com/library/...:新tag`。
4. **旧版 `deploy.sh`（13,162 B）的 `front` 分支用 `kubectl set image`**：违反前端铁律，apply -k 会把 tag 带回去。新版已改为改 `front.yaml` + apply -k；master1 未换脚本前不要用 front 分支。
5. **同一 tag 不能覆盖推送**：节点有缓存不重拉，必须发新 tag。
6. **Harbor 下没有 `ai-tims` 项目**，只有 `library`，前缀写错就 ImagePullBackOff。
7. **VM 连不上 Harbor**（DNS 失败、无 docker 凭据），只能在 VM 构建 + 导出。
8. **PowerShell 重定向补丁变 UTF-16**：用 `git format-patch -o <目录>` 生成补丁文件。
9. **台式未配 git 身份**：cherry-pick/commit 会失败；提交统一在 VM 上做。
