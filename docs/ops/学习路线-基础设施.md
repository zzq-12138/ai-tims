## 阶段① registry：先懂「镜像从哪来」

**目标**：理解镜像仓库在交付链路里的位置——为什么本地构建的镜像 k3s 拿不到、为什么要自己架一个仓库。

**做什么**（对照 [中间件动手实验.md 实验 D](中间件动手实验.md)）：
1. 起一个隔离的 registry 实验实例（5500 端口）；
2. 走完 推 → 删本地 → 拉 → digest 比对 闭环；
3. 理解 `_catalog`、`tags/list` 两个 API。

**验证产出**：推拉闭环成功输出（含 digest 一致截图）+ `_catalog` 返回截图。

**对应论文**：部署设计/运行环境章节（论文章节编号待开题定稿，**需现场确认**）——「镜像交付方案：本地 registry + tag 规则」一小节。

**答辩可能被问**：
- 为什么不用 Docker Hub / 为什么不买云仓库？（答：公司仓库优先 + 本地 registry 兜底的拍板口径；离线/内网可用）
- digest 和 tag 的区别？（tag 可变，digest 不可变；可复现部署用 digest）

## 阶段② compose 中间件：把四个组件亲手搭一遍

**目标**：Nacos / Milvus(+etcd/minio) / RabbitMQ / registry 每个都能独立从零写出 compose、验证健康、理解参数。**必须动手**，不能只看复盘文档。

**做什么**（对照 [中间件动手实验.md](中间件动手实验.md)，每个组件四级台阶 L1~L4）：
1. L1 自己写最小 compose 跑起来；
2. L2 加数据卷验证持久化；
3. L3 加内存限额与账号；
4. L4 把实验实例接入项目验证一次真实调用（Nacos 注册服务、Milvus 同步一条知识、RabbitMQ 收发一条消息）。

**验证产出**：四个实验的截图（容器 healthy、持久化证据、L4 真实调用证据）+ 每个实验的记录表填完。

**对应论文**：架构设计章节的「中间件选型」——每个组件一段「选型理由 + 部署要点」，素材直接来自 [中间件部署复盘.md](中间件部署复盘.md) 的选型与踩坑表。

**答辩可能被问**：
- Nacos 为什么 standalone 够用？（毕设规模、单机；生产才需要集群）
- Milvus 为什么需要 etcd 和 minio？（元数据 / 对象存储分离）
- 事件为什么先用 Redis stub 后换 RabbitMQ？（接口先行、签名不变，M4 切换零改造）
- 内存预算 256/256/1536/350/128 怎么定的？（16G 总量分配台账，实测余量 11.7G）

## 阶段③ k3s 单节点

**目标**：按 [k3s单节点搭建手册.md](k3s单节点搭建手册.md) 从前置检查走到卸载，全程亲手。

**做什么**：手册阶段一~八全部走一遍，重点是：第一个 Pod 成败原因、`registries.yaml` 私有仓库配置、`imagePullPolicy` 三条规则。

**验证产出**：手册第六节截图清单（nodes Ready / version / first pod / registry 镜像 Pod / 拉取事件）。

**对应论文**：技术路线一句话口径（任务书钉死）：「部署方案：VM 单节点 k3s 验证 + 企业集群 namespace 级部署」——**开题材料不展开 k8s 实施细节**（DEVLOG 2026-11-02 拍板），实施细节留到中期后的部署章节。

**答辩可能被问**：
- 为什么 k3s 不是 kubeadm/完整 K8s？（单节点省 ~1.5-2G 控制面开销；验收口径只需单节点；最终演示在公司集群）
- 单节点的局限？Node 宕机全挂——如实承认，毕设验证的是交付物（manifests）可在任意 namespace 一键部署，不夸大 HA。
- k3s 和 Docker 什么关系？（自带 containerd 并存，镜像互不可见，经 registry 打通）

## 阶段④ 部署一个服务到 k3s

**目标**：把 ticket-system 一个服务真实跑上 k3s：打镜像 → 推 registry → Deployment + Service(NodePort) → 配置注入 → ping 通。

**做什么**：
1. 写最小 Dockerfile（JRE 基础镜像 + fat jar），构建 `localhost:5000/tims/system:{ver}`（tag 带版本，勿用 latest——IfNotPresent 坑）；
2. Deployment 挂 `ConfigMap`（普通配置）+ `Secret`（密钥，对齐 `.env.example` 的注入链路注释：`.env → compose environment → K8s Secret`）；
3. Service 用 NodePort 暴露，本机 `curl http://192.168.40.10:{nodePort}/api/system/ping` 返回统一 Result；
4. 练滚动更新：改 tag 重新 apply，观察旧 Pod 退出新 Pod 就绪。

**验证产出**：ping 通的 curl 输出截图 + `kubectl rollout status` 输出 + 滚动更新前后 `get pods` 对比截图。

**对应论文**：部署章节的「单服务交付链路」（CI 构建 → 镜像 → manifests → 集群）；这也是 GitHub Actions CI（已建，`mvn -B -DskipTests package`）向部署侧的自然延伸。

**答辩可能被问**：
- 配置和密钥怎么进容器？（ConfigMap/Secret 环境变量注入，密码不落镜像不落 git）
- 滚动更新时服务会不会断？（多副本 + 就绪探针；单副本有秒级断口，如实说明）
- 应用健康检查怎么做？（`/api/{svc}/ping` + actuator，任务书统一口径）

## 阶段⑤ 全栈 manifests 化（对应 M8）

**目标**：六服务 + 前端 + 中间件的部署清单可在**任意 namespace** 一键 apply（M8 验收口径：Deployment/Service/Ingress/ConfigMap/Secret/HPA + namespace 参数化 + kustomize 或 values 化）。

**做什么**：
1. 中间件以 StatefulSet/Deployment + PVC manifests 化（或声明依赖集群外已有实例，二选一，**需现场确认**公司集群是否提供 MySQL/MQ 中间件）；
2. namespace 参数化（kustomize `namespace:` 字段），六服务一套 base + overlays；
3. HPA 给 order/knowledge 两个热点服务配 CPU 阈值副本伸缩；
4. 端到端验证：建单 → 发布知识 → HYBRID 检索命中 → 预演 M4 推送链路埋点。

**验证产出**：`kubectl apply -k overlays/dev` 一键部署录像/截图 + 六 ping 全通 + 滚动更新与 Pod 自愈演示（删 Pod 自动重建）——M8「VM 单节点上演示 Pod 自愈/滚动更新」验收原文要求。

**对应论文**：部署与交付章节主体；评测章节（M7）在此环境跑 100 条评测集与 200 单压测。

**答辩可能被问**：
- 多租户在 K8s 里怎么体现？（应用层 tenant_id 隔离，共享库共享表——K8s namespace 是部署隔离不是租户隔离，两层概念别混）
- 一键部署怎么保证可重复？（manifests 版本化 + 镜像 digest/tag 锁定 + init.sql 一键重建）
- 为什么不演示跨节点容灾？（单节点口径 + 公司集群 namespace 部署，论文不夸大 HA）
