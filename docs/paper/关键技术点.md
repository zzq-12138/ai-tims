## 一、架构与设计决策

### K01 按业务域拆分的六微服务架构

- 问题/背景：单体应用无法把认证、工单、知识检索、实时推送分别扩容，且 M4 压测需要单独替换瓶颈服务；毕业设计又要求体现微服务治理能力。
- 方案：按业务域拆为 `ticket-gateway`(8080)、`ticket-system`(8101)、`ticket-order`(8102)、`ticket-knowledge`(8103)、`ticket-ai`(8105)、`ticket-push`(8109)，全部注册到 Nacos，由网关按 `/api/{svc}/**` 前缀路由，下游保留全路径、网关不剥前缀。路由配置见 `ai-tims-parent/ticket-gateway/src/main/resources/application.yml`。
- 数据/证据：Nacos 服务列表稳定 6 条；7 条路由（auth/system/order/kb/ai/push/ws）验证全部 200；各服务 `/api/{svc}/ping` 统一返回 `Result`。
- 论文可用角度：系统设计章节——论证“按业务能力而不是按技术分层拆分”，并说明网关不剥前缀可让服务本地直连调试，降低联调成本。
- 证据来源：DEVLOG 三、M0 骨架收口与 M1 第一阶段（`56bef3d`、`93025a5`）；`ticket-gateway/.../application.yml`。

### K02 共享库共享表 + tenant_id 多租户隔离

- 问题/背景：若采用独立库或独立 schema，建库、迁移、备份成本随租户线性增长；本系统租户规模小，隔离诉求主要是“数据不串”和“审计可追溯”，不是物理隔离。
- 方案：单库 `aitims` 内所有业务表统一加 `tenant_id` 列，唯一键一律设计为 `(tenant_id, 业务键)`（如 `uk_tenant_phone`、`uk_tenant_username`）；`TenantContext` 按“Sa-Token 会话 → 请求头 `X-Tenant-Id` → 默认 1”的优先级解析租户；MyBatis-Plus `TenantLineInnerInterceptor` 自动为查询追加 `tenant_id = ?`、为插入回填 `tenant_id`；定时任务用 `TenantHelper.ignore` 显式关闭拦截。
- 数据/证据：跨租户读写 E2E 通过；注册、登录、工单、知识检索链路均验证租户不串；`sql/init.sql` 一键重建成功。
- 论文可用角度：系统设计与数据库设计章节——对比“独立库/独立 schema/共享表”三种多租户方案，说明在低租户量、强运维简化诉求下选择共享表，并给出拦截器实现与绕过场景。
- 证据来源：DEVLOG 三、M2 批一（`99d11e8`）；代码 `TenantContext`、`MybatisPlusConfig`；`sql/init.sql` 唯一键定义。

### K03 知识标签采用 JSON 列而非独立标签表

- 问题/背景：标签需要支持过滤与展示，但若建 `kb_tag` + `kb_knowledge_tag` 两张关联表，每次列表查询都要多一次 join，且标签维护入口很少。
- 方案：`kb_knowledge.tags` 使用 MySQL `JSON` 列存储字符串数组（如 `["贴片机","抛料"]`），应用层序列化/反序列化；检索主链路不依赖标签表，标签只在混合检索重排阶段做命中加权。
- 数据/证据：无实测数据（未做 JSON 列 vs 关联表的查询基准测试）；功能验证通过，53 条知识正常读写。
- 论文可用角度：数据库设计章节——作为“反范式化取舍”的案例，论证依据是“单租户 + 标签仅用于过滤/展示 + 无标签维度统计需求”，并诚实说明未做性能对比。
- 证据来源：`sql/init.sql` 第 266-292 行注释与 `tags JSON` 定义；DEVLOG 三、M3 批 B（`7714233`）。

### K04 不引入 Spring Security，采用 Sa-Token

- 问题/背景：Spring Security 的过滤器链、`UserDetailsService`、会话与 CSRF 配置对“网关统一鉴权 + 下游无状态服务”的轻量场景过重，且与 WebFlux 网关组合时排障成本高。
- 方案：认证与授权用 Sa-Token（`token-name: Authorization`、UUID token、30 天有效期、`is-share: true`），密码哈希单独引入 `spring-security-crypto` 的 `BCryptPasswordEncoder`，不引入 `spring-boot-starter-security`。网关用 `SaReactorFilter` 统一拦截，白名单放行登录、注册、验证码、健康检查与 `/ws/**`。
- 数据/证据：登录/登出/当前用户/注册全链路 E2E 通过；未登录访问受保护接口返回 HTTP 401 + 业务码 10401；全模块 `mvn -DskipTests package` 通过。
- 论文可用角度：系统设计与安全设计章节——论证“鉴权前置到网关、业务服务只信任网关注入的身份”，并对比 Spring Security 的适用边界，避免写成“因为简单所以不用”。
- 证据来源：DEVLOG 三、M1 第一阶段；`ticket-gateway/.../SaTokenConfigure.java`；父 POM 依赖清单。

### K05 工单状态机以常量迁移表为唯一事实来源

- 问题/背景：若在 Service 里散落 `if (status == X)` 判断，新增状态或分支时容易漏改，且无法统一返回错误码、无法统一写流转日志。
- 方案：定义 7 个状态（`PENDING` 待受理、`PROCESSING` 处理中、`PENDING_VERIFY` 待验证、`RESOLVED` 已解决、`CLOSED` 已关闭、`SUSPENDED` 已挂起、`CANCELLED` 已取消）与 11 条合法迁移，集中放在 `STATE_MACHINE` 常量表；迁移入口 `transit()` 先查表，非法迁移抛 `20401`；每次成功迁移写 `wo_ticket_log` 流转日志（前后状态、操作人、备注、时间）。
- 数据/证据：37/37 条 E2E 断言通过，覆盖主流程（待受理→处理中→待验证→已解决→已关闭）及挂起/恢复、取消分支；非法迁移全部返回 20401 且工单状态不变。
- 论文可用角度：详细设计章节——把“状态机表驱动”作为可维护性设计，说明新增迁移只需改常量表；可配一张状态迁移图。
- 证据来源：DEVLOG 三、M2 批二（`cb4d24a`）；`ticket-order/.../statemachine/TicketStateMachine.java`。

### K06 自动派发规则：4/2/1 加权打分

- 问题/背景：工单创建后需要给出建议处理人，人工分派在批量建单场景下不可行。
- 方案：对候选处理人按三个维度打分：同部门 +4、同角色 +2、当前在办量少 +1（在办量升序作为同分排序），取最高分且未超在办上限者；接口返回建议处理人，不强制落库，保留人工改派。
- 数据/证据：E2E 验证建单响应带 `assigneeId/assigneeName`，规则命中符合预期；无独立准确率指标。
- 论文可用角度：详细设计章节——说明“规则打分而非模型推荐”的阶段性选择，为 M5 的 AI 分派留出替换点。
- 证据来源：DEVLOG 三、M2 批二；`ticket-order/.../service/DispatchService.java`。

### K07 工单号 Redis 日流水 + 唯一键兜底

- 问题/背景：数据库自增 ID 不适合作为对外单号（可枚举、跨环境不连续），而 UUID 单号不可读、不利于人工沟通。
- 方案：格式 `WO + yyyyMMdd + 4 位日流水`；Redis `INCR` 生成日流水，key 设置约 25 小时 TTL（覆盖跨日边界）；插入前依赖 `uk_tenant_ticket_no` 唯一键，捕获重复键异常后重试取号。
- 数据/证据：模拟器批量创建 200 条工单无重号；单机建单吞吐 8.3/s（优化前）→ 21.3/s（优化后）。
- 论文可用角度：详细设计章节——说明“可读性 + 并发安全 + 跨日重置”三者的取舍，以及 Redis 故障时的降级边界。
- 证据来源：DEVLOG 三、M2 批二与 M4 批二；`ticket-order/.../service/TicketService.java`；`sql/init.sql` 唯一键。

### K08 附件安全模型：UUID 存储名 + 白名单 + 越权校验

- 问题/背景：附件上传存在路径穿越、可执行文件伪装、超大文件占满磁盘、以及跨租户/跨用户越权下载四类风险。
- 方案：①原始文件名不落盘，存储名用 UUID，扩展名从白名单取（仅文档/图片/压缩包等允许类型，拒绝 `exe/js/html` 等）；②单文件上限 20MB；③下载与删除前校验 `tenant_id` 与上传人/工单归属，越权返回业务错误；④附件元数据落 `wo_attachment`，物理文件放独立目录，不通过静态资源直接暴露。
- 数据/证据：15/15 条附件 E2E 断言通过，覆盖正常上传下载、超限拒绝、类型拒绝、跨租户越权拒绝、删除后不可下载。
- 论文可用角度：安全设计章节——按“输入校验—存储隔离—访问控制”三层组织，配一张攻击面与防护对照表。
- 证据来源：DEVLOG 三、M3 批 A（`7714233`）；`ticket-order/.../service/AttachmentService.java`；`wo_attachment` 表定义。

### K09 单节点 k3s 而非 kubeadm 的部署取舍

- 问题/背景：毕设环境是 4 vCPU / 16GB 的虚拟机，已经承载 MySQL、Redis、Nacos、RabbitMQ、Milvus（约 4GB RSS），标准 kubeadm 的控制面（kube-apiserver、etcd、controller-manager、scheduler）会再占约 1.5-2GB，容易触发 OOM。
- 方案：选择 k3s 单节点（内置 SQLite、默认 Traefik、组件裁剪），计划关闭 Traefik 以释放端口与内存；镜像走本地 `registry:2`，`imagePullPolicy: IfNotPresent`；k3s 安装安排在 M4 压测之后并先打 VM 快照。
- 数据/证据：无实测数据（截至当前尚未实装 k3s）；仅有纸面内存预算与前置条件清单。
- 论文可用角度：系统部署章节——把“资源受限环境下的发行版选型”写成约束驱动的决策，而不是“k3s 更轻”这种结论式表述。
- 证据来源：DEVLOG 二、部署形态决策；`docs/ops/k3s单节点搭建手册.md`；DEVLOG 三、M4 前的前置条件章节。

### K10 离线镜像交付链路

- 问题/背景：公司集群不能访问外网镜像仓库，且跨机传输大镜像容易因磁盘抖动损坏。
- 方案：`images.env` 统一版本与仓库前缀；`build/save/load/push` 四脚本，强制 `--platform linux/amd64`、禁止 `latest` tag、把 JRE 与 nginx 基础镜像一并打入 tar；tar 生成后计算 sha256，落地端先校验再 `load`；后端 Dockerfile 参数化 `JAR_FILE`，前端多阶段构建（node 编译 → nginx 托管）。
- 数据/证据：`ticket-push` 单服务实测 build → save（122MB，镜像 333MB）→ sha256 校验 → load → tag → push 全链路通过；镜像构建耗时 21s，save 12.5s。
- 论文可用角度：系统部署章节——论证“构建在联网 VM、运行在离线集群”的产物交付模型，并给出完整性校验闭环。
- 证据来源：DEVLOG 三、离线镜像交付链路（`08a443d`）；`scripts/` 四脚本；`docs/ops/镜像离线交付手册.md`。

### K11 监控组件瘦身与资源预算

- 问题/背景：完整 Prometheus + Grafana 栈在 16GB 虚拟机上会挤占业务与中间件内存，而毕设只需要证明“可观测”而非生产级监控。
- 方案：仅保留 Spring Boot Actuator 的 `health,info` 端点作为存活探针，指标通过自建埋点表与脚本统计，不部署 Prometheus/Grafana；资源预算优先保障 Milvus（1536M）与 MySQL。
- 数据/证据：无实测数据（未做监控栈资源对比）；Actuator 端点在各服务可用。
- 论文可用角度：系统部署章节——说明“可观测性最小闭环”的取舍，避免被质疑缺少监控时无法自洽。
- 证据来源：DEVLOG 二、监控瘦身决策；各服务 `application.yml` 的 `management.endpoints.web.exposure.include`。

## 二、认证、注册与租户

### K12 Sa-Token + Redis 共享会话 + 网关统一 401

- 问题/背景：网关与业务服务是不同进程，若会话只存在 JVM 内存，网关鉴权结果无法被下游复用，且多实例部署会丢会话。
- 方案：Sa-Token 会话统一存 Redis，网关与 `ticket-system` 共用同一 Redis 与同一 `token-name: Authorization`；token 为 UUID、有效期 30 天、`is-share: true`（同一账号多端共享）；网关 `SaReactorFilter` 对全路径拦截，白名单放行 `/api/auth/login`、`/api/auth/register`、`/api/auth/code`、ping 与 `/ws/**`；鉴权失败统一写 HTTP 401 + `{"code":10401,"message":"未登录或凭证失效"}`。
- 数据/证据：E2E 验证“登录拿 token → 带 token 访问 → 登出后旧 token 失效”；未登录请求 401 且响应体为统一 `Result`；网关重启后会话仍有效（Redis 持久化）。
- 论文可用角度：系统设计章节——说明“认证集中、会话共享”的边界，配一张“浏览器—网关—Redis—业务服务”时序图。
- 证据来源：DEVLOG 三、M1 第一阶段（`ff4fc68`）；`ticket-gateway/.../SaTokenConfigure.java`、`application.yml`。

### K13 网关租户头剥离与回填

- 问题/背景：若直接信任客户端传入的 `X-Tenant-Id`，攻击者改一个请求头即可越权读取其他租户数据。
- 方案：网关先删除客户端自带的 `X-Tenant-Id`，再根据已认证会话中的租户信息回填；同时删除客户端伪造的 `X-Forwarded-For`，由网关重新追加真实客户端 IP（这是按 IP 做登录防爆破的前提）。下游 `TenantContext` 仍保留“会话优先”的兜底顺序。
- 数据/证据：E2E 验证伪造 `X-Tenant-Id` 不生效，仍按会话租户查询；按 IP 计数在代理场景下不串。
- 论文可用角度：安全设计章节——作为“零信任边界”的落地细节：头部不可信、身份由网关重写。
- 证据来源：DEVLOG 三、M2 批一（`99d11e8`）；`ticket-gateway/.../TenantHeaderFilter.java`、`application.yml` 的 `RemoveRequestHeader`。

### K14 注册校验与唯一约束

- 问题/背景：开放注册接口是滥用与脏数据的主要入口，仅靠前端校验可被直接绕过。
- 方案：服务端校验手机号格式与验证码；`(tenant_id, phone)`、`(tenant_id, email)`、`(tenant_id, username)` 三组唯一键兜底并发重复注册；注册成功后按 `role_code = USER` 查角色并绑定，避免客户端指定角色；默认租户为 1。
- 数据/证据：E2E 验证重复手机号/邮箱返回明确业务错误，验证码错误不落库；并发重复注册由唯一键拦截。
- 论文可用角度：详细设计章节——说明“校验前置 + 数据库约束兜底”的双层防御。
- 证据来源：DEVLOG 三、M1 第二阶段（`828f15f`）；`ticket-system/.../service/RegisterService.java`；`sql/init.sql` 唯一键。

### K15 邮箱验证码四重约束

- 问题/背景：验证码接口若不限制，会被当作免费邮件/短信网关刷取，且验证码可被暴力枚举。
- 方案：①有效期 5 分钟；②同一邮箱 60 秒内只能发一次；③同一邮箱每日最多 10 次；④校验失败累计 5 次即作废当前验证码（失败计数 key 保留 5 分钟）。验证码使用后立即删除，保证一次性。发送端提供 `mock` 与 `smtp` 双实现，真实授权码存于 `~/secrets/smtp_auth`（600 权限，不入 Git）。
- 数据/证据：E2E 验证 60 秒频控、每日上限、错误 5 次后正确验证码也失效；M1—M4 阶段使用 mock 发信，真实 SMTP 发信未实测。
- 论文可用角度：安全设计章节——把“频控、时效、一次性、试错上限”作为验证码四个正交约束来写。
- 证据来源：DEVLOG 三、M1 第二阶段与 M2 批一；`RegisterService.java`；`VerificationCodeSender` 双实现。

### K16 密码策略与 BCrypt

- 问题/背景：明文或弱哈希存储密码不可接受；自研加密容易踩盐值与迭代次数的坑。
- 方案：密码长度 8–64，必须同时包含大写、小写、数字、特殊字符；使用 Spring Security Crypto 的 `BCryptPasswordEncoder` 做哈希，数据库只存哈希值；登录时统一走 `matches()`，不区分“用户不存在/密码错误”的提示。
- 数据/证据：E2E 验证弱密码被拒、正确密码可登录、错误密码返回统一凭证错误；数据库中无明文密码。
- 论文可用角度：安全设计章节——说明为何选 BCrypt（自适应成本、内置盐）而不是 MD5/SHA。
- 证据来源：DEVLOG 三、M1 第二阶段（`828f15f`）；`RegisterService.java`、`AuthService.java`；父 POM 依赖。

### K17 登录防爆破双维度

- 问题/背景：只按用户名锁定会被“换账号撞库”绕过，只按 IP 锁定会误伤 NAT 后的正常用户。
- 方案：双维度计数——同一用户名 15 分钟窗口内失败 5 次，锁定 15 分钟；同一 IP 10 分钟窗口内失败 10 次，封禁 30 分钟；锁定期间直接返回 `10412`，不再校验密码；登录成功后清空用户名维度计数。阈值均可在 `application.yml` 配置。
- 数据/证据：E2E 验证第 6 次登录返回 10412；IP 维度在代理头被剥离后可正确识别真实来源。
- 论文可用角度：安全设计章节——用“双维度 + 可配置阈值”说明对撞库与误伤的平衡；可补一张失败计数状态图。
- 证据来源：DEVLOG 三、M2 批一（`99d11e8`）；`ticket-system/.../service/AuthService.java`、`application.yml`。
- 差异提示：DEVLOG M1 曾记“失败 ≥5 锁 5 分钟”，最终代码为用户名锁 15 分钟，见附录 A。

## 三、工单业务与事件链路

### K18 状态迁移乐观锁 version

- 问题/背景：两名处理人同时点击“开始处理”，若无并发控制，后写者会覆盖前者的状态与处理人，流转日志也会出现两条互相矛盾的记录。
- 方案：`wo_ticket` 增加 `version` 字段，迁移时以“读取到的 version”作为更新条件（`UPDATE ... WHERE id=? AND version=?`），更新影响行数为 0 时返回 `20402`（并发冲突，请刷新重试）；状态机校验与版本更新在同一次事务内完成，成功后才写流转日志。
- 数据/证据：并发迁移 E2E 验证仅一条成功，另一条返回 20402；37/37 状态机断言不受影响。
- 论文可用角度：详细设计章节——说明“业务状态机 + 数据库乐观锁”的组合，对比悲观锁在低冲突场景下的吞吐劣势。
- 证据来源：DEVLOG 三、M4 批一（`9295659`）；`TicketStateMachine.java`、`TicketService.java`；`sql/init.sql` 的 `version` 列。

### K19 RabbitMQ 事件链路：afterCommit + confirm + DLX

- 问题/背景：工单创建后要通知推送服务，若在事务提交前发消息，可能出现“消息已发、事务回滚”的幽灵事件；若消息丢失，实时卡片与统计都会缺失。
- 方案：①事件在 `afterCommit` 回调中发布，保证只有落库成功才发消息；②生产者开启 `publisher-confirm` 与 `mandatory`，记录确认与退回；③拓扑为 topic exchange `tims.ticket.event`（durable），路由键 `ticket.created` / `ticket.closed`，队列 `q.push.ticket` 绑定 `ticket.#`；④消费失败重试 3 次后投递死信 `tims.ticket.dlx` → `q.push.ticket.dead`，`requeue=false` 避免毒消息循环。
- 数据/证据：E2E 验证创建/关闭事件各产生 1 条消息、消费端 `consumers=16`；事件发布到消费扇出延迟 5–11ms；死信队列可观察到重试耗尽消息。
- 论文可用角度：系统设计章节——按“事务一致性—投递可靠性—消费幂等”三段论证，配一张 exchange/queue/DLX 拓扑图。
- 证据来源：DEVLOG 三、M4 批一（`9295659`）；`EventPublisher.java`、`RabbitConfig`、`ticket-push` 消费配置。

### K20 事件投递三级降级

- 问题/背景：RabbitMQ 是单点，若 Broker 宕机或网络中断，工单事件不能直接丢失，否则实时推送与统计断链。
- 方案：第一级 RabbitMQ；第二级 HTTP 直推 `ticket-push` 内部接口（携带 `X-Internal-Token`，绕过网关鉴权）；第三级写 Redis List `tims:event:stream` 暂存，由 `FallbackStreamScanner` 每 10 秒补投。三级都失败时只记录错误日志，不影响工单主流程。
- 数据/证据：停掉 RabbitMQ 容器后，30 条工单仍全部产生卡片（`degraded=3`，30/30），P50 1656ms、P95 2193ms；恢复 Broker 后无重复卡片（消费端按事件 ID 去重）。
- 论文可用角度：可靠性设计章节——说明“主链路可用性优先于消息绝对有序”，并给出各降级档的代价。
- 证据来源：DEVLOG 三、M4 批一与 M4 批二；`EventPublisher.java`、`FallbackStreamScanner.java`。

### K21 四时间戳埋点与 P50/P95/P99 统计

- 问题/背景：只看接口总耗时无法判断瓶颈在消息投递、检索还是推送；仅看平均值会被长尾掩盖。
- 方案：在工单创建、事件发布、消息消费、卡片推送四个节点写入时间戳，落 `wo_ticket_event`（或等价埋点表）；脚本按“创建→消费→推送”计算分段耗时与端到端耗时，输出 P50/P95/P99、样本数、降级分布。
- 数据/证据：200 条样本的端到端 P50 356ms、P95 507ms、P99 687ms；分段均值“创建 373ms、消费→推送 361ms”，据此定位消费并发瓶颈。
- 论文可用角度：性能测试章节——把“埋点分段”写成定位方法，而不是只报一个总数。
- 证据来源：DEVLOG 三、M4 批一/批二；`scripts/m4_stress.py`；`wo_ticket_event` 表。

## 四、知识库与混合检索

### K22 Milvus 集合结构与 HNSW 参数

- 问题/背景：知识检索需要按租户与设备类型过滤后再做向量相似度搜索，若先全库检索再过滤，会浪费算力并引入跨租户数据。
- 方案：集合 `kb_knowledge` 字段包含 `id`(主键)、`tenant_id`、`apply_device_type`、`title`、`content`、`vector`(FLOAT_VECTOR, dim=1024)；索引类型 HNSW，`M=8`、`efConstruction=64`，检索 `ef=64`，度量 `COSINE`；查询表达式先做 `tenant_id == ?`（可选叠加 `apply_device_type == ?`）再 `topK`，实现前置过滤。
- 数据/证据：53 条知识全部入集合并可检索；发布后约 2s 可命中；相同主题 cosine 0.77、不相关 0.65（该指标区分度有限，见待补证据）。
- 论文可用角度：详细设计/关键算法章节——说明“前置过滤 vs 后置过滤”的差异，给出 HNSW 三个参数的含义与取值理由。
- 证据来源：DEVLOG 三、M3 批 B（`7714233`）；`MilvusVectorStore.java`。
- 差异提示：DEVLOG 只写“HNSW/COSINE”，未记参数；参数以代码为准。

### K23 增量向量同步任务

- 问题/背景：知识发布后必须尽快可检索，但全量重建向量成本高，且智谱接口有速率与失败风险。
- 方案：定时任务每 10 秒扫描 `status=PUBLISHED AND vector_synced_at IS NULL`（含失败重试），每次取 16 条，拼接 `title + summary + content` 后截断 4000 字符，批量调用 embedding；写入 Milvus 采用“按主键删除→插入→flush”，成功后回写 `vector_synced_at`；失败记录错误但不阻塞后续批次。
- 数据/证据：50 条种子知识 + 3 条 E2E 知识共 53 条全部同步；发布到可检索实测约 2 秒；单批 16 条为经验值，未做吞吐基准。
- 论文可用角度：详细设计章节——说明“最终一致”的同步模型与幂等写入策略，配一张状态流转图（草稿→待审→发布→已同步）。
- 证据来源：DEVLOG 三、M3 批 B；`VectorSyncService.java`、`EmbeddingService.java`。

### K24 向量/关键词/混合三模式检索

- 问题/背景：纯向量对型号、编号等精确词不敏感；纯关键词对同义表达召回差；需要可切换、可对比的检索入口。
- 方案：`SearchController` 暴露 `mode=VECTOR|KEYWORD|HYBRID`。VECTOR 走 Milvus Top10；KEYWORD 走 MySQL FULLTEXT Top10；HYBRID 取两路 Top10 做 RRF 融合后重排。`k` 默认 5、上限 20。Milvus 不可用时 VECTOR/HYBRID 自动降级为关键词并标记 `fallback=true`。
- 数据/证据：三模式 E2E 均返回结果；HYBRID 分值约 0.05 量级；关键词模式 `ft_score` 实测 0.8837（“贴片机 抛料”）、0.8834（“回流焊 虚焊”）。
- 论文可用角度：关键算法章节——三种模式的对照实验设计，说明为什么最终选 HYBRID 作为默认。
- 证据来源：DEVLOG 三、M3 批 C（`80ac406`）；`SearchService.java`、`SearchController.java`。

### K25 RRF(k=60) 融合与业务加权 1.5/1.2

- 问题/背景：向量分（cosine）与全文分（`ft_score`）量纲不同，直接加权需要归一化，且归一化参数随语料漂移；业务上又希望“设备类型匹配”“标签命中”优先。
- 方案：采用 Reciprocal Rank Fusion，只用排名不用原始分：`rrf(d) = Σ 1/(k + rank_i(d))`，`k=60`；两路各取 Top10；融合后如查询文本包含知识条目的 `applyDeviceType` 则 ×1.5，包含任一 `tags` 则 ×1.2（可叠加为 1.8）；按最终分降序取 TopK。
- 数据/证据：可反推的分值示例见下表（同一 query，向量榜 A 第 1、B 第 3；关键词榜 B 第 2、A 第 6）：

  | 文档 | 向量项 | 关键词项 | RRF 基础分 | 设备类型 ×1.5 | 标签 ×1.2 | 两者叠加 ×1.8 |
  | --- | --- | --- | --- | --- | --- | --- |
  | A | 1/61=0.016393 | 1/66=0.015152 | 0.031545 | 0.047318 | 0.037854 | 0.056781 |
  | B | 1/63=0.015873 | 1/62=0.016129 | 0.032002 | 0.048003 | 0.038402 | 0.057604 |

  可见基础分 B 略高，但 A 命中设备类型后反超，说明加权可在排名接近时改变结果；实测 HYBRID 返回分约 0.05，量级与表一致。
- 论文可用角度：关键算法章节——RRF 的无量纲特性、k 值对头部集中度的影响、业务加权与纯相关性排序的权衡；可直接用上表作为“可解释性”例证。
- 证据来源：`SearchService.java`（`RRF_K=60`、`DEVICE_BOOST=1.5`、`TAG_BOOST=1.2`、`CANDIDATE_K=10`）；DEVLOG 三、M3 批 C。

### K26 FULLTEXT ngram 与 MyBatis-Plus 例外

- 问题/背景：MySQL 默认分词器不支持中文，`MATCH` 对中文短语召回很差；同时项目约定 Mapper 全部使用 MyBatis-Plus 注解、禁用 XML。
- 方案：`kb_knowledge` 建 `FULLTEXT KEY ft_title_content (title, content) WITH PARSER ngram`；`wo_ticket` 建 `ft_title_desc (title, description)`；查询使用 `MATCH(k.title, k.content) AGAINST(#{kw} IN NATURAL LANGUAGE MODE)`，并以 `AND MATCH(...) > 0` 过滤零相关；该 SQL 以 `@Select` 注解写在 `KbKnowledgeMapper` 中，作为“禁 XML”的唯一书面例外，理由注释写在类头。
- 数据/证据：`ft_score` 实测 0.8837/0.8834；中文短语可命中；ngram 对单字查询不友好（需至少 2 字），已在检索提示中规避。
- 论文可用角度：关键算法/详细设计章节——说明中文全文检索的三种可选方案（ngram、外部分词、向量），以及为何在不引入 ES 的前提下选 ngram。
- 证据来源：`sql/init.sql`（`WITH PARSER ngram`）；`KbKnowledgeMapper.java`；DEVLOG 三、M3 批 C。
- 差异提示：DEVLOG 某处写“BOOLEAN MODE”，代码为 `NATURAL LANGUAGE MODE`，以代码为准。

### K27 智谱 embedding 客户端参数与容错

- 问题/背景：外部 embedding 接口存在超时、限流与返回结构变化风险，直接串在检索主链路会放大故障。
- 方案：模型 `embedding-3`，输出 1024 维；连接超时 5s、读超时 30s；批量上限按 16 条调用；输入截断 4000 字符；密钥只从 `~/secrets/zhipu_api_key` 读取（600 权限），不写入配置与仓库；异常统一包装为业务异常，由同步任务记录并等待下一轮重试。
- 数据/证据：密钥失效期间同步任务持续失败但不影响检索降级；有效期内 53 条知识同步成功；单次 RTT 约 300ms 量级（未做正式基准）。
- 论文可用角度：详细设计章节——把“外部依赖的参数化与失败隔离”写清楚，说明密钥治理。
- 证据来源：DEVLOG 三、M3 批 B/C；`EmbeddingService.java`；`~/secrets/zhipu_api_key`。

### K28 检索侧降级：fallback=true

- 问题/背景：Milvus 是单点容器，一旦宕机，VECTOR/HYBRID 模式会直接 500，知识库页面不可用。
- 方案：检索入口对 Milvus 调用做异常捕获，失败即改用 FULLTEXT 关键词检索，返回体携带 `fallback=true` 与降级原因；`fallback` 不改变 HTTP 状态码，保证前端仍能展示结果与提示条。
- 数据/证据：停 Milvus 后 50/50 次检索全部返回（`degraded=1`），P50 1754ms、P95 2538ms；恢复后 `fallback=false`。
- 论文可用角度：可靠性设计章节——说明“降级不是隐藏故障”，通过响应标记让调用方可感知。
- 证据来源：DEVLOG 三、M3 批 C 与 M4 批二；`SearchService.java`。
- 差异提示：DEVLOG 早期写“Milvus 不可用则纯关键词”，代码另加 `fallback` 标记，二者是演进关系。

### K29 知识审核状态流与 30401

- 问题/背景：知识由处理人沉淀，但不能直接进入检索库，需要审核；审核动作也必须防止非法跳转。
- 方案：状态 `DRAFT → PENDING → PUBLISHED / REJECTED`，`PUBLISHED` 后允许下架回 `DRAFT`；非法迁移返回 `30401`；审核通过时写审核人、审核时间与意见，驳回时必填原因；只有 `PUBLISHED` 才进入向量同步。
- 数据/证据：E2E 覆盖创建→提交→通过→检索命中、驳回→修改→再提交；非法迁移返回 30401；最终 53 条 PUBLISHED。
- 论文可用角度：详细设计章节——与工单状态机对照，说明“业务对象状态机”的复用模式（常量表 + 统一错误码 + 操作日志）。
- 证据来源：DEVLOG 三、M3 批 B；`KnowledgeService.java`；`kb_knowledge.status`。

## 五、实时推送与降级矩阵

### K30 WebSocket 鉴权、在线表与心跳

- 问题/背景：浏览器 WebSocket 无法自定义 Authorization 头；多实例推送需要知道“用户在哪个节点在线”；长连接还需要防止中间设备静默断开。
- 方案：握手 URL 携带 `?token=`，`AuthHandshakeInterceptor` 调 `StpUtil.getLoginIdByToken` 校验并写入用户与租户；连接建立后写 Redis 在线表（key 为用户维度，value 含节点/会话，TTL 30 秒），每 10 秒心跳刷新；断开时删除；连接建立即补推未读数与最近卡片。
- 数据/证据：E2E 验证无 token 拒绝、有效 token 建立、心跳 10s、在线状态 30s 过期；连接后收到 `UNREAD_CARD` 补推。
- 论文可用角度：详细设计章节——说明“token 走 query 而非 Header”的工程原因，以及“在线表 TTL + 心跳”如何避免僵尸连接。
- 证据来源：DEVLOG 三、M4 批二（`d35b9d3`、`ce8dc5a`）；`ticket-push/.../ws/`；`PushInfraConfig.java`。

### K31 前端指数退避重连与离线补推

- 问题/背景：网络抖动或服务重启会导致 WebSocket 断开，若固定 1 秒重连会形成重连风暴。
- 方案：`src/utils/ws.js` 实现指数退避（带最大间隔与抖动），断线后按序重连；重连成功重新拉取未读与最近卡片，保证“断线期间不漏卡片”；页面卸载时主动关闭并清理定时器。
- 数据/证据：浏览器 E2E 验证断言通过：刷新页面重连、列表实时插入新卡片、侧栏卡片数变化、在线指示由灰变绿。
- 论文可用角度：详细设计章节——把“前端容错”纳入系统可靠性，而不是只写后端。
- 证据来源：DEVLOG 三、M4 批二；`ai-tims-front/src/utils/ws.js`、`views/TicketList.vue`。

### K32 推送降级矩阵与空卡片兜底

- 问题/背景：推送链路依赖知识检索、RabbitMQ、WebSocket 三个环节，任一环节故障都应“有结果”，而不是静默失败。
- 方案：用位标记描述降级：`1`=知识库降级（纯关键词）、`2`=MQ 降级（本地线程池直推）、`4`=知识库整体不可用；多个位可叠加（如 `3`=MQ + 知识降级）。知识库完全不可用时仍推送一张“已受理/排队中”的空卡片，卡片带 `degraded` 标记与原因。
- 数据/证据：正常场景 `degraded=0`（200/200）；停 Milvus `degraded=1`（50/50）；停 MQ `degraded=3`（30/30）；全停 `degraded=4`（4/4 空卡片）。
- 论文可用角度：可靠性设计章节——用“位标记 + 降级矩阵”表达多维故障组合，比单一开关更可扩展；可直接画一张 4 行场景表。
- 证据来源：DEVLOG 三、M4 批二；`PushPipeline.java`；`ErrorCode`/前端卡片组件。

### K33 冷启动预热

- 问题/背景：`ticket-push` 首次消费时 JIT 未预热、连接池未建立、Milvus 客户端首次建连，首条消息耗时明显高于稳态。
- 方案：应用启动后预热线程池与 HTTP/Milvus 连接，并提前加载常用配置；压测脚本在正式计时前先发送预热流量。
- 数据/证据：首条消息 3s → 预热后 0.87s；4/4 条预热样本均低于 1s。
- 论文可用角度：性能优化章节——说明“冷启动”是测量偏差来源，压测必须先预热，否则 P95 被首条样本污染。
- 证据来源：DEVLOG 三、M4 批一冷启动优化；`PushInfraConfig.java`。

## 六、性能优化

### K34 端到端 P95 4293ms→507ms（并发 1）/943ms（并发 10）

- 问题/背景：M4 首轮压测端到端 P95 为 4293ms，远超任务书 2000ms 指标；且并发升高后进一步劣化。
- 方案：两处改造——①把 `ticket-push` 消费并发从 4-8 提升到 16-32（线程池 4/16/2000 + `CallerRunsPolicy`）；②把 Milvus gRPC 的连接超时与调用超时分离为 connect 3s / rpc 1s，消除“重建信道→超时→再重建”的死循环；同时对知识检索失败做 1s 快速失败。
- 数据/证据：200 条工单压测结果如下（`degraded` 为降级次数）：

  | 场景 | 并发 | 样本 | P50(ms) | P95(ms) | P99(ms) | 创建均值(ms) | 消费→推送均值(ms) | 降级数 |
  | --- | --- | --- | --- | --- | --- | --- | --- | --- |
  | 正常·顺序 | 1 | 200 | 356 | 507 | 687 | 373 | 361 | 0 |
  | 正常·并发 | 10 | 200 | 488 | 943 | 1212 | 539 | 521 | 0 |
  | 停 Milvus | 5 | 50 | 1754 | 2538 | 3130 | 1821 | 1812 | 50 |
  | 停 RabbitMQ | 5 | 30 | 1656 | 2193 | 2233 | 1710 | 268 | 30 |

  优化前后：P95 4293ms → 507ms（并发 1，降幅 88.2%）；并发 10 时 943ms（相对单并发上升 1.86 倍，仍在 2000ms 内）。
- 论文可用角度：性能测试章节——先给基线、再给两次改造、最后给四场景矩阵，形成“发现问题—定位—优化—回归”的闭环。
- 证据来源：DEVLOG 三、M4 批二（`d35b9d3`）；`scripts/m4_stress.py`；`PushInfraConfig.java`；`MilvusVectorStore.java`。
- 差异提示：DEVLOG 中 gRPC 超时先后出现 10s、1s/1s 等口径，最终代码为 3s/1s，见附录 A。

### K35 消费并发 4-8 → 16-32

- 问题/背景：单条消息处理包含“检索 + 组卡 + 推送”三段，均为 I/O 等待；并发过低时消息在队列中排队，端到端 P95 被拉长。
- 方案：`@RabbitListener` 的 `concurrency` 提到 16、`max-concurrency` 到 32；本地线程池核心 4、最大 16、队列 2000，拒绝策略 `CallerRunsPolicy`（在 MQ 降级直推时提供背压，避免丢任务）。
- 数据/证据：分段均值“消费→推送”从 2429ms 降至 361ms（同一批 200 条口径）；MQ 扇出 5–11ms，说明瓶颈在消费端而非 Broker。
- 论文可用角度：性能优化章节——用“分段耗时 + 队列扇出”证明扩容消费并发是有效手段，而不是盲目加机器。
- 证据来源：DEVLOG 三、M4 批二；`ticket-push/.../config/PushInfraConfig.java`、消费监听器配置。

### K36 Milvus gRPC 连接/调用超时分离

- 问题/背景：Milvus Java SDK 缓存的 gRPC 通道默认没有 RPC deadline。对端宕机时线程会长时间阻塞；若把连接超时也设得很短，会出现“建连失败→销毁通道→立即重连”的抖动循环。
- 方案：`ConnectParam` 连接超时 3s；每次 `search/insert/delete` 使用 `withRpcDeadline(1s)`（调用级 deadline）；通道复用，不因单次调用超时重建；异常统一转业务异常，交给检索降级。
- 数据/证据：改造前 Milvus 停机场景请求堆积至 4293ms P95；改造后停 Milvus P95 2538ms，且 50/50 全部降级成功；恢复后无残留损坏通道。
- 论文可用角度：性能优化/开发难点章节——解释“超时不是越小越好”，连接与调用需要分级；这是典型的分布式依赖治理案例。
- 证据来源：DEVLOG 三、M4 批二；`MilvusVectorStore.java`（`withConnectTimeout(3s)`、`withRpcDeadline(1s)`）。

### K37 降级快速失败（1s 预算）

- 问题/背景：知识库故障时，如果仍等待默认长超时，推送链路会被拖到秒级，失去降级意义。
- 方案：检索调用设置 1s 调用预算，超时即走关键词；关键词也失败则返回空结果并置 `degraded` 位；推送侧不因检索失败而失败。
- 数据/证据：停 Milvus 场景 50 条全部在 1s 预算内切换，P95 2538ms（含创建与推送开销），无 500；未发生“等待 10s 后超时”。
- 论文可用角度：可靠性设计章节——把“快速失败”作为降级策略的一部分，与熔断区分：这里是单次调用预算，不是状态机熔断。
- 证据来源：DEVLOG 三、M4 批二；`SearchService.java`。

### K38 分段埋点定位瓶颈

- 问题/背景：端到端 P95 高并不代表所有环节都慢；若无分段数据，容易误判为“数据库慢”或“Milvus 慢”。
- 方案：按“创建接口返回—事件发布—消息消费—卡片推送”四段记录时间戳，脚本分别统计；先看均值定位大段，再看 P95 找长尾。
- 数据/证据：优化前“创建 373ms、消费→推送 2429ms”，直接指向消费段；优化后消费段 361ms，端到端 P95 达标。
- 论文可用角度：性能测试章节——作为“测量方法”而非结论，说明如何避免拍脑袋优化。
- 证据来源：DEVLOG 三、M4 批一/批二；`scripts/m4_stress.py`。

### K40 Maven 增量编译不感知 POM 变更

- 数据/证据：`clean` 后问题消失；增量构建耗时 22s，clean 构建可接受。

### K41 GitHub Actions CI 流水线

- 问题/背景：本地构建通过不代表远端可复现；需要每次 push 自动验证全模块编译。

### K42 本地镜像仓库与 tag 规则

- 论文可用角度：系统部署章节——说明“内网 registry + 显式版本”如何保证可复现部署。
- 证据来源：DEVLOG 三、P0 收尾（`a18b6f9`）；`docker/docker-compose.yml`；`scripts/`。

### K43 VM 资源约束下的容量规划

- 问题/背景：物理机 i7-7700（4C8T/32GB）上的虚拟机若按 8 vCPU 分配会造成 CPU 时间片争抢，压测数据不可信。

- 论文可用角度：性能测试章节——交代测试环境与资源边界，避免“实验室数据不可复现”的质疑。
- 证据来源：DEVLOG 二、环境与容量决策；`docker/docker-compose.yml`。

## 八、开发难点（深坑实录）

### K45 Jackson 嵌套对象反序列化致 500

- 症状：调用智谱接口返回后解析失败，接口 500，日志提示 `Cannot deserialize value of type ... from Object value`。
- 根因：响应中 `usage` 等字段既可能是对象也可能是字符串/空值，直接用强类型 DTO 承接，遇类型漂移即失败。
- 修法：把易漂移字段改为 `JsonNode` 或 `Object` 承接，业务只取 `data.embedding`；对 `error` 结构单独建模；异常转为业务异常并记录原始响应片段。
- 论文可用角度：开发难点章节——外部 API 契约不稳定时的防御式反序列化。
- 证据来源：DEVLOG 三、M3 踩坑；`EmbeddingService.java`。

### K46 Milvus SDK `getRowRecords` 字段匹配异常

- 症状：按主键查询已插入实体时抛出 `key not found`，但数据确实存在。
- 根因：SDK 2.4.4 的 `getRowRecords` 依赖 `outFields` 名称与集合 schema 完全匹配，字段顺序/别名不一致时内部映射失败。
- 修法：改用 `search` + `getIDScore()` 获取主键与分数，绕开行记录映射；写入侧统一字段名常量，避免别名。
- 论文可用角度：开发难点章节——第三方 SDK 版本缺陷的规避与最小复现。
- 证据来源：DEVLOG 三、M3 踩坑；`MilvusVectorStore.java`。

### K47 gRPC 通道无超时导致长阻塞

- 症状：Milvus 容器停止后，检索线程成批卡住，接口 P95 飙升，甚至线程池耗尽。
- 根因：SDK 缓存的 gRPC 通道默认无 deadline；首次失败后重建通道又会立即重试，形成抖动循环。
- 修法：连接超时 3s + 调用级 1s deadline；通道复用；失败快速降级（详见 K36）。
- 论文可用角度：开发难点章节——远程调用必须显式设置 deadline，不能依赖 SDK 默认值。
- 证据来源：DEVLOG 三、M4 踩坑；`MilvusVectorStore.java`。

### K48 Nacos 3 默认开启鉴权导致注册失败

- 症状：服务启动日志报 403/未授权，Nacos 服务列表看不到实例。
- 根因：Nacos 3.x 默认开启鉴权，未配置 `NACOS_AUTH_TOKEN` 与 identity 信息时客户端无法注册。
- 修法：Compose 中显式设置 `NACOS_AUTH_TOKEN`（Base64、≥32 字节）、`NACOS_AUTH_IDENTITY_KEY/VALUE`，服务端与客户端配置一致；token 走环境变量，不硬编码。
- 论文可用角度：开发难点章节——中间件默认安全策略变化对启动链路的影响。
- 证据来源：DEVLOG 三、M1 踩坑；`docker/docker-compose.yml`。

### K49 Spring Cloud LoadBalancer 缺失致 `lb://` 503

- 症状：网关路由配置正确，但访问 `/api/order/**` 返回 503，日志提示无可用实例。
- 根因：Spring Cloud 2025.0 将负载均衡实现拆分，仅引入 `nacos-discovery` 时缺少 `spring-cloud-starter-loadbalancer`，`lb://` 无法解析。
- 修法：网关 POM 增加 `spring-cloud-starter-loadbalancer`；确认 `ReactorServiceInstanceLoadBalancer` 在类路径。
- 论文可用角度：开发难点章节——BOM 拆分导致的“依赖缺失型”故障。
- 证据来源：DEVLOG 三、M1 踩坑；`ticket-gateway/pom.xml`。

### K50 scp/跨机传输尾部字节丢失

- 症状：跨机拷贝后的 jar/源码尾部若干字节缺失，构建报“zip END header not found”或源码语法错误；本地重试又正常。
- 根因：VM 虚拟磁盘 I/O 抖动叠加 Windows 侧安全软件扫描，写入尾部可能未落盘；非确定性，难复现。
- 修法：跨机传输统一 `tar + md5`（或 sha256）校验，落地端校验一致后再使用；大改动前打 VM 快照；构建产物损坏时 `mvn clean package` 重建并比对 md5。
- 论文可用角度：开发难点章节——把“环境不可靠”作为实验可复现性的一部分，说明校验闭环。
- 证据来源：DEVLOG 四、问题与解决（磁盘抖动条目）；`08a443d` 的 sha256 校验。

### K51 PS5 → ssh 引号剥离

- 症状：在 PowerShell 5 中执行 `ssh vm "mysql -e \"...\""`，远端收到的 SQL 被截断或引号丢失，命令行为与预期不符。
- 根因：PS5 对多层引号的转义规则与 bash 不同，参数在本地就被拆分，远端只收到片段。
- 修法：复杂远端命令改用 `bash -s` + stdin heredoc，或先写脚本再 `scp` 执行；避免三层以上引号嵌套。
- 论文可用角度：开发难点/附录——跨平台脚本的可移植性。
- 证据来源：DEVLOG 四、调试经验。

### K52 docker-proxy 残留导致端口仍被占用

- 症状：容器已 `docker stop`，`ss` 仍显示端口被监听，服务无法重新绑定。
- 根因：Docker 的 `docker-proxy` 进程随容器停止存在延迟；此外旧版 Tomcat 可能仍占用端口。
- 修法：确认 `docker ps` 无容器后，等待 proxy 退出或重启 Docker 服务；用 `ss -lntp` 找到真实 PID 再处理；禁止直接 `kill -9` 关键进程。
- 论文可用角度：开发难点/附录——端口冲突的排查顺序。
- 证据来源：DEVLOG 三、M1 踩坑；四、系统状态检查。

### K53 国内镜像源对 milvusdb 镜像 403

- 症状：`docker pull milvusdb/milvus` 从 daocloud 源返回 403，Compose 启动失败。
- 根因：部分加速源对特定命名空间做访问限制。
- 修法：`milvus/minio` 改走 `1ms.run` 源，`etcd` 改走 quay 官方源；Compose 中固定镜像 tag；拉取后 `docker tag` 统一成本地仓库地址。
- 论文可用角度：开发难点章节——离线/受限网络下的镜像获取策略。
- 证据来源：DEVLOG 三、M3 踩坑；`docker/docker-compose.yml`。

### K54 MySQL 不支持 `ADD COLUMN IF NOT EXISTS`

- 症状：`init.sql` 重复执行时报列已存在，无法做到“一键重建/幂等升级”。
- 根因：MySQL 8.0 不支持该语法（MariaDB 支持），条件 DDL 需借助存储过程或先查 `information_schema`。
- 修法：`init.sql` 采用 `DROP TABLE IF EXISTS` + 全量重建，保证一键可重建；增量升级单独维护迁移脚本，不用条件 DDL。
- 论文可用角度：开发难点章节——数据库初始化脚本的幂等设计。
- 证据来源：DEVLOG 三、M2 踩坑；`sql/init.sql`。

### K55 Java `Map.of` 键值对上限 10

- 症状：编译报“cannot find symbol / too many arguments”，定位到 `Map.of(...)` 处。
- 根因：`Map.of` 只有 10 对参数的重载，超过即无匹配方法。
- 修法：改用 `Map.ofEntries(Map.entry(...), ...)`；或直接构造 `HashMap`。
- 论文可用角度：开发难点/附录——API 设计边界导致的编译错误。
- 证据来源：DEVLOG 三、M2 踩坑；`TicketService.java` 等。

### K56 草稿工单 `ticket_no` 非空约束冲突

- 症状：保存草稿时插入失败，提示 `ticket_no` 不能为 NULL。
- 根因：表设计把 `ticket_no` 设为 `NOT NULL`，但草稿阶段尚未取号。
- 修法：草稿阶段先生成临时号（或允许 NULL 并加唯一键的部分索引语义），提交时再取正式号；`init.sql` 注释说明该字段生命周期。
- 论文可用角度：开发难点章节——业务生命周期与数据库约束的错配。
- 证据来源：DEVLOG 三、M2 踩坑；`sql/init.sql`、`TicketService.java`。

### K57 网关可执行 jar 传输损坏

- 症状：网关 jar 在 VM 上启动报 `Invalid or corrupt jarfile`，本机同 jar 可运行。
- 根因：跨机传输末尾字节丢失（同 K50），且 fat jar 体积大更易触发。
- 修法：重新打包并 `md5sum` 比对；用 tar 传输；保留上一版本 jar 以便快速回滚。
- 论文可用角度：开发难点/附录——部署产物的完整性校验。
- 证据来源：DEVLOG 四、问题与解决。

### K58 公共模块扫描范围与 WebMVC 冲突

- 症状：网关启动失败，提示 `Spring MVC found on classpath, which is incompatible with Spring Cloud Gateway`；或公共模块 Bean 未被扫描到。
- 根因：网关是 WebFlux 技术栈，类路径混入 `spring-boot-starter-web` 即冲突；`@ComponentScan` 默认只扫启动类所在包，公共模块包不在其下。
- 修法：网关 POM 排除 `spring-boot-starter-web`；启动类显式 `scanBasePackages = "com.tims"`；公共模块不引入 Web 依赖（只保留 `spring-web`/校验 API）。
- 论文可用角度：开发难点章节——技术栈混用的类路径冲突。
- 证据来源：DEVLOG 三、M0/M1 踩坑；`ticket-gateway/pom.xml`、各 `*Application.java`。

## 九、调试经验合集（操作性踩坑）

> 以下问题偏“操作/环境”而非设计，合并为表格，论文中可作为“开发过程”附录或一节小字描述，不单独展开。

| 编号 | 症状 | 根因 | 修法 |
| --- | --- | --- | --- |
| D01 | Docker Compose 插件不存在 | 只装了 Docker Engine，未装 compose 插件 | 安装 `docker-compose-plugin`，用 `docker compose` 而非 `docker-compose` |
| D02 | `docker build -f` 找不到 Dockerfile | 构建上下文与 `-f` 相对路径基准不同 | 统一在仓库根执行，`-f` 用相对根路径 |
| D03 | Docker 29 无法登录 registry | 新版本默认要求 HTTPS/凭证助手 | 配置 `insecure-registries` 或使用 `--tls-verify=false` 的等价方案 |
| D04 | 容器已停但端口仍监听 | `docker-proxy` 退出延迟 | 等待或重启 Docker 服务，`ss -lntp` 定位 |
| D05 | Python 脚本取 MySQL 报“表不存在” | 连接未指定库名，默认落到 `mysql` 库 | 连接串显式加 `/aitims`，或 SQL 全限定名 |
| D06 | Python `websockets` 9.1 起 `handler(ws)` 报参数错误 | 新版本 handler 签名为 `(ws, path)`/`(ws)` 变化 | 按版本适配签名，或升级到 10+ 并统一封装 |
| D07 | e2e 脚本误报失败 | 断言依赖前一步结果，级联失败被计为多条 | 每个断言独立前置，失败即短路，输出真实原因 |
| D08 | `pkill` 后服务仍存活 | 匹配串过宽/进程名为 java | 用 `ss -lntp` 取 PID 精确 kill；避免 `-9` |
| D09 | MySQL 初始化脚本重复执行报错 | 非幂等 DDL（无 `IF NOT EXISTS`） | 重建策略 + 迁移脚本分离（K54） |
| D10 | 前端请求 401 但控制台无业务码 | 网关返回 401 时未写响应体 | 网关 `SaReactorFilter` 统一写 JSON 体（K12） |
| D11 | 前端 WS 连接 401 | 浏览器无法带 Authorization 头 | 改用 `?token=` 握手（K30） |
| D12 | Nacos 控制台端口访问不到 | 3.x 控制台端口与 8848 分离 | 开放 8849（控制台）与 9848（gRPC），检查安全组 |
