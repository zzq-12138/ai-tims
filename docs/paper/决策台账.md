## 二、决策条目

### DEC-01 行业方向选型：SMT / 精密电子制造

- **决策结论**：保持现状，论文统一定位为「SMT / 精密电子制造设备维保」，不换行业。
- **备选方案**：CNC 机加工 / 汽车维修（OBD）/ IT 运维工单 / 电梯·暖通·电力 / 航空 ATA。
- **决定性数据**：六方向五维评分（可得性 / 字段完整度 / 规模 / 复杂度 / 迁移成本）：SMT **19**、CNC 15、汽车 19、IT 运维 19、电梯暖通 12、航空 18。仓库实测：8 类设备（贴片机 11、AOI 10、涂布 10、贴合 10、蚀刻 10、回流焊 2、MES 2、SPI 1），56 条记录去重后 54 条唯一知识点。同象异因可构造性：贴装偏移（锡膏印刷/贴装/炉温）、蚀刻不均（喷嘴/浓度/温度）、AOI 模糊（对焦/光源/镜头）。
- **为什么不选另一边**：汽车与 IT 运维总分同为 19，但迁移成本仅 1 分——换方向会作废 54 条知识、100 条评测、8 类设备与 M7 八轮消融；且 CNC/电梯/航空的公开数据是振动/电流时序，缺「措施-验证-适用条件」文本字段。
- **论文建议表述**：「本文面向 SMT / 精密电子制造设备维保场景，覆盖贴片、AOI、SPI、回流焊、涂布、贴合、蚀刻与 MES 共 8 类对象。」
- **局限与答辩风险**：总分与汽车/IT 并列，必须用「迁移成本 + 同象异因可构造性」做 tie-break 说明，不能只说「SMT 最好」；`glassId` 等面板命名残留需在论文中清理口径。
- **证据出处**：`docs/paper/研究方向/数据与基线决策_v1.md` §1–§2。

### DEC-02 基线嵌入模型：BGE-M3 与 embedding-3 双报

- **决策结论**：论文主基线写 **BGE-M3（CPU，1024 维）**；现网部署继续用 **embedding-3（API，1024 维）**；两者在同一评测集上同时报告。
- **备选方案**：①只报 BGE-M3；②只报 embedding-3；③换其他开源 embedding。
- **决定性数据**（61 条 PUBLISHED + 100 条 query，同一余弦检索）：BGE-M3 Hit@3 **98.0%**（95% CI 95–100）、Hit@1 97.0%、Recall@5 99.0%、MRR 0.979；embedding-3 Hit@3 **100%**、Hit@1 98.0%、Recall@5 100%、MRR 0.990。McNemar：BGE 独有命中 0、embedding 独有命中 2，**p=0.5 不显著**。分风格 Hit@3：colloquial 93.8% vs 100%、missing 93.3% vs 100%。延迟（4 vCPU CPU-only）：BGE 均值 **203.4ms** / P95 **364.5ms**；embedding-3 均值 **293.1ms** / P95 **379.9ms**。建库：570ms/条 vs 27ms/条（BGE 慢约 21×，但离线一次性）。
- **为什么不选另一边**：只报 embedding-3 会被质疑「为什么不用导师指定的 BGE-M3 / 是否挑模型」，且 API 不可离线复现；只报 BGE-M3 会丢掉现网已建索引与吞吐优势。
- **论文建议表述**：「本文以 BGE-M3 作为可复现的 dense 基线，另以现网 embedding-3 作为部署对照；两者 Hit@3 分别为 98.0% 与 100.0%，McNemar p=0.5，差异不显著。部署选择 embedding-3 基于批量建库吞吐与现网稳定性，而非检索精度显著更优。」
- **局限与答辩风险**：n=54/100，2pp 差异不显著，不能写「embedding-3 更准」；BGE-M3 的 P95 364.5ms 是单并发 CPU 值，与 M7 的 279.7ms（含服务链路、embedding-3）不可跨表直接比较。
- **证据出处**：`docs/paper/评测/_baseline_compare.json`；`scripts/eval/compare_embedding_baseline.py`；`docs/paper/研究方向/数据与基线决策_v1.md` §5。

### DEC-03 去重阈值：0.85 召回档 vs 0.92 生产档

- **决策结论**：论文「基线」写 **0.85**（候选生成/召回档）；系统配置用 **0.92 + 人工确认**（生产/精度档）。二者是不同层面口径，不矛盾。
- **备选方案**：①统一 0.85；②统一 0.92 无人工确认；③0.75 松阈值。
- **决定性数据**：现有 `ai_extracted` 256 条有分数样本中，3 条 MERGE 全部在 **0.9385**（同标题 MES 重复），0.92–0.98 共 3 条，**0.85–0.92 为 0 条**，<0.85 共 253 条 → 两档在真实日志上无行为差异。成对相似度（56 条有效记录）：BGE-M3 在 ≥0.92 有 2 对且全为同标题真重复；0.85–0.92 有 **12 对**，逐对判读**可直接合并 0 对**（6 对因果/变体、6 对不同故障或跨设备）。embedding-3 ≥0.92 有 3 对，其中 **0.9262 为假合并反例**（贴片机贴装偏移 vs 锡膏印刷偏移）；0.85–0.92 有 **46 对**。漏合并：两档均覆盖 2 组真重复，**漏合并 0**。
- **为什么不选另一边**：统一 0.85 会引入 12/46 对候选且 0 对可合并，纯增人工负担；统一 0.92 无人工确认会出现 0.9262 这类假合并直接入库。
- **论文建议表述**：「0.85 为文献基线的候选生成阈值（召回优先），0.92 为生产入库阈值（精度优先，所有 MERGE 需人工确认）。两档的敏感性对比见 §x：0.85 额外引入 12 对候选，人工判读 0 对可直接合并。」
- **局限与答辩风险**：12/46 对的「可合并」为单人语义判读，非双人独立标注；样本仅 56 条，扩库后需重算；不得把 0.85 说成「系统阈值」。
- **证据出处**：`docs/paper/评测/_baseline_compare.json`（`dedup_similarity`）；`docs/paper/研究方向/数据与基线决策_v1.md` §5.4；DEVLOG 人工合并实测（MERGE 0.9385）。

### DEC-04 数据规模方案：知识点 54→310、评测集 100→250

- **决策结论**：知识点扩到 **310**（10 类设备 × 31 主题），评测集扩到 **250**（100 正例 + 150 负例四类）；先补内容结构再扩容。
- **备选方案**：①维持 54 条只用 100 评测；②纯合成一次性扩到 500+；③换行业拿外部数据。
- **决定性数据**：现有 56 条字段覆盖：现象 53/56、原因 50/56、步骤 53/56、预防 52/56、**验证/复测 1/56、适用条件 0/56**；平均 150.2 字（58–326）。评测集 100 条 = formal 54 / colloquial 16 / noisy 15 / missing 15。负例分层：N1 跨设备同象异因 40、N2 同设备同象异因 40、N3 知识未覆盖 40、N4 信息不足/多故障 30。
- **为什么不选另一边**：54 条撑不起「同象异因」的分层统计（每类不足 3 条无法报 CI）；纯合成会放大模板泄漏、答辩无法解释分布；换行业与 DEC-01 冲突。
- **论文建议表述**：「知识库由现有 54 条种子知识、56 条公开手册锚点、160 条受控合成与 40 条同象异因困难对构成，共 310 条；评测集 250 条，含 100 条正例与 150 条四类负例。」
- **局限与答辩风险**：**没有企业真实工单**，R/P 层也是种子/手册改写，禁止写「真实工单验证」；合成的具体构造与质检规则见配套文档，论文 Limitations 必须写模板泄漏与构造负例偏差。
- **证据出处**：`docs/paper/研究方向/数据与基线决策_v1.md` §1.3、§3。

### DEC-05 检索路由：保留 VECTOR 单路，不宣称加权/RRF 有增益

- **决策结论**：检索默认走 **VECTOR（topK=5）**；HYBRID 作为可用但非最优配置保留；论文明确写「设备加权与 RRF k 无显著增益」。
- **备选方案**：①HYBRID + 设备×1.5 + 标签×1.2 作生产默认；②KEYWORD（低延迟）；③调 RRF k（30/60/100）。
- **决定性数据**（M7 八轮，100 query，61 条知识）：KEYWORD Hit@3 **90.0%**、P95 16.4ms；VECTOR **100.0%**、P95 281.6ms；HYBRID（k=60 无加权）**96.0%**、P95 296.8ms；HYBRID + 设备×1.5 + 标签×1.2（生产配置）**96.0%**、P95 281.5ms；设备加权增量 **0.0pp**、标签加权 **0.0pp**；RRF k=30/60/100 均 **96.0%**，增量 **0.0pp**。最优组合 VECTOR topK=5：Hit@3 100%、P95 **279.7ms**。
- **为什么不选另一边**：HYBRID 比 VECTOR 低 4pp（关键词一路在语义歧义 query 上把正确条目挤出前 3）；加权与 RRF k 实测 0pp，写「调参提升」会被复现打脸。
- **论文建议表述**：「在本评测集上，纯向量检索（Hit@3 100.0%，P95 279.7ms）优于混合检索（96.0%）；设备/标签加权与 RRF k 的增量均为 0.0pp，故不作为默认配置。」
- **局限与答辩风险**：HYBRID 的 E3/E4/E6/E7 为离线复算，与真实接口前 3 集合一致率 94%（6/100 因同分并列差异）；不得把「离线复算」写成「接口实测」。
- **证据出处**：`docs/paper/评测/评测报告.md` §2–§3；`docs/paper/评测/消融结果.csv`。

### DEC-06 门控阈值：不抬全局阈值，改「间隔 + 根因一致性」

- **决策结论**：放弃「继续抬高全局余弦阈值」的路线；改用 **top1−top2 间隔 + 根因一致性校验**，并把论文论证轴从「Hit@3」切到「错误推送率 / 覆盖率」。
- **备选方案**：①0.75 门控上线；②抬到 0.80/0.85/0.92；③无门控全返回。
- **决定性数据**（300 条：100 正例 + 100 leave-gold-out + 四类负例各 25）：0.75 门控下混合等权错误推送率 **21.4%**（25/117），正例流 1.3%、负例流 60.0%；**无门控全返回时 61.7%**（185/300）。0.80 时错误率 **0%** 但正例覆盖仅 **31%**；0.85 覆盖 **1%**、0.92 覆盖 **0**。正例 top1 余弦：**median 0.786**、p25 0.756、max 0.852；leave-gold-out：median 0.695、p25 0.669、max 0.7885。间隔 ≥0.08 规则：leave-gold-out 误推 6→0、负例错误 18→6、正例覆盖仍 **47%**，错误率 **9.2%**。
- **为什么不选另一边**：分数分布决定了单阈值没有空间——0.85 已在正例分布最右端，抬阈值等于放弃覆盖；0.80 虽 0% 错误但只覆盖 31%，业务不可用。
- **论文建议表述**：「单阈值在 0.80 时可达 0% 错误推送，但正例覆盖仅 31%；0.75 门控的错误推送率为 21.4%。引入 top1−top2 间隔 ≥0.08 与根因一致性校验后，错误率降至 9.2%，覆盖率保持 47%。」
- **局限与答辩风险**：**0.75 从未上线**，只是反事实评估（`关键技术点.md` 明确「设计提出、代码未实现」）；今天现网是无门控全返回。不得写「现网 0.75 门控」。
- **证据出处**：`docs/paper/评测/阈值错误率评估.md` §1–§4；`docs/paper/评测/threshold_eval.csv`；commit `3af9213`。

### DEC-07 错误集中度：主战场是同象异因

- **决策结论**：问题三应用章节的改进重点锁定 **N2 同象异因**（同设备、现象相同、根因不同），而不是领域外或噪声。
- **备选方案**：①优先处理缺字段/噪声；②优先处理领域外；③靠提高阈值通吃。
- **决定性数据**：0.75 下 25 条错误推送的构成：**同象异因 11 条（44%）**、同因异象 7 条（28%）、leave-gold-out 6 条（24%）、正例 1 条（4%，且 top1 是库内同题重复而非语义跑偏）。分切片：同象异因 **11/25 推送且 100% 错误**；同因异象 7/25 且 100% 错误；领域外 **0/25**；缺字段/噪声 16/25 但 16 条全部命中原始 gold（**0 错误**）。
- **为什么不选另一边**：领域外已被向量检索天然挡住（0/25）；缺字段/噪声虽然推得多但推得对（0 错误），不是错误来源；只有同象异因是「推得出去且推错」。
- **论文建议表述**：「错误推送高度集中于同象异因样本（11/25，44%），该类样本推送后 100% 错误；领域外样本推送率为 0，缺字段/噪声样本虽有推送但 0 错误。因此三态决策的关键判别对象是同象异因。」
- **局限与答辩风险**：25 条错误的样本量小，44% 的比例 CI 很宽；负例是构造样本，分布不等于真实故障分布。
- **证据出处**：`docs/paper/评测/阈值错误率评估.md` §2–§3。

### DEC-09 检索/推送性能：并发扩容 + 超时分离

- **决策结论**：性能问题不靠加机器，靠 **消费并发 4-8→16-32** + **Milvus connect/rpc 超时分离（3s/1s）** + 检索失败 1s 快速失败。
- **备选方案**：①加节点/加副本；②延长超时；③降级关闭检索。
- **决定性数据**（200 样本）：端到端 P95 **4293ms → 507ms**（并发 1，降幅 **88.2%**）、**943ms**（并发 10，相对单并发 1.86×），P99 687/1212ms；分段均值「创建 373ms、消费→推送 361ms」定位消费瓶颈。Milvus 停机场景：改造前请求堆积 P95 4293ms，改造后 **P95 2538ms 且 50/50 全部降级成功**，恢复后无残留损坏通道。
- **为什么不选另一边**：单条消息处理是 I/O 等待型，加机器边际收益低；延长超时会让故障时堆积更严重（原 4293ms 正是「重建信道→超时→再重建」死循环）。
- **论文建议表述**：「通过消费并发扩容与 gRPC 连接/调用超时分离，端到端 P95 由 4293ms 降至 507ms（并发 1）/943ms（并发 10），并在 Milvus 停机时实现 50/50 全量降级。」
- **局限与答辩风险**：并发只测到 10，距 2000ms 指标余量有限，20/50 并发拐点未测（任务书 T12）；4293→507 是特定压测环境值，不能外推为通用 SLA。
- **证据出处**：`docs/paper/关键技术点.md` K34、K35。

### DEC-14 标注方案：人工标注 → 构造真值（弱监督）+ 三层核验

- **决策结论**：**人工标注方案作废（2026-11-06）**。1000 条工单与 300 对关系集的真值在生成时即确定，存于 `_gold_draft.jsonl` / `_gold_relation_draft.jsonl`；验证改为三层：L1 程序化自洽核验、L2 独立模型盲评、L3 10 条生成器保真度抽检；另加 200 条跨模板留出集。统一口径为 **construction-based gold（弱监督）**，论文禁止出现「人工标注 / 专家标注 / 双人标注 / 标注者间 κ」。
- **备选方案**：①按原计划人工标注 1000 条（+ 第二人 κ）；②只标 200–300 条子集并做小样本 κ；③降低标准，只标根因一个字段；④构造真值 + 三层核验（现行）。
- **决定性事实**：①1000 条 × 每条 1–2 分钟 ≈ **17–33 小时**纯阅读，且「根因是否被证据确认」「条件属哪一类」需要领域判断，对非专业者是硬门槛；②用户实测标完 5 条后确认无法继续，属可执行性问题而非意愿问题；③第二读者同样需要领域判断，无可用人力，外行复核仅覆盖 2 个二值字段、性价比低；④真值本来就在生成脚本中确定，人工重标属重复劳动且引入新口径噪声。
- **为什么不选人工**：人工方案的关键路径不可压缩——做不完就没有数据，做完了也只有 2 个二值字段的 κ，仍拿不到全槽位一致性；而构造真值方案可复现、可扩展、成本 ¥0.1 量级，且验证点（自洽、可复现、跨模板）全部可程序化或可低成本完成。
- **论文建议表述**：「工单语料的五元组与排除假设在生成时由场景表确定，构成基于构造的真值（construction-based gold），属弱监督标签，未经人工标注；本文以程序化自洽检查、独立模型盲评与 10 条生成器保真度抽检对其质量进行核验，并以跨模板留出集检验模板依赖。」
- **局限与答辩风险**：①失去全槽位人工 κ；②失去真实语料外部效度（全部合成）；③失去「现象是否符合设备原理」的人工闸门；④失去争议条目的仲裁记录。以上四条必须写入 Limitations。
- **答辩应对话术（被问「ground truth 谁标的」）**：「真值不是标出来的，是构造出来的——生成工单时用同一张场景表同时确定现象、根因、措施、验证与条件，文本与真值物理隔离。所以这是 construction-based gold / 弱监督，不是人工标注。为证明它不自说自话，我们做了三层核验：程序化自洽检查五项 100%、与生成器无关的独立模型盲评、10 条保真度抽检；另用一套完全不同的模板生成 200 条留出集，检验模型学的是能力还是模板。代价是没有全槽位人工 κ、也没有真实语料外部效度，这两点已写进 Limitations。」

### DEC-27 多信号门控原型：默认不启用，只有「阈值+根因一致性」可跨库迁移

- **决策结论**：门控原型按**可开关**实现，参数（阈值 T / 间隔 M / 相对间隔 R / z 门槛 Z / 一致性门槛 C / cons 权重）**全部只在 54/55 快照上定，原样迁到 310 库评估一次，不二次调参**。结论：**相对分数信号不可移植；唯一可迁移的是「零错误绝对阈值 + 根因一致性」组合**，代价是覆盖率由 74% 降到 24%，定位为**精度优先模式**，不写成「全面修复」。
- **一句话结论**：**margin、相对间隔、z-score 三种相对量在 310 库上与绝对阈值同步漂移（54 上选定的 M=0.086 迁到 310 只剩 7 条推送、覆盖 3%、错误率 42.9%），不能解决库规模问题；54 上定死的 0.80/0.16「阈值+根因一致性」原样迁移后取得 24% 覆盖 / 3.45% 错误（29 推 1 错），是唯一满足「错误推送率 ≤10%」的可迁移工作点，对照 0.75 单阈值在 310 的 74% / 48.5%。**
- **原型信号**：①绝对 top1 余弦 `s1`；②间隔 `s1−s2`；③相对间隔 `(s1−s2)/s1`；④批内 z-score `(s1−μ)/σ`；⑤根因一致性 `cons = 0.5714·J(工单,现象) + 0.2857·J(工单,根因) + 0.1429·设备一致`（抽到「我怀疑是…导致」这类显式假设时改为 `0.8·J(假设,根因) + 0.2·J(工单,现象)`）。`J` 为字符二元组 Jaccard，**非语义模型、非分类器**。
- **参数标定（仅 54，300 条 = 100 P + 100 N + 100 LG）**：18 组 cons 权重网格选出 `{sym 0.5714, rc 0.2857, dev 0.1429}`；单阈值 best **0.775 → 59% 覆盖 / 9.8% 错误**、safe **0.80 → 31% / 0%**；margin best **0.086 → 47% / 9.2%**；margin+cons **0.086/0.02 → 47% / 6.3%**；阈值+cons best **0.775/0.15 → 58% / 2.7%**、safe **0.80/0.16 → 30% / 0%**；rel **0.116 → 44% / 9.7%**；**z 在 54 上就没有 ≤10% 工作点**。三配置在 54 上曲线几乎重合（同覆盖下错误率差 1–3pp，属样本量级），**54 上看不出 margin 的优势**。
- **跨库迁移（310，参数不动）**：单阈值 0.775 → 45% / 35.6%；**margin 0.086 → 3% / 42.9%**；margin+cons → 3% / 33.3%；rel → 2% / 50.0%；rel+cons → 2% / 40.0%；单阈值 0.80 → 25% / 12.1%；**阈值+cons 0.80/0.16 → 24% / 3.45%**；阈值+cons 0.775/0.15 → 45% / 27.3%。**只有 0.80/0.16 满足 ≤10%**，其 29 条推送 = 24 正例（全对）+ 4 负例（全对）+ **1 条 LG（错）**。
- **机制**：扩库后正例 margin 中位数 **0.0822→0.0290（缩 2.8×）**、负例 0.0373→0.0145，**相对量随绝对量一起漂移**——相对化只消除整体平移，消不掉「top2 被同题新条目抬高」造成的间隔压缩。`cons` 的中位数基本不动（P 0.1913→0.1887、N 0.0523→0.0626），因为它是文本字段比对而非分数几何，故可迁移；但判别力窄（310 上 LG 0.1631 vs P 0.1887，仅差 0.0256），这是那 1 条 LG 漏网的直接原因。
- **如实记录的反例**：用户设想的「margin + 根因一致性」在 54 上按「覆盖损失 ≤1pp」选出的 C 只能是 **0.02**（几乎不过滤），迁到 310 后 margin 本身已只剩 3% 覆盖，cons 救不回来。**可迁移的是「阈值+cons」这一支，不是「margin+cons」。**
- **论文写法**：创新点四改写为「多信号门控原型 + 跨库冻结迁移」；结果写 24% 覆盖 / 3.45% 错误并明确是精度优先；曲线与工作点放 5.4 稳健性小节；「相对信号不可迁移」同时进 5.6 局限与负结果小节（位置未定者按暂定标注）。
- **不可说**：❌「多信号门控把 310 库错误率修回 19.1% 且保持 74% 覆盖」；❌「margin 比单阈值更稳健」；❌「根因一致性由语义模型/分类器计算」；❌ 把 3.45% 与 0.75 的 74% 并列而不提覆盖率代价。

### DEC-30 AI 对话撤回与计费口径解耦：撤回只删消息，不回滚已发生的模型调用

- **背景**：AI 对话的「撤回」是**硬删除**——该条用户消息与它触发的那条 AI 回复从 `ai_chat_message` 中真实删除，会话回到「这轮没发生过」，也不再作为上下文送入模型。但模型调用在删除之前已经发生并计费，`ai_call_log` 按调用逐条落行（表内无 `session_id`），删消息不会也不应该把已经花掉的成本抹平。
- **决策结论**：**计费口径与消息生命周期解耦**。观测页的成本与 token 按「调用实际发生」累计，**包含已撤回的对话**；撤回只影响会话展示与上下文拼装，不影响 `ai_call_log` 与成本统计。
- **一句话结论**：**消息可以删，账不重算。**
- **影响**：
  1. 观测页的调用次数 / token / 估算费用**不等于**「现存会话的消息量」，两者对不上属预期，不是 bug；
  2. 论文与答辩引用成本时，**分母是调用次数**（`ai_call_log` 行数），不是现存会话数或消息条数；
  3. 若被问「撤回后成本为什么没降」，用本条解释：撤回是内容层操作，计费是调用层事实；
  4. 论文中若同时给出「会话数 / 消息数」与「调用成本」，须注明两者口径不同，不可互相推算。
- **适用范围**：**仅 AI 对话撤回**（`/assistant` 页的消息级撤回）。不涉及工单、知识库等其他数据，这些数据的删除与回滚仍按各自规则处理。
- **证据出处**：`ai_call_log` 表（无 `session_id` 字段，按调用落行）；`docs/sql/20261113_ai_chat_message_quote_recall.sql`；`AiChatSessionService#deleteRound`（物理删除 + 同一事务清理引用与重算标题）；验收结论：删除后消息行 `COUNT=0`，同期 `ai_call_log` 条数与 token 不变。

### DEC-31 评测报告归档口径：同一实验多次运行，报告数字只取同一次完整运行

- **背景**：AI 应用层路由评测在 2026-11-07 前后共跑过三次——08:18:18 的中间运行、08:47:58 的完整运行（正式报告采用）、以及一次独立的第二次全小模型运行（93.0%）。三次运行的条目 id 完全一致（R001–R300，无多无少），但模型输出文本、tokens、耗时、费用逐条不同，导致汇总值不同（全小模型 92.67% / 93.67% / 93.0%）。此前中间运行的快照以乱码文件名残留在 `docs/paper/`，易被误当成另一套结果。
- **决策结论**：**同一实验多次运行时，报告数字只能取自同一次完整运行，且以能由原始行（如 `routing_rows.json`）复算的版本为准**；中间运行的数值只用于说明采样波动量级，**不得与正式结果混用、不得跨运行拼表、不得对不同批次求平均**。
- **一句话结论**：**一次报告一套数，跨运行不拼表。**
- **影响**：
  1. 论文与答辩引用任何数字时，须注明所属运行批次（本报告为 2026-11-07 08:47:58）；
  2. 中间运行与正式版的差异只写成「采样波动」，不得写成方法改进或性能回退；
  3. 同一指标出现 92.67% / 93.0% / 93.67% 时，必须各自标注口径，不可相加、求平均或择一冒充全体；
  4. 归档只保留可复算的正式版原始行，中间快照不单独归档；清理时须先核对 id 集合与能否被正式版覆盖。
- **适用范围**：全部离线评测与论文引用的实验数字（AI 应用层路由、门控、抽取、S3 等）。不涉及线上 `ai_call_log`——那是按调用发生记账，口径见 DEC-30。
- **证据出处**：`docs/paper/ai应用层/路由评测报告.md` §5 第 7 条（2026-11-13 补注，含 92.67% 原值）；`docs/paper/ai应用层/路由评测.json` 与 `raw/routing_rows.json`（`generated_at 2026-11-07 08:47:58`，正式版）；08:18:18 中间快照的删除记录见 VM `DEVLOG.md` 2026-11-13。

### DEC-32 资源配额「先测后定」：先实测，再按一倍余量申请

- **背景**：2026-11-14 在 master1 只读体检显示，公司集群可调度的 Ready 节点只有 3 台（rn-8300、worker1、worker2），合计约 8.6 核 / 57G，单节点最大剩余仅 4.5 核。此前「一套 = 8 核 / 16GiB」是按业务画像得到的估算值，未经实测；且 MySQL、Redis、Milvus、Nacos、网关等中间件可能由环境本身已配置，按估算整包申请容易与实际不符。
- **决策结论**：**不预先按估算值申请 namespace 配额**。先在测试环境把各模块单独跑起来，用 `kubectl top` 观测真实 CPU / 内存占用，再按实测值留**一倍余量**写入 `requests`，最后据此申请配额。此前的「8 核 / 16GiB」仅作为**上限参考**，不作为申请依据。
- **一句话结论**：**先跑小模块、测出真值，再按两倍实测值申请配额。**
- **理由**：估算值与实测值可能差数倍。先申请要么占着不用、挤占他人余量，要么申请不足导致 Pod Pending 或被限流；先测后定可以一次报准。
- **影响**：
  1. 配额申请动作后移到实测之后，当前不提交固定的 8 核 / 16GiB namespace 配额；
  2. 单个 Pod 规格必须小于单节点最大剩余（当前 4.5 核），不能按「整机 8 核」申请；应按 namespace 配额 `requests.cpu=8` / `requests.memory=16Gi` 拆成多个小规格 Pod，由调度器分散；
  3. 每个模块的实测需记录命令、时间与 `kubectl top` 原始值，归档到 `docs/ops/公司环境操作记录.md`；
  4. 中间件若由环境自带，不重复计入申请量；只为自己新建并运行的部分申请。
- **适用范围**：公司集群的 namespace 配额与 `requests` 申报。不改变已定的离线镜像、K8s 1.24 兼容等部署口径（DEC-11）。
- **证据出处**：`docs/ops/公司环境操作记录.md` 第六节（2026-11-14 14:36 master1 只读实测）与台账同日 14:36 行。

  3. 文档与答辩口径统一为「清单/API 兼容性已验证，运行时验证待部署」，不扩大结论。
- **适用范围**：19.64 的兼容性结论与结论表述边界；不改变 DEC-33 的选型顺序与 DEC-34 的判读口径。
- **证据出处**：`docs/ops/公司环境操作记录.md` 操作台账 2026-11-16 第三条补记（ns Active + 40/40 dry-run）。

### DEC-36 镜像发布改为「集中 push 到 harbor.xnunion.com，各节点自拉」

- **背景**：原方案是逐节点搬运镜像，效率低且易漏。2026-11-16 在 19.64 上实测：`harbor.xnunion.com` 解析为 **172.27.18.160**（同一台）；`http://harbor.xnunion.com/v2/` 返回 **401**（仓库存活、需认证），`https` 返回 **000**（443 未开）；该地址已同时出现在 `daemon.json` 的 `insecure-registries` 与 `~/.docker/config.json` 的认证记录中，属于「已信任 + 已有凭证」。推送探针返回 **Pushed**，digest `sha256:ead92baed3591802f72396d6400afb30375587be8e79f4414223a2601cf8a8b4`，size 523 字节，证明对 `library` 项目有写权限。
- **决策结论**：
  1. 镜像发布方式由「逐节点搬运」改为「**搬一次到 master1 → push 到 `harbor.xnunion.com` → 各节点自拉**」；
  2. 镜像仓库确认为 **`harbor.xnunion.com`（= 172.27.18.160，仅 HTTP，已在集群信任名单）**；
  3. **172.27.8.220 的 Nexus 仅作 Maven/yum 仓库，不再作为镜像源**；
  4. **待定项**：是否在 `ai-tims` 项目下发布；若该项目不存在，暂用 `library`。
- **一句话结论**：**镜像只搬一次，推到 harbor.xnunion.com，各节点自己拉。**
- **命名更正**：仓库名以 `getent hosts` 实测与 `/v2/` 响应为准，正确写法 **`harbor.xnunion.com`**；此前若出现 `harbor.cmuxntion.com`、`harbor.xmution.com`，均为截图小字识别错误（本仓库文档检索未发现这些错误写法，无需改字）。
- **理由**：集中推送后各节点按镜像名拉取，避免逐节点复制 tar；仓库已信任、已有凭证且写权限已验证，改造成本最低；Nexus 只承担 Maven/yum，避免职责混淆。
- **影响**：
  1. `deploy/k8s/overlays/company` 的镜像前缀应改为 `harbor.xnunion.com/<项目>/...`，项目名待定前先用 `library`；
  2. 各节点需能解析 `harbor.xnunion.com` 且信任 HTTP（`insecure-registries`）；新加入的节点要同步该配置；
  3. 探针镜像 `library/ai-tims-probe:1` 属临时产物，确认权限后应在 Harbor 界面删除；
  4. 项目归属（`ai-tims` 还是 `library`）确认后再改清单与文档，避免二次改名。
- **适用范围**：镜像仓库与发布链路；不改变已定的环境选型（DEC-33）、兼容性结论（DEC-35）与配额原则（DEC-32）。
- **证据出处**：`docs/ops/公司环境操作记录.md` 操作台账 2026-11-16 第四条补记（仓库定位 + push 探针）。

### DEC-37 Nacos 命名空间用 ID，不用名字

- **背景**：公司公共 Nacos（`10.96.1.240:8080`，控制台 `http://172.27.19.64:30081`）中已存在命名空间 `zzq-tims`。Nacos 的服务注册/配置查询只认 namespaceId，不认显示名。
- **决策结论**：`NACOS_NAMESPACE` 取值为 **`7a8fa30c-0121-4606-8c17-f6b932e9c80a`**（即 `zzq-tims` 的 namespaceId），写入 `deploy/k8s/base/config/common-configmap.yaml`；**服务注册必须显式指定该 ID，否则会落到 public**。
- **一句话结论**：**命名空间填 ID（`7a8fa30c-0121-4606-8c17-f6b932e9c80a`），不要填 `zzq-tims` 这个名字。**
- **理由**：填名字会被当作不存在的空间，服务静默注册到 public，表现为「配置读不到、实例列表看不到」，排查成本高。
- **影响**：六个后端启动参数统一走该 ConfigMap；后续新建环境或换命名空间，只改这一处 ID；填错时表现为注册到 public，而非启动报错。
- **适用范围**：Nacos 注册与配置；不改变 MySQL 接入方式与环境选型结论。
- **证据出处**：`docs/ops/公司环境操作记录.md` 操作台账 2026-11-18 补记（控制台 + `/nacos/v1/console/namespaces`）。

### DEC-38 Nacos 地址必须用主端口 8848，不能用控制台端口 8080

- **背景**：2026-11-18 首次部署后 `ticket-gateway`、`ticket-knowledge` 进入 CrashLoopBackOff，日志为 `NacosException: Client not connected, current status:STARTING`，栈顶在 `NamingGrpcClientProxy.registerService`。实测 `mqis-tm16-test/nacos-service` 映射为 `8080:30081, 8848:30849, 9848:31849`，此前配的是 `10.96.1.240:8080`。
- **决策结论**：`NACOS_ADDR` 使用 **`10.96.1.240:8848`**（主端口），gRPC 由客户端自动 +1000 走 **9848**；**不得填控制台/HTTP 端口 8080**。
- **一句话结论**：**Nacos 客户端连 8848，gRPC 自动走 9848；填 8080 会去连不存在的 9080。**
- **理由**：Nacos 2.x 客户端注册走 gRPC，端口约定为主端口 + 1000；8080 是控制台映射，其后不存在 9080，连接永远建不起来，表现为注册一直 `STARTING` 而非明确报错。
- **影响**：六个后端统一走 `tims-common-config` 的 `NACOS_ADDR`；换环境时需同时确认 8848 与 9848 两个端口可达。
- **适用范围**：Nacos 接入地址；不改变命名空间取值（DEC-37）。
- **证据出处**：`docs/ops/公司环境操作记录.md` 第十节 10.1–10.2。

### DEC-39 模型整体切换为公司内网 vLLM，数据不出网

- **背景**：原配置指向智谱云 `https://open.bigmodel.cn/api/paas/v4`（`glm-4-flash`）。公司内网无外网出口，`curl -v` 报 `NSS error -5961 PR_CONNECT_RESET_ERROR`（SNI 域名白名单拦截）。内网 vLLM 实测可用：对话 `http://172.27.26.253:18892/v1`（`Qwen/Qwen3.8-27B-dev`，`max_model_len=262144`，`system_fingerprint=vllm-0.23.0-tp4`），向量 `http://172.27.26.253:18893/v1/embeddings`（`Qwen/Qwen3-Embedding-8B`）。
- **决策结论**：对话与向量**全部切到内网 vLLM**，不再依赖任何公网模型服务；key 为服务级，写入 Secret 的 `LLM_API_KEY` / `ZHIPU_API_KEY`，不进文档、不进镜像。
- **一句话结论**：**模型全部走内网 vLLM，数据不出网，也不再受 SNI 白名单影响。**
- **理由**：公网通道已被证实不可用；内网 vLLM 已跑通对话、embedding 与完整入库/检索链路，且数据不出内网。
- **影响**：
  1. 改 `common-configmap.yaml` 的 `LLM_BASE_URL` / `LLM_CHAT_MODEL` / `ZHIPU_EMBEDDING_URL`；
  2. `ai.yaml` 的 `LLM_CHAT_MODEL` 与 `SPRING_AI_OPENAI_CHAT_OPTIONS_MODEL` **两处都要改**，只改一处不生效；
  3. `knowledge.yaml` 的 `TIMS_KB_EMBEDDING_MODEL`；
  4. 模型为 `-dev` 开发版权重，答辩前需压测稳定性。
- **适用范围**：对话与向量模型接入；不改变向量维度决策（DEC-40）。
- **证据出处**：`docs/ops/公司环境操作记录.md` 第十节 10.3、10.7。

### DEC-40 向量维度保持 1024（`dimensions` 降维），不重建集合

- **背景**：`Qwen/Qwen3-Embedding-8B` 默认输出 **4096 维**，原设计为 **1024 维**；Milvus 集合维度创建后不可修改。实测 vLLM 支持 `dimensions` 参数：带 `dimensions: 1024` 返回 1024 维，不带返回 4096 维。
- **决策结论**：**保持 1024 维**，请求时显式传 `dimensions: 1024`；已有集合不重建。
- **一句话结论**：**维度留在 1024，用降维参数适配，代价是精度略降。**
- **理由**：重建集合意味着历史知识全部重算与重新入库；1024 维已在实测中给出可用检索分（top1 0.88829 ≥ 阈值 0.75），收益不足以覆盖重建成本。
- **影响**：embedding 请求必须带 `dimensions`；换模型或改维度需同时改 `TIMS_KB_EMBEDDING_MODEL` 与集合维度，并重跑入库。
- **适用范围**：向量表示与 Milvus 集合；不改变模型选型（DEC-39）。
- **证据出处**：`docs/ops/公司环境操作记录.md` 第十节 10.4、10.7（`dim=1024` 日志与检索分数）。

### DEC-41 外部访问用 NodePort，不安装 ingress-nginx

- **背景**：集群内没有 ingress-nginx（`kubectl get pods -A | grep -i ingress` 为空），仓库里的 Ingress 资源 `ai-tims`（host `tims.company.local`）没有控制器承接，实际不可用。
- **决策结论**：**不安装 ingress controller**；`ticket-gateway` 用 **NodePort 30204** 对外，前端用 **NodePort 31579**。
- **一句话结论**：**没有 ingress 控制器就不硬上 Ingress，直接 NodePort。**
- **理由**：安装 ingress-nginx 属于新增集群级组件，需额外权限与端口占用，且与公司既有入口可能冲突；NodePort 在本环境改动最小、可立即验证。
- **影响**：访问地址带端口；后续若要域名+80/443，需单独申请并安装控制器，届时再改回 Ingress。
- **适用范围**：外部访问方式；不改变前后端内部调用关系（DEC-42）。
- **证据出处**：`docs/ops/公司环境操作记录.md` 第十节 10.5。

### DEC-42 前端用同源 nginx 反代，不做跨域直连

- **背景**：base 原先没有前端 Deployment，overlay 只有镜像名预留。新增 `deploy/k8s/base/apps/front.yaml`（ConfigMap + Deployment + Service，NodePort 31579），镜像 `harbor.xnunion.com/library/ai-tims-front:1.0.0`。前端请求为相对路径（`/api/...`、`/ws/push`）；镜像自带 nginx 已有 `/api/` 反代到 `ticket-gateway:8080`，但**缺 `/ws/` 反代与 SSE 缓冲设置**。
- **决策结论**：前端与 API **同源**，由 front 的 nginx 统一反代到 gateway；用 ConfigMap 覆盖 `default.conf`，补 `/ws/`（带 `Upgrade` / `Connection` 头）与 `proxy_buffering off`、`proxy_read_timeout 300s`。
- **一句话结论**：**同源反代，不搞跨域；WebSocket 与 SSE 的 nginx 配置必须补齐。**
- **理由**：同源省去 CORS 与 token 跨域传递问题；WebSocket 升级头与 SSE 缓冲不配会导致推送失败或消息延迟到达。
- **影响**：前端只暴露一个端口（31579）；后续换域名或加 Ingress 时，反代规则随 ConfigMap 一起迁移。
- **适用范围**：前端与 gateway 的访问路径；不改变 gateway 对外暴露方式（DEC-41）。
- **证据出处**：`docs/ops/公司环境操作记录.md` 第十节 10.6、10.7。

### DEC-43 门控阈值 0.70 + 查询侧 instruction 前缀（Qwen3-Embedding-8B）

- **背景**：向量化模型由智谱 embedding-3 切到内网 `Qwen/Qwen3-Embedding-8B`（DEC-39，1024 维降维见 DEC-40）后，分数刻度整体下移：实测 top1 余弦 0.6753 被 0.75 阈值判为 C 档、`refs` 清空；关闭门控后同一问题的 top1 就是正确的 SOP《回流焊温区温度偏低》。8 条抽样同向（有解 0.6446～0.7858、无解 0.4422～0.5523），说明**区分度仍在、是刻度平移**，属模型切换后未重标定 + 查询侧缺 instruction 前缀。
- **决策结论**：① 查询侧启用 Qwen3-Embedding 官方检索指令前缀，拼成 `Instruct: {desc}\nQuery: {q}`；**文档侧保持原文，不重灌 Milvus 向量**；② 门控阈值 0.75 → **0.70**；③ 软带 **0.07 保持不变**（区间 [0.70, 0.77)），门控三档结构与回退层不变。
- **为什么文档侧不重灌**：Qwen3-Embedding 的 instruction 只作用于查询向量；文档侧加前缀会与库里 310 条既有向量口径不一致，且需要全量重算。只改查询侧即可对齐协议，回滚也只是清空一个环境变量。
- **落地形态（可回滚的开关，不硬编码）**：`EmbeddingService.embedQuery()` 读 `tims.kb.embedding.query-instruction`（环境变量 `KB_EMBED_QUERY_INSTRUCTION`），为空则退化为原文本；`SearchService.tryVectorSearch()` 改调 `embedQuery()`。阈值走 `KB_GATE_THRESHOLD`（默认仍是 0.75，环境变量覆盖为 0.70）。生产环境在 `deploy/k8s/base/apps/knowledge.yaml` 的 `ticket-knowledge-config` 固化这四个 key（`KB_GATE_ENABLED=true`、`KB_GATE_THRESHOLD=0.70`、`KB_GATE_SOFT_BAND=0.07`、`KB_EMBED_QUERY_INSTRUCTION=...`），`deploy/` 下无第二份同名 key。
- **镜像**：`harbor.xnunion.com/library/ticket-knowledge:1.0.1`（上线前为 1.0.0；节点有镜像缓存，必须换 tag 才会真正滚动重建）。镜像内 `/app/app.jar` 与构建产物 md5 一致。
- **上线状态**：**已上线**。2026-11-19 在公司环境的知识库 Pod 内直接请求 `/api/kb/search`（HYBRID、topK=5）验证生效：返回 `gateThreshold=0.70`、`gateEnabled=true`、`degraded=false`、`fallback=false`；同一问句的 `maxVectorScore` 为 **0.76701**，`tier` 由上线前的 **C**（`items` 被清空）变为正常返回（`reason` 给出通过说明），top1 为《回流焊预热不足导致冷焊》。该验证为**单条 query（n=1）**，只证明配置生效与方向一致，不作统计结论；线上批量回放仍列为待补。
- **回滚方式**：① 镜像回退 `deploy.sh knowledge 1.0.0`（1.0.0 不读前缀配置，天然忽略该变量）；② 阈值改回 0.75 并 `rollout restart`；③ 清空 `KB_EMBED_QUERY_INSTRUCTION`。三步互相独立，不需要重灌向量、不涉及数据变更。
- **适用范围与局限**：0.70 的标定前提是「310 条知识库 + Qwen3-Embedding-8B + dimensions=1024 + 文档侧不加前缀」；换模型、换维度、或文档拼接方式变化都必须重新标定。软带是否随阈值平移、以及间隔规则是否引入，属于后续独立实验，不在本条预判。
- **证据出处**：`docs/paper/评测/Qwen3Embedding阈值重标定.md` §七；`deploy/k8s/base/apps/knowledge.yaml`；`docs/paper/评测/_qwen3/续接记录.md`。
