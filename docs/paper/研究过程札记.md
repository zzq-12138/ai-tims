## 1. 工程缺陷

### P-01 雪花 ID 超出 JS 安全整数，工单详情 404

| 栏 | 内容 |
|---|---|
| **现象** | 工单详情页偶发 404；同一工单在列表能查到，点进详情却提示不存在。 |
| **定位过程** | 对比列表返回的 ID 与详情请求携带的 ID，发现末位被改写。`ai-tims-front/src/utils/request.js` 第 6–7 行注释留下复现值：`2117985300138262530 → 2117985300138262500`。后端雪花 ID 为 19 位 Long，超过 JS `Number.MAX_SAFE_INTEGER`（2^53−1），`JSON.parse` 默认转 Number 时丢精度，按错误 ID 查库自然 404。 |
| **根因** | 序列化层把 64 位整数当 JS Number 处理；不是数据库或接口逻辑问题。 |
| **对策** | 前端引入 `json-bigint`（`storeAsString: true`），在 axios `transformResponse` 统一解析；只把超出安全范围的整数转字符串，其余数字保持 Number（`request.js` 第 9–23 行）。 |
| **验证结果** | 修复后详情页可正常打开，ID 不再变尾。**未找到自动化回归测试记录**；证据为代码注释中的前后值对照。 |
| **论文用途** | 第 3 章系统实现（工程贡献），一句话交代「长整型主键与前端安全整数边界」即可；不单独占实验小节。若写「系统可复现性」，可作为工程细节示例，**不要**把它写成 AI 方法贡献。 |

**证据与复核**：B。`ai-tims-front/src/utils/request.js` L6–L23；`ai-tims-front/package.json` L13–L15。

### P-02 消息中心恒为空：首装标志 + 字段名不一致

| 栏 | 内容 |
|---|---|
| **现象** | 登录后消息中心列表始终为空，未读数不更新；刷新、换账号都一样。 |
| **定位过程** | 两处独立缺陷叠加：① `stores/push.js` 用 `if (loaded && next === userId.value) return` 做防重，`userId` 初始为 `''`，首装时直接 return，localStorage 从未被读取；② `/api/auth/me` 返回字段是 `userId`，布局层只取 `auth.user?.id`，取到 `undefined` 后消息被写进 `anon` 键，REST 兜底也永不触发。证据：`push.js` L34–L36 注释「若只比较 userId 会在 undefined 场景下直接 return，导致已读消息永远不落回列表（问题 6 的根因）」；L48–L50 的 `loaded` 首装逻辑；L55–L56 注释「旧版本因取错字段（id 而非 userId）把消息写在 anon 键」。`MainLayout.vue` L197–L199 注释「返回的是 userId（不是 id）」。 |
| **根因** | 状态机缺「是否已装载」维度；前后端字段命名不一致且无统一取值函数。 |
| **对策** | 增加模块级 `loaded` 标志，首次调用强制读 localStorage；新增 `uidOf()` 统一取 `userId ?? id`；对历史 `anon` 键做一次性迁移并删除旧键，避免串号。 |
| **验证结果** | 换账号可正确装载各自消息箱，历史消息回填。**未找到自动化测试记录**，证据为代码注释与迁移逻辑。 |
| **论文用途** | 第 3 章系统实现（工程贡献）；可归入「多端状态一致性」一小段。价值中等，不建议进实验章。 |

**证据与复核**：B。`ai-tims-front/src/stores/push.js` L30–L70；`ai-tims-front/src/layout/MainLayout.vue` L197–L200。

| 栏 | 内容 |
|---|---|
| **现象** | 浅色标签上的文字偏淡，对比度实测 3.03:1，低于 WCAG AA 正文级 4.5:1。 |
| **定位过程** | 用对比度工具测得 3.03:1（**该测量值仅见于会话记录，仓库内未找到测量报告或截图**）。检查样式发现：自定义规则只写单类选择器 `.el-tag--primary`，与 Element Plus 默认的同类规则权重相同，构建后加载顺序导致默认色覆盖自定义色。 |

| **论文用途** | 第 4 章 AI 应用层/界面可用性一句话；价值低。可作为「工程验收清单包含可访问性」的旁证，不单独成节。 |

**证据与复核**：C（修复代码为 B，测量值无原始记录）。`theme.css` L177–L183。

### P-09 transformers 5.22.1 下 Qwen2 梯度检查点不生效

| 栏 | 内容 |
|---|---|
| **现象** | 开启 `gradient_checkpointing` 后显存不降，RTX 4090 24G 上 `seq_len≥768` 必 OOM。 |
| **定位过程** | 对比不同 transformers 版本的 Qwen2 实现：5.22.1 的 Qwen2 没有 `_gradient_checkpointing_func` 调用点，`gradient_checkpointing_enable()` 只置标志、不真正重算。证据：`scripts/finetune/train_lora.py` L11–L14 原文「transformers 5.22.1 的 Qwen2 实现里没有 `_gradient_checkpointing_func` 调用点，`gradient_checkpointing_enable()` 只置标志、显存不降，导致 4090(24G) 上 seq_len≥768 必 OOM」。 |
| **根因** | 框架版本与模型实现不匹配；且检查点必须在 PEFT 包装之后开启，`use_reentrant=True` 与「只有 adapter 需要梯度」不兼容。 |
| **对策** | 锁 `transformers==4.46.3`、`datasets==3.6.0`、`huggingface_hub==0.36.2`；在 `get_peft_model` 之后调用 `gradient_checkpointing_enable(gradient_checkpointing_kwargs={"use_reentrant": False})`，再 `enable_input_require_grads()`（`train_lora.py` L145–L151）。 |
| **验证结果** | 4090 24G、bf16：`seq_len=1024` 峰值 17.04 GB，`seq_len=2048` 峰值 19.27 GB；2048/b2 仍 OOM。`scripts/finetune/README.md` L33–L50 有版本对照表。 |
| **论文用途** | 第 3 章 3.4「训练环境与可复现性」；工程贡献。写法：给出「必须 4.46.x + peft 后开启 + use_reentrant=False」三条硬约束，供复现。 |

**证据与复核**：A。`train_lora.py` L11–L14、L145–L151；`finetune/README.md` L33–L50；`GPU环境验收.md` §一。

### P-06 构造真值自检首测 0/500

| 栏 | 内容 |
|---|---|
| **现象** | L1 第一项「排除假设的证据可在原文子串匹配」首测 **0/500**，其余四项正常。 |
| **定位过程** | 逐条比对失败样本：gold 里存的是**规范化短语**（如「气压不足」），原文是**风格化叙述**（经 typo/missing 扰动后写法不同），`in` / 子串判断必然失败。证据：`标注方案变更说明.md` L79–L81 原文「第 1 项首次为 0/500——gold 存的是规范化短语，原文是风格化叙述（typo/missing 扰动后不一致）。属生成器缺陷，已改为『从工单正文回截证据子串』并重新生成全量数据，复跑后 500/500」。 |
| **根因** | 生成器在写 gold 时做了规范化，而正文又被扰动，两者不再字面一致；检查器假设「gold 是原文子串」，假设不成立。 |

### P-21 计算路线三次干净集：79.17% → 68.0% → 92.0%

### P-22 闸门 v2：定向修补在两个独立留出集上都未转化为准确率提升（消融负结果，非主结果）

| 栏 | 内容 |
|---|---|
| **现象** | `det-trigger-v2` 冻结后（`230d114b…`，2026-11-10T14:41:35+08:00）新出 Holdout-4（120 条，与前三套题干/数字签名零重叠），五组同集同分母：小模型裸跑 **32.5%**、工具自调 **75.0%**、det-v2 **90.0%**、**v1 语义副本复现 92.5%**、全大模型 **93.33%**。为回答「v2 到底有没有比 v1 好」，用冻结代码**离线还原 v1 语义**（0 元、0 API）在**同一份** Holdout-4 上补跑：v1 = **92.5%** —— **v2 比 v1 低 2.5pp**；先在 Holdout-3 上复现 92.0%（触发 18%、来源 61/18/21、五分类 8 条漏触发，逐项一致）证明该副本可信，同一份 Holdout-3 上 v2 = **89.0%**（−3.0pp）。两项改动在靶心上都没有转化为准确率收益。 |
| **定位过程** | 先做机制归因再动手：Holdout-3 的 8 条漏触发里，有 3 条**正确答案**被判 `conflict` 且值在候选集 0 命中 → 缺口在「基数方向」（题面数当基数、中间结果当现值），于是只补反向枚举；另有 3 条误覆盖同源于「用不完整候选集去改答案」，于是候选不全时降级 `uncomputable`、`picked=[]`。**没有逐条看那 8 条去加线索、改正则或调 rank 阈值**——事实上 v2 在 Holdout-3 上冒烟时反而从 92.0% 掉到 89.0%（新增 3 条巧合误接受，`H3-027/028/031`），按「只测不调」协议不回改。 |
| **根因** | 改动 A 修的是「候选集表达力缺口」，改动 B 修的是「覆盖前提不成立」，都不是「判断力」。A 的副作用是**候选集变宽**，而接受判据是「答案数字 ∈ 候选集」——越宽越容易巧合接受，于是 G5 准确率没变（同集 v1/v2 均 87.5%），却新增 3 条 G2 漏触发（`H4-024/025/029`，H3 上同样 3 条），触发率下降被误读成「效率提升」；B 的前提在 7 算子全集下几乎不成立，**两份集 `incomplete=True` 都是 0 次**，是惰性分支，「误覆盖 3→0」实际由 A 造成（`conflict` 变 `recomputed`，跳过覆盖）。它也救不了「题面根本没有数字」的题：G7 组闸门只触发 1 次（6.25%），升级后仍错，62.5% 与全大模型持平——**天花板在模型侧**。 |
| **对策** | ① 上线形态锁定「只升级不覆盖」：覆盖策略 85.0% < 升级 90.0%，6 条差距全是「多值题只能裁决第一个数」（`H4-001` 只给 `560`、缺达成率 93.7；其余 5 条百分挑错），覆盖在多候选并列时无法裁决；② 若真要上线，用 **v1 语义**（不做反向枚举；覆盖仍停用）——但**不为此新开 `det-trigger-v3`**：撤掉两处已被同集证据否定的改动没有新机制假设，只是重跑，不构成方法推进；③ 把「同集净退步 2.5pp」原样写进结论，卖点只留成本（0.000332 元/条 = 大模型的 41.8%，0.00095 口径 34.9%），并注明「省下的升级次数里有 3 次就是丢掉的分」；④ 触发来源与五类错误单列，让「闸门兜住了什么、没兜住什么」可逐条核查。 |
| **验证结果** | 同集消融（H4，120 条）：v1 **92.5%** > v2 **90.0%**，净退步 **2.5pp**；H3 复算 v1 92.0% / v2 89.0%（−3.0pp）。分组同集对照：G5 v1 = v2 = **87.5%**（改动 A 收益 0，触发率 50%→31.25%），G2 v1 100% → v2 **81.25%**（唯一变差处），G7 两边同为 62.5%；**漏触发 v1 8 → v2 11**（新增 3 条全在 G2）；G5 那 6 条 `delta_percent` 传 `scale:0.1` 的关系抽错**没有消失**（H3 上两边 G5 均 62.5%，H4 上两边均 87.5%）。H4 v2 明细：触发 15.83%（19 条）；来源 自调 72（90.28%）/ 强制 19（94.74%）/ 未触发 29（86.21%）；五类错误（工具 30 条）17/0/11/0/2；det 残余 12 = 漏触发 11 + 升级后也错 1，**误覆盖 0**（v1 为 3，`H4-065/066/075`，归因改动 A）。9 条题面二义剔除后 111 条：det 91.89% vs 大模型 93.69%，方向不变。费用 v2 0.000332 元/条（41.8%）、2.48 轮、9.46 s；v1 0.000363 元/条（45.7%）、2.52 轮；本轮总花费约 0.13 元。 |
