## 一、口径

- 分数列 `score`：该 query 的 top1 余弦。
- `pushed`：`score >= thr` 的条数。
- `P`：`usable=true` 表示 top1 命中 `expectedIds`；`err` = 推送中 `usable=false` 的条数。
- `LG`：leave-gold-out，构造上 100% 不可用；`err = pushed`，错误率恒为 100%。
- `N`：`usable=true` 仅 N4（缺字段/噪声）命中原始 gold；`err` = 推送中 `usable=false` 的条数。
- `hit1` / `hit@1%`：仅 `P` 有意义，按全量 100 条计算，不随阈值变化；`LG/N` 记为 `-`。
- 混合等权错误率 = 三池 `err` 合计 / 三池 `pushed` 合计。

## 三、可复算结论

1. **前缀有效**：`P` 的 Hit@1 从 raw **82.0%** 升到 instruct **92.0%**（+10.0pp）；0.70 下 `P` 推送数从 87 降到 82、正例错误从 8 条降到 2 条。
2. **instruct 0.70 工作点**：`P` 覆盖 **82.0%**，正例错误 **2 条（2.4%）**；`LG` 56 条全错；`N` 推送 53 条、错 33 条（62.3%）。三池合计 `pushed=191`、`err=91`，混合等权错误率 **47.6%**；按有效负例口径为 **45.1%**（与 [Qwen3Embedding门控阈值实测结果.md](Qwen3Embedding门控阈值实测结果.md) §三一致）。
3. **0.75 的代价**：覆盖从 82.0% 降到 **71.0%**，正例错误降为 0；减少的 11 条里，**2 条本来错误、9 条本来正确**——这就是“该推不推”的量化代价。
4. **0.77 也不达标**：`P` 错误 0，但覆盖只剩 **61.0%**；`N` 错误率仍有 **23.8%**。单靠抬高阈值不能同时满足“高覆盖 + 低错误”。
5. **不宣称达标**：0.70 不是“错误率达标点”，而是“恢复被误挡正确回答、同时正例错误仍可接受”的折中点；混合等权 47.6% 的错误率仍然很高，不能写成「已达标」。

## 四、`gateEnabled` 为什么被忽略

**实测**：请求体带 `"gateEnabled":false`，返回仍是 `"gateEnabled":true`、`tier":"C"`、`total":0`、`items":[]`。

**代码定位与结论**：

| 问题 | 结论 | 依据 |
|---|---|---|
| 请求级字段名是否就是 `gateEnabled`，有无别名或未映射 | **没有请求级字段**。POST 的 DTO 只有 `query` / `mode` / `topK`，没有 `gateEnabled`，也没有别名；传入的 `gateEnabled` 是未知属性，被 Jackson 忽略（Spring Boot 默认不因未知属性报错） | `ai-tims-parent/ticket-knowledge/src/main/java/com/tims/knowledge/controller/SearchController.java:38-57` |
| 门控是否被 `KB_GATE_ENABLED` 等配置强制覆盖、请求参数是否被忽略 | **是**。门控只看 `@Value("${tims.kb.gate.enabled:true}")` 等配置，`search()` 入参只有 `tenantId/query/mode/topK`；响应里的 `gateEnabled` 回写的是配置值，不是请求值 | `SearchService.java:46-53`、`SearchService.java:72`、`SearchService.java:143-167`、`SearchService.java:173`；配置映射见 `application.yml:60-66` |
| 不改生产配置看原始 topK 的正确做法 | **当前没有只读开关或内部 debug 检索端点**。`/api/kb/search` 只有上述 DTO；`/api/kb/ping`、`/internal/kb/extract/queue-stats` 都不是检索；Actuator 只暴露 `health,info`。端口转发 8103 仍是同一门控；转发 Milvus 19530 不是“只读调试端点”，还需 query 向量与 Milvus 客户端。可行路径只有两条：① 用同一镜像另起一份**只读旁路实例**，仅把 `KB_GATE_ENABLED=false`，指向同一 Milvus/MySQL，不动现网；② 新增仅内网可达的 debug 参数/端点（代码改动，本轮不做） | `SearchController.java:30-43`、`PingController.java`、`ExtractionQueueStatsController.java`、`application.yml:114-118`；既有先例是 `KB_GATE_ENABLED=false` 重启后采集（[知识库310敏感性对照.md](知识库310敏感性对照.md) §执行方式） |

> 结论：**请求参数被完全忽略，门控由环境变量/配置强制决定**。本次看到的 `gateEnabled:true` 是配置值，不是“请求没生效”的偶发问题。

## 五、同批对照事实

- knowledge 容器生效配置：`TIMS_KB_EMBEDDING_MODEL=Qwen/Qwen3-Embedding-8B`、`TIMS_KB_EMBEDDING_DIMENSIONS=1024`、`TIMS_KB_MILVUS_COLLECTION=kb_knowledge_vec`、`KB_EMBED_QUERY_INSTRUCTION` 已设（`Given a web search query, retrieve relevant passages that answer the query`）。
- 噪声版 query（`蚀刻机 刻过头了，线路都刻细了，有没有人遇到过，求个解决方案`）返回 `maxVectorScore=0.6589`、`tier=C`；同请求重复两次均为 **0.6589**——说明该读数在这条**噪声措辞**下是稳定可复现的。
- 手工再套一层 `Instruct: ...\nQuery: ...` 得 **0.6612**（+0.0023），说明**服务端已自动加查询前缀**，手工再加一层只是重复前缀，不改变结论。
- **口径更正（2026-11-23 定案）**：0.6589 只适用于上面这条噪声 query；干净 query `蚀刻机过蚀刻怎么处理` 在 VECTOR 与 HYBRID 下均为 **0.7737 / A 档**（top1 `2117517479423836162`）。因此 0.6589 **不是同一 query 的分数漂移**，不能与 0.6751（回流焊 raw 读数）做差；原「相差 0.016、归因库批次」的结论**作废**，跨 query 不做比较。
