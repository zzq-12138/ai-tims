# 0.75 余弦阈值错误推送率评估

> 任务：算出现网 0.75 余弦阈值下的真实错误推送率，作为「降到 ≤3%」的前提。
> 数据：复用 M7 的 `eval_set.csv`（100 条正例），新增 leave-gold-out 100 条、四类负例 100 条。
> 全部分数来自真实 HTTP `VECTOR` 检索（Milvus 未降级），不用 LLM 打分。

## 一、三个结论

**结论 1（现网 0.75 的错误推送率）：没有 <3%。**
0.75 门控下，正例流错误推送率 1.3%（76/77 推送命中标准答案），但「库中无可用案例 + 负例」流是 60.0%（40 条推送里 24 条不可用）；等权混合 300 条为 **21.4%**（25/117）。若把"现网"按今天代码的真实状态理解——**0.75 门控尚未实现**（`docs/paper/关键技术点.md` 第 696/730 行明确写着"设计提出、代码未实现"）——则所有检索结果都会返回，混合口径的不可用率是 **61.7%**（185/300）。

**结论 2（"先退回未优化基线再优化"）：该路子的前提不成立，而且大部分"回退"根本没有可测变化。**
M7 实测：KEYWORD 90.0% → HYBRID 96.0%（+6pp）、纯 VECTOR 100.0%（比 HYBRID 高 4pp）；设备加权 96→96（0pp）、标签加权 96→96（0pp，离线 Hit@1 -1pp/MRR -0.005）、RRF k=30/60/100 全 96（0pp）。也就是说：真正"退回去会变差"的只有 HYBRID→KEYWORD（-6pp，但延迟 228ms→11ms，这是速度换精度）；回退加权与 k 调参是 0pp，"再优化"的天花板仍是 96%，讲不出增量；而"回退到纯 VECTOR"其实是 +4pp，不是更差基线。**拿 0pp 的回退去凑"先变差再优化"的故事，评委只要问一句"为什么要把已知不更差的配置退回去"就会露馅。**

**结论 3（差距与主要错误来源）：差 18.4pp，错误集中在"同象异因/同因异象"，不是"领域外"。**
等权混合 21.4% 距 3% 差 **18.4pp**（正例+负例 200 口径 17.1%，差 14.1pp）。0.75 下 25 条错误推送中：同象异因 11 条（44%）、同因异象 7 条（28%）、leave-gold-out 6 条（24%）、正例 1 条（且该条 top1 是库内同题重复条目，并非语义跑偏）。四类负例分切片：同象异因 11/25 被推送且 100% 错误、同因异象 7/25 且 100% 错误、领域外 0/25、缺字段/噪声 16/25 但 16 条全部命中原始 gold（0 错误）。**最有希望的改进不是继续抬阈值**（0.80 时错误率 0% 但正例覆盖只剩 31%，0.85 只剩 1%），**而是"top1−top2 间隔 + 根因一致性校验"**：间隔 ≥0.08 时 leave-gold-out 误推 6→0、负例错误 18→6、正例覆盖仍有 47%。

## 二、口径与数据

### 2.1 分数口径
- 置信度 = `GET /api/kb/search?mode=VECTOR&topK=5` 返回的 **top1 COSINE 分数**，取值 0~1。
- 生产默认是 HYBRID，返回的是 RRF 融合分（量级约 0.03），**不能直接套 0.75 余弦阈值**。因此本评估用同一 query 的 VECTOR top1 分作为"若加余弦门控"的置信度代理；上线需要在服务里透出向量相似度（本任务未改后端）。
- 三个阈值 0.75 / 0.85 / 0.92；`推送 = top1 分 ≥ 阈值`。

### 2.2 样本与"可用"判定
| 集合 | 条数 | 构造 | "可用"判定 |
|---|---|---|---|
| P 正例原始 | 100 | M7 `eval_set.csv`（gold 在库内） | top1 ∈ expectedIds |
| LG leave-gold-out | 100 | 逐条把 gold 从 Milvus 临时删除后再检索，模拟库内无可用案例 | 按构造不可用（gold 已移除） |
| N1 同象异因 | 25 | 症状逐字取自库内条目 + 同设备族内**库未覆盖**的根因（如 E207 类症状 + 真空泵膜片老化） | 不可用 |
| N2 领域外 | 25 | 空压机/真空泵/AGV/锅炉等 25 个库未覆盖主题，关键词全库 0 命中 | 不可用 |
| N3 同因异象 | 25 | 根因逐字取自库内条目 + 该条目未描述的另一种表现 | 不可用 |
| N4 缺字段/噪声 | 25 | 对 eval_set 前 25 条 formal 做确定性降级：去设备字段 / 截半句 / 错别字+噪声 | top1 ∈ 原始 gold 才算可用（保守口径） |

负例构造规则固化在 `scripts/eval/gen_negative_set.py`，每行 CSV 带 `source`（规则生成/规则生成+人工复核）与 `basis`（为何不可用）、`check`（构造校验结果：症状在库内=1、根因 0 命中=1、锚点根因在库内=1）。生成时自动校验：四类 100 条 `check_failed = 0`。

### 2.3 指标定义
- 覆盖率/推送率 = 推送量 / 样本量。
- **错误推送率 = 推送中被判不可用的比例**（本文所有"错误推送率"都用这个分母）。
- A 档准确率 = 正例推送中 top1 ∈ expectedIds 的比例；A 档召回 = 命中条数 / 100。
- 混合口径为 100 P + 100 LG + 100 N 等权。

**"≤3%"用单一余弦阈值能实现，但只能落在 0.80，代价是 69% 的正确问题不再被回答。** 0.78 仍 11.7%。分数分布没有留出"高精度 + 高覆盖"的区间。

## 七、"先退回未优化基线再优化"的诚实评估

M7 八轮（同一 100 条评测集，Hit@3）：

| 回退动作 | Hit@3 变化 | 延迟变化 | 是否真的变差 | 结论 |
|---|---|---|---|---|
| HYBRID → KEYWORD 基线 | 96.0% → 90.0%（-6.0pp） | 228.1 → 11.1ms | **是** | 唯一"回退真的变差"的项，但本质是"用 6pp 换 20 倍速度"，应作为成本对照，不是待优化基线 |
| 去掉设备加权 1.5 | 96.0% → 96.0%（0.0pp） | ≈0 | 否 | 回退无变化，"再优化"上限仍是 96% |
| 去掉标签加权 1.2 | 96.0% → 96.0%（0.0pp，离线 Hit@1 -1.0pp、MRR -0.005） | ≈0 | 否 | 同上；离线口径甚至略负 |
| RRF k 60 → 30 或 100 | 96.0% / 96.0% / 96.0%（0.0pp） | ≈0 | 否 | k 不敏感，"调 k 提效果"讲不出数 |
| topK 5 → 3 | Hit@5 99.0% → 96.0%（-3.0pp，Hit@3 不变） | 略降 | 部分 | topK 只影响第 4/5 位的召回 |
| HYBRID → 纯 VECTOR | 96.0% → 100.0%（**+4.0pp**） | 228→221ms | 否（更好） | 叫它"更差基线"是事实错误 |

直说：
1. 0.75 门控目前**不在代码里**，所以"退回未优化基线"没有"门控"可退；今天的系统本身就是"无门控基线"。任何门控都是新增，不是回退。
2. 设备/标签加权与 RRF k 的回退增量是 0pp——把它们"退回去再优化"最多回到 96%，故事没有数字支撑。
3. 唯一能制造"先变差"的是退到 KEYWORD（90%，11ms）。评委追问"为什么基线要退回一个已知更差的配置"时，唯一站得住的回答是"它是低延迟对照，不是目标架构"；如果说成"为了优化"，就是自曝凑数。
4. 更稳的叙事：KEYWORD（90%，11ms）作低成本对照，VECTOR（100%，220ms）作精度上界，HYBRID（96%，228ms）作折中；把"改进"落在**错误推送率/覆盖率**这条轴上（0.75→21.4% 错误率、0.80→0% 但覆盖 31%、间隔规则→9.2%/覆盖 47%），而不是硬讲 Hit@3 的提升。

## 八、最有希望的改进方向（按数据排序）

1. **加"top1−top2 间隔"作为第二判别**：0.75 + margin≥0.08，正例覆盖 47%、正例错误 0、LG 错误 6→0、负例错误 18→6。代价小、可解释、不需要新模型。
2. **根因一致性校验（治同象异因/同因异象）**：这两类贡献 18/25 条错误推送，且分数与间隔都"很像真的"。可行做法：知识条目补一个结构化 `rootCause` 字段，推送前比对 query 中"怀疑根因"与条目根因；或加一个轻量 rerank/LLM 一致性判定。按当前数据推算：这两类误推清零后，混合错误率 25→7 条（6.0%）；再叠加 margin 规则可望压到 ≤3%，但**这是推算，未实测**。
3. **不要继续抬全局阈值**：0.80 已达 0% 错误但覆盖 31%，0.85 覆盖 1%。分数分布（正例 median 0.786、max 0.852）决定了单阈值没有空间；要提升判别力得改分数可比性（rerank、向量归一化、query 改写），而不是调阈值。
4. **知识库清理**：正例唯一"错误"P-054 的 top1 是《贴片机抛料故障》，与 expected《贴片机抛料故障》同题不同 id（重复条目）；库内还有 5 条 `[角色矩阵]/[合并取舍E2E]` 测试遗留（61 向量 vs 56 条真实知识；清理后 55 条）。发布前去重、剔除测试数据，能减少"第一名被同题重复条目抢占"的假错误。

## 九、方法与局限

**方法链**：PUBLISHED 知识反推 100 条正例 → 同一批 query 做"删除 gold—检索—恢复"（N0/N1 校验）→ 规则生成四类负例（逐条校验规则）→ 真实 HTTP VECTOR top1 余弦 → 三阈值判定与切片。脚本：`scripts/eval/gen_negative_set.py`、`scripts/eval/threshold_eval.py`、`scripts/eval/LeaveGoldOut.java`、`scripts/eval/leave_gold_out.sh`；逐条结果 `docs/paper/评测/threshold_eval.csv`，汇总 `_threshold_metrics.json`。

**局限（必须和数字一起看）**：
1. **0.75 不是现网已实现的门控**（`关键技术点.md` 696/730 行：T02 置信度兜底"设计提出、代码未实现"），本文算的是"若上线 0.75"的反事实；今天现网是"无门控全返回"，混合不可用率 61.7%。
2. **余弦分来自 VECTOR 路径，生产走 HYBRID**；RRF 分与余弦不可比。要真正上线门控，需让服务同时返回向量相似度（涉及后端改动，本任务按要求未改）。
3. **负例构造有偏**：同象异因的症状逐字取自库内（抬高了相似度，可能高估误推）；领域外主题选得较"远"（可能低估误推）。真实用户输入介于两者之间，21.4% 应理解为"平衡混合口径"的量级，不是精确的线上值。
4. **缺字段/噪声按保守口径**：命中原始 gold 即计可用；若产品定义是"缺字段一律追问"，这 16 条推送应全部算错误，负例错误推送率会从 52.9% 升到 70.6%（24/34）。
5. **样本量与统计误差**：每类 25 条、总 300 条、单次运行；21.4% 的 95% 置信区间约 ±4.6pp（n=117 推送），不足以支撑"3.0% vs 3.1%"这类精细结论。
6. **leave-gold-out 只删 expectedIds**：若库内存在同内容重复条目，模拟的"无案例"会被重复条目稀释；本次 0.75 的 6 条 LG 推送均非同题重复，但 P-054 说明重复条目真实存在。
7. **"不可用"是构造定义**，不是逐条人工临床判断；规则与锚点已人工复核，但仍建议抽 20 条做人工双盲确认。
8. **成本**：新增 API 调用约 600 次 embedding（300 条 query × 正例/负例 + 100 条 leave-gold-out 检索），按 18.8 字/条估算约 1.1 万 tokens，约 0.006 元；未用 LLM 打分。
