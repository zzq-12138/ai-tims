# C 档兜底建议与处置配对记录（实现说明）

> 定位：只做「记录」，不做自动吸纳、不做闭环回流。
> 改动开关：`tims.ai.fallback.enabled`（环境变量 `AI_FALLBACK_ENABLED`），**默认 false**。
> 表结构：`docs/sql/20261111_ai_fallback_pair.sql`（仅 DDL，不随服务启动自动执行）。

## 一、为什么做

知识库门控分 A/B/C 三档，C 档（相似度低于软带下限）当前直接不推送条目，这次问答等于没有产出。本次把 C 档改成：**仍然不推送任何库内条目**，但由大模型给出通用建议，并显式标注“无知识库依据，仅供参考”，同时把建议与工单关闭时回填的实际处置配对留档。

**统计口径可分离**：`ai_fallback_pair.no_kb_basis=1` 与 `ai_call_log.status='FALLBACK'` 一起标识“无库内依据”的答案。19.1% 错误推送率等既有指标只统计库内条目，混入自由生成答案会失真，因此这两类记录必须能被单独筛出。

## 二、已实现

1. **C 档判定不变**：`ticket-knowledge` 的 `SearchService` 门控阈值与 A/B/C 判据未改动，`ticket-ai` 只读取检索响应里的 `tier` / `reason`。
2. **C 档兜底建议**：开关打开且检索正常返回 C 档时，RAG prompt 追加“兜底模式”指令（禁止编造知识库引用），服务端在回答首段统一加标记 `【无知识库依据，仅供参考】`（不依赖模型是否听话）。
3. **落库**：`ai_fallback_pair` 记录工单号/租户、档位、建议原文、模型、prompt 版本（`CHAT 版本 + "+fallback-v1"`）、`no_kb_basis=1`、建议时间。
4. **处置回填接口**：`POST /api/ai/fallback/{id}/disposition`，body `{"actualDisposition":"..."}`；写入实际处置、回填人（登录用户 ID）、回填时间，并自动判定一致性。
5. **前端**：工单详情 AI 分析抽屉在 C 档时展示黄色提示“无知识库依据，仅供参考”，并提供“回填实际处置”入口（文本框提交）。
6. **可观测**：`ai_call_log.status` 新增取值 `FALLBACK`（区别于 `SUCCESS` / `DEGRADED` / `BLOCKED`）；流式响应 `usage.fallbackSuggestionId` 返回配对记录 id，`meta.noKbBasis=true`。

## 三、一致性如何判定（选型说明）

**选择自动比对**，不引入人工标记：

- **算法**：NFKC 归一化 → 小写 → 仅保留字母/数字/汉字 → 字符二元组 Dice。
- **阈值**：`score ≥ 0.30` 记 `consistent=1`，否则 `0`；任一文本归一化后不足 8 个字符记 `NULL`（无法判定，避免“已处理”这类短句误判）。
- **原始值保留**：建议原文与处置原文都完整落库，`consistency_score` 一并保存，便于后续离线重判与阈值校准。

**为什么不用人工标记**：本功能只做记录、不驱动任何自动动作，人工标注会引入额外流程与标注者间不一致；自动比对可复现、可审计、零人工成本。代价是“换一种说法但意思相同”会被判为不一致，因此结果只用于分析，不能当作“建议有效性”的最终结论。

> 实测校准结论见第六节：Dice 在“长建议 vs 短处置”下会被长度稀释，0.30 阈值实际很难达到，后续需要改口径或重标定。

## 四、未实现（明确边界）

- **反馈校验未实现**：没有“建议是否被采纳/是否复发”的闭环观测，也没有把实际处置回流到抽取或检索。
- **自动吸纳未实现**：不写 `kb_knowledge`、不动 Milvus、不触发 `ExtractionReviewService.approve`，`ExtractionService` 抽取链路未改动。
- **不做分析面板**：只提供记录与最小回填入口。

**原因**：反馈校验依赖真实用户在工单关闭环节的回填覆盖率，以及一个可观测的复发窗口；当前既没有稳定回填量，也没有复发观测数据，此时做自动吸纳会把未经校验的自由生成内容写进知识库，风险高于收益。因此先把“建议—处置”配对沉淀下来，等真实样本足够后再决定阈值与吸纳策略。

### 6.5 已知局限（实测暴露）

## 七、新口径：处置侧覆盖率（2026-11-11 追加）

### 7.1 旧口径为什么不能用

Dice 的公式是 `2×共同片段/(建议片段+处置片段)`，分母里同时含建议长度和处置长度。建议 1000 多字、处置 80 字时，分母被建议撑大，**哪怕处置每一个字都能在建议里找到，分数上限也只有约 `2×80/(1000+80) ≈ 0.15`**，永远够不到 0.30。所以旧的 `consistency_score=0.0884` 并不代表“不一致”，它代表“两段文本长度差太大”。

新口径把分母**只放在处置侧**：只看师傅写的那几段，有几段能在建议里找到对应说法。建议再长也不会把分数压低。

### 7.2 定义与算法

| 步骤 | 做法 |
|---|---|
| 1. 切分处置 | 按 `，,。；;、换行 ！？：` 切成片段（师傅通常用逗号/分号断句） |
| 2. 归一化 | NFKC 归一化 → 转小写 → 只保留字母/数字/汉字（与旧口径同一套，去掉标点、空格、Markdown 符号） |
| 3. 丢弃噪声片段 | 归一化后不足 4 个字符的片段不计入分母（“已处理”“正常”这类没有信息量） |
| 4. 片段命中判定 | 把该片段的**字符二元组**（相邻两个字一组）拿去建议全文里找，能找到的比例 ≥ **50%** 记为命中 |
| 5. 算分 | `score = 命中片段数 / 有效片段总数`（0–1） |
| 6. 留证 | 每段都记录：片段原文、覆盖比例、是否命中、**命中的建议原句** |
| 7. 无法判定 | 没有处置文本，或切完一个有效片段都没有 → 三个新字段全部为 NULL |

实现：`CoverageScorer.java`（算法）+ `FallbackSuggestionService` 新增 `coverageScore / coverageHits / coverageSegments / coverageDetail` 四列写入，旧 `consistency_score` 原样保留、不覆盖。

### 7.3 为什么用字符二元组，不用关键词或分词

- **不用关键词词典**：维修领域同义词太多（“皮带松”“皮带打滑”“张紧不足”），词典要一直维护，漏一个就判错。
- **不用分词**：中文分词对“Y型过滤器”“冷却塔风机”这类专业词经常切错，切错就全盘错。
- **二元组的好处**：不依赖词典和分词，只要字面有重叠就能给部分分。例：
  - 处置「更换了电源模块」→ 二元组 `更换/换了/了电/电源/源模/模块`
  - 建议「建议更换电源模块并复测」→ 含 `更换/电源/源模/模块`
  - 覆盖 4/6 ≈ 0.67 ≥ 0.5 → **判命中**，同义改写（“更换了” vs “更换”）留出了余地。

**漏判/误判风险（必须说清）**：

1. **同义不同字判不中**：处置写“电源板”、建议写“电源模块”，二元组几乎不重合 → 0 命中。这是主要漏判来源。
2. **语序倒了会断**：“先清洗再补水” vs “补水前先清洗”，相邻字变了，二元组断裂。
3. **只写结果的短句被过滤**：“已恢复”“正常了”不足 4 字，不计入分母，样本里这类句子越多，分数越只反映“有动作描述的部分”。
4. **建议越长越容易误命中**：建议的二元组池大，片段随便几个常用词就可能凑够 50%。这是假阳性来源；缓解办法是把建议限制在“同主题段落”，本轮未做。
5. **片段太少会跳档**：只有 3 段时，中 1 段就是 33%、中 2 段就是 67%，粒度很粗（见 7.7）。

### 7.4 数据准备：测试行标记

`ai_fallback_pair` 原有 12 行，其中 10 行是本轮复测反复请求留下的无处置记录（同一工单 `WO20261105-0017`）。按“能标记就不删”的原则：

- 新增列 `is_test TINYINT NOT NULL DEFAULT 0`（`docs/sql/20261111_ai_fallback_pair_is_test.sql`）
- 把 10 行无处置的复测记录标为 `is_test=1`，**保留不删**
- 重算/列表接口默认 `WHERE is_test=0`，需要时传 `includeTest=true` 才带出来
- 结果：12 行里 **可见 2 行**（就是下面两条有处置的有效样本）

### 7.6 新旧口径对照

| 记录 | 处置字数 | 旧 Dice | 旧判定（≥0.30） | 新覆盖率 | 新明细 | 人工看 |
|---|---|---|---|---|---|---|
| A `2120421751173951490` | 80 | 0.0884 | 不一致 | **0.8750** | 7/8 段命中 | 方向一致，新口径符合直觉 |
| B `2120428594512392193` | 25 | 0.0089 | 不一致 | **0.0000** | 0/3 段命中 | 确实答非所问，新口径也判不一致 |

结论：新口径把“长度差”这个干扰项拿掉了。A 从 8.84% 提升到 87.5%，B 仍然是 0——说明它区分的是**内容是否覆盖**，而不是**文本是否够长**。

### 7.7 阈值建议（先给区间，不写死）

因为片段数只有 3–8 段，粒度很粗（3 段时一命中就 +33%），**不建议只卡一个总分**，建议分档 + 最小片段数双条件：

| 覆盖率 | 判定 | 说明 |
|---|---|---|
| ≥ 0.60 | 一致 | 3 段中 2 段、8 段中 5 段，属于“主要动作都被建议覆盖” |
| 0.30 – 0.60 | 部分一致 | 新增中间档，不并入“一致”，只用于观察 |
| < 0.30 | 不一致 | 基本答非所问 |
| 有效片段 < 3 段 | 样本不足 | 不判定，避免 1/1=100%、1/2=50% 这种跳档 |

建议区间取 **`[0.55, 0.70]`** 作为“一致”线的候选，默认先按 0.60 观察。理由：A=0.875、B=0.0，两条样本离得很开，中间任何值都能分开；但要等真实回填累计到 **≥30 条** 再定死，现在只有 2 条，定死没有统计意义。

### 7.8 局限（如实记录）

1. **样本量太小**：只有 2 条有效样本，一条命中、一条答非所问，无法校准阈值，只能给区间。
2. **片段少会跳档**：处置普遍只有 3–8 个片段，分数是 0.33/0.67 这种台阶，不是连续值。
3. **只认字面，不认语义**：同义词（电源板/电源模块）会漏判；这是为了免维护词典付出的代价。
4. **建议越长越容易误命中**：建议是 1000+ 字的通用排查清单，片段容易“蹭”到某句话；样本 A 的第 6、7 段就属于“方向对但表述不同”，覆盖率刚好卡在 0.5 附近，比较脆弱。
5. **配对对象可能错位**：同一工单多次问答时，建议和处置可能不是同一个问题（样本 B），需要在配对时带上问题标识，本轮未做。
6. **旧分数仍需保留**：`consistency_score` 不删，作为对照与回退依据。
