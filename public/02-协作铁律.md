## 2. 机器分工：编译在 VM，编辑在台式，发布在 master1

| 角色 | 机器 | 只做这些 | 绝对不做 |
|---|---|---|---|
| 编辑 / 传输 | 台式 Windows，仓库 `g:\JAVA\Code\ai-tims` | 改代码、`scp` 单文件到 VM、整理交付包 | 不编译、不构建镜像、不连公司集群 |
| 编译 / 构建 / 导出 | VM `dev@192.168.40.10`，仓库 `/home/dev/ai-tims` | `mvn package`、`docker build`、`docker save \| gzip`、生成 MANIFEST | 不 push Harbor（网络不通）、不碰公司集群 |
| 装载 / 推送 | 公司内网任意装了 Docker 的机器（master1 或跳板机） | `md5sum -c`、`docker load`、`docker login`、`docker push` | 不改部署清单 |
| 发布 | master1，`/data/sdv1/tims` | `deploy.sh`：镜像准备 → 改 tag → `apply -k` → `rollout status` → 回读 | 不 build 镜像 |

原因：台式没有 Docker，VM 连不上 Harbor，公司集群只有 master1 有 kubeconfig 和工作目录。跨角色做事一定会在某一步断掉。

## 3. 公司环境边界

- 只碰 **`ai-tims`** 这一个 namespace。别人的配置、工作负载、ClusterRole、PV、中间件一律不动。
- 公共资源只用不改：MySQL `10.96.1.253:3306` 的 `aitims` 库、Nacos `zzq-tims`、Harbor `library`、内网 vLLM。
- 任何写操作（apply / patch / set env / delete / restart）**必须先说明回滚方式**，再执行。
- 只读检查也用普通账号，不用 root；否则权限判断会失真。
- 公司侧操作一律写绝对路径，`/root/tims-ops` 已废弃删除。
- 服务器上 `deploy/` 是**手工上传**的，没有 `.git`。改清单前先在 master1 上 `cat` 现场那份，**不要拿本地仓库直接覆盖**，否则服务器上手写的 `front.yaml`、`kustomization.yaml` 改动会静默消失。

## 4. 台账制度（强制）

公司内网任何机器上每发生一次操作，**当轮**在 `docs/ops/公司环境操作记录.md` 追加一条，六项成表：

| 时间 | 机器（用 IP 后缀区分） | 命令全文 | 输出 | 判读 | 回滚 |
|---|---|---|---|---|---|

- 只追加不覆盖，禁止攒批补记；未记录视为该操作未完成。
- 不写真实账号、口令、token、Key，只写键名 + 「见 Secret」。
- 写脚本用单引号 heredoc（`<<'TIMS_EOF'`）+ `md5sum` 校验，避免粘贴截断和 `$` 提前展开。校验不一致必须重写再执行。
- 向服务器写文件前先备份（`cp -p ... .bak-$(date +%Y%m%d-%H%M)`）。

## 5. 前端发版铁律

发新版前端只有一种做法：

1. 改 `deploy/k8s/base/apps/front.yaml` 里 Deployment 的 `image:` tag；
2. `kubectl apply -k deploy/k8s/overlays/company`；
3. `kubectl -n ai-tims rollout status deploy/ai-tims-front --timeout=180s`；
4. 回读实际镜像。

**禁止 `kubectl set image`。** 手工改只动集群、不动清单，下一次任何 `apply -k` 都可能把它带回旧 tag。2026-11-18 已因此丢过 1.0.2。

补充：前端 Deployment 名 `ai-tims-front`，**容器名是 `front`**；`set image` 写错容器名会静默无效。

## 7. 代码同步纪律

- 台式与 VM **必须对齐到同一提交**再动代码。
- VM 工作区可能有大量未提交改动：只 `scp` 本次改到的单个文件，**不许整目录覆盖、不许 `git add .`**。
- 覆盖前先核对：把 VM 上的旧文件拉回本地，与台式改动前版本对比，确认差异只有本次改动。
- 台式工作区是 **CRLF**、仓库历史是 **LF**。`scp` 后在 VM 上先 `sed -i 's/\r$//' <文件>` 再 `git add`，否则整文件显示为改动。
- 提交统一在 VM 上做（台式可能没配 Git 身份）。
- 只用 fast-forward 推送，**禁止 force push**；需要绕行时用临时 worktree（见 `docs/ops/发布流程.md` §2.3）。
- PowerShell 重定向补丁会写成 UTF-16；用 `git format-patch -o <目录>` 生成补丁文件。

## 8. 文档同步制度

- 代码、DDL、配置、口径一变，**同一轮内**同步改文档，不攒批。
- 交付或汇报前核对文档与代码是否一致，尤其本地与 VM 上的文档版本。
- 每轮改动后汇报必须列出：改了哪些文档 + 各自版本/时间；涉及开发机同步的给 MD5 对比结果，不能只说「已更新」。
- 台账、决策台账只追加不覆盖；决策编号（DEC-xx）顺延。

## 9. 沟通规范（用户明确要求）

- 一律用**大白话**，不用学术腔和行话；必须先让用户看懂，用户才能做决策。
- 出现专业名词当场解释含义，用日常说法打比方说明「这到底在算什么」。
- 给选择题时讲清每个选项**对用户意味着什么**，不要罗列技术权衡。
- 每条运维指令必须分步、每步为可直接整段复制的完整命令，并注明：在哪台机器、用哪个账号、预期输出、失败如何判读、回滚方式。
- 汇报分批次：每批完成先单独汇报，不要攒到最后。

## 10. 实验与论文口径

- 所有数字必须可复核、可溯源到 csv / metrics.json，禁止美化。
- 构造集与反构造集结果必须并列，构造集标为上界。
- 不同题集的结果不可跨集相减；一次报告一套数（DEC-31）。
- 单次实验 1 元以内可直接跑（路由类 2 元），超出先报预估再执行。
- 所有准备进论文的内容必须记录；不确定归属的标「暂定」。
- 论文中必须标注反构造集的构造方法、数据来源与局限性，提前准备答辩口径。
